## 0. 一分钟看懂这个版块

### 数据流

```
乐檬 SaaS（AGI 网关 / 报表端点）
   │  ① 采集：duckle 管线（console 按账套分：3120 / 64188）
   ▼
对象存储湖（ZOS：lemeng/<源>/system_book=<账套>/bizday=<日>/…）
   │  ② 物化：dbt（staging 视图直接读湖 → 增量/全量 mart 落 PG 的 staging schema）
   ▼
pg_duckdb / Postgres（staging.mart_* / fct_* / dim_*）
   │  ③ 发布面：console 报表 / 问数 bot / 断言与探针
   ▼
人看到的数据
```

三层各有归属，**别混**：

| 层 | 归谁 | 判据长什么样 |
|---|---|---|
| 采集 | duckle console（每账套一个） | 管线 run 是否有事件行、湖里该日是否有分区 |
| 物化 | 平台调度器（`platform.scheduler`）+ dbt | 模型测试、`load_log` 水位 |
| 观测 | 断言脚本 → OO `data_plane_probes` → 桥 → 企微 | 断言逐条吐 verdict，**桥消费 `verdict <> 'OK'`** |

### 一天的时间表（CST，现行稳态）

```
00:05–07:35  回填切片         data.backfill_slice      每 30 分钟一轮，每条推进 1 天
00:40        T-3 源快照        console lemeng.recon.preagg
02:30        主档 dbt           data.dbt_tables          （实测 ~18 分钟）
03:25        热层 GC            data.retail_hot_gc       （只保留今天批次）
03:30        对账四件           data.dbt_tables_recon
03:40        压缩记账           data.lake_compact_index
03:50        对账缺整天自愈      data.recon_restate
04:30        台账当夜自愈闸      data.recon_ledger_guard
05:30/06:00/06:30/07:30  审计链 a2a / a2b / a1 / window
08:50        窗口重采           console lemeng.retail.windows.l1
09:00        采集开窗           tick 每 10 分钟；1h 各域 :05–:41 奇数分钟
```

**注意**：白天（09:00–01:59）只有采集和 10m/1h 物化；**全史重活一律在 02:00–09:00**。

## 1. 十条硬规矩（每条都有案例撑腰）

| # | 规矩 | 为什么（案例 / 出处） |
|---|---|---|
| 1 | **先问引擎**：新数据面工件先查 duckle 组件目录（`list_components`/`get_component_schema`），落三档再决定自己写 | 自己写等于第二套实现，靠人手同步必漂移；E3 证成方法学见正典 §1.1.1 |
| 2 | **登记面不止一处**：管线要进 `pipelines/` + `schedules/` + catalog + 契约 + 新鲜度锚 | 案例 25/29：只进 `pipelines/` ⇒ 卷里永不自动采集，而闸照样绿 |
| 3 | **窗口语义不能照信首次探针** | 案例 27：契约写「T-1 有数据」，实测恰好相反（发布滞后 16–46h） |
| 4 | **分页必有哨兵**：页数×页容量 = 硬上限，超了要 die 不能静默 | 案例 3/26：1459 单/时击穿 1400；9 页×100 静默丢 78% |
| 5 | **路径模板逐字核对**：`prefix//*/bizday=` 多一个斜杠，本地全绿、真机才炸 | 案例 28 |
| 6 | **物化断链是默认风险**：采集绿 ≠ 数据到了 | 案例 17：湖领先两天、PG 停在一周前，**37 个 job 无一跑 dbt，没有任何东西报错** |
| 7 | **读湖有三方竞态**（tick 重写 / 物化读 / 问数读）⇒ 读「今天」的路径必须用热层或闭窗谓词 | 案例 22；本仓 `etag-race-*` 若干次实测 |
| 8 | **口径改一处要四处同步**（dbt 构件 / 契约 / 采集侧 / 断言） | 案例 51/52：换货半边缺失 ⇒ 净额系统性高估 |
| 9 | **新列落湖成功 ≠ 列有意义**：要验非空率与语义 | 案例 31：补列补错别名，唯一键照样 FAIL |
| 10 | **运维只走 openship MCP / 平台调度器**，不裸 SSH；脚本交付走 lock | 根本法则；否则改的是机器状态而不是仓 |

## 2. 假绿形态学（本次复盘的核心）

> 这条线最贵的教训**不是「跑错了」，而是「看起来跑对了」**。以下八种都真实发生过，
> 且**都没有报错**——只能靠判据发现。

| # | 形态 | 例子 | 识别方法 |
|---|---|---|---|
| 1 | **闸只查一个方向** | 案例 25：只查「排班引用的管线存在」，不查「管线必须有排班」 | 为每条规矩问：**反向**成立吗？ |
| 2 | **判据测错对象** | 案例 50：延迟断言测「用户不走的那条视图」⇒ 恒假红两天 | 判据要**测用户真实路径 + 预热后计时** |
| 3 | **catch-all 兜住不该兜的错** | 2026-11-28：㉓ `compact_parity` 把「列不存在」兜成「未启用压缩 ⇒ OK」 | 降级分支**只匹配预期的缺失**，其它一律 UNKNOWN |
| 4 | **两类失败混成一种** | 2026-11-28：`notify.health` 用 `dead>0` 一刀切，4 条永久失败（40003/模板缺配）按红 7 天、一天 288 条红 | 先问「这两种失败要采取的动作一样吗」 |
| 5 | **口径差被当成数据差** | 案例 51/52：报表 vs 行级接口的换货半边 | 差先归类（口径/覆盖/真缺口）再判 |
| 6 | **观测面随迁移静默停发** | 案例 48：断言随旧 job 一起下线，45h 没人知道 | 迁移清单里加一条「**观测面跟着搬了吗**」 |
| 7 | **来源是别人的错文本** | 案例 49：`psql` 不在容器里，报错文本进了 `org` 列 ⇒ 明细恒 0 行 | 每个取值都问「它可能是错误文本吗」 |
| 8 | **窗口/相位侥幸** | 案例 22：审计曾因相位恰好避开，lookback 一改就必然红 | 并发场景要**故意造一次重叠**验证 |

**通用动作**：任何判据上线前，先做**变异测试**（人为制造一次真红），确认它真的会红——本仓每个断言都有 `WIRE_<NAME>_SELFTEST` 开关就是为这个。

## 3. 决策台账（为什么是 A 不是 B）

| 决策 | 选了什么 | 为什么（否掉了什么） |
|---|---|---|
| 采集引擎 | **duckle**，不自研 | 自研 = 第二套分页/checkpoint/幂等实现；引擎缺口按 E1/E2/E3 登记例外 |
| 工程化层 | **保留 dbt**（2026-11-25 用户定） | DAG/增量/67 条审计/选择器/血缘都在它身上；裸 SQL 只留热路径 POC |
| 调度载体 | **平台调度器**，openship 只做基建 | 业务压力不放运维平台；归属判据见 `deploy/jobs.md` §1.1 四问 |
| 车道拆分 | 10m 只到 `fct_retail_sale`，其余 1h 按域分片 | 10 分钟全量重建物理不可能（案例 53：全串行） |
| 长任务形态 | **切片**（30 分钟一轮，进度从湖推导） | 8 小时长驱动在 2 槽容器里占满一整夜，且每天数次部署都杀它 |
| 湖布局演进 | **封版分区压缩（两腿读）** | 全史读 1,508 个文件 256s；月文件后 275s→22s，且失败方向是「变慢不变错」 |
| 压缩推广顺序 | 按**谁读全史**排，不按实现难度排 | `inventory_movement` 消费方是 10 天窗 ⇒ 压缩对它无收益，暂缓 |
| 判据同源 | 断言与自愈闸**共用一条 SQL** | 两套判据必然漂移（案例 25 的同类） |
| 迁移纪律 | **先手动跑一轮再切流** | 2026-11-27 实测：一处「docker 依赖」背后是三处宿主假设 |
| 事实源位置 | 规则正文只在 `docs/standards/` + 正典；经验在 WeKnora；仓内只放指针 | 避免第二套正文 |

## 5. 现在是什么样（稳态与已知边界）

- **采集**：两账套 console，管线按 l0/seg 分片；`ADOPTED_SOURCES` 白名单；`BRANCH_NUMS` 走 whoami 现算（案例 33 后）。
- **物化**：tables 主档 ~18 分钟；1h 十域 :05–:41；tick :02/:12…；对账四件 03:30；审计链 05:30–07:30。
- **观测**：core 断言 20 条每 5 分钟；heavy 4 条每 30 分钟；SLA 每 5 分钟；全部走 `data_plane_probes` → 桥 → 企微（**不新建 OO 规则**）。
- **已知边界（诚实清单）**：
  - 主档偶发 90→150 分钟超时（#2818 节点数翻倍，未根治）；
  - `retail_order_line` 压缩未做（需先补 §7 audit 判据）；
  - `inventory_movement` 压缩暂缓（同分区两条写路径 + 消费方是窗口）；
  - `P0.5 物化水位门禁` 未开工（前提「内容水位」没有任何域在报）；
  - AMD 两项抽样度量的**样本源不在平台库**，未定位。

## 7. 最后一句

这条线的成本几乎全部来自**「不报错的错」**：断链、静默截断、口径漂移、判据把不住。
所以每次改进都要问同一个问题：

> **如果它现在坏了，谁会知道？多久会知道？**

答不上来，就还没做完。
