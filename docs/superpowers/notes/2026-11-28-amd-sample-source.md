# AMD 两项抽样度量的**样本源**：找到了，而且它停了

> 背景：路线图 `2026-11-04-auto-metric-derivation-roadmap.md` 的 G2/G3 两项度量
> （首答产出率 / 徽标覆盖率）长期挂在「**样本不足**」。2026-11-28 排查发现：
> 不是样本少，是**采集对话轨迹的流停了**。

## 1. 样本源在哪

不在平台库、也不在数据仓库 —— 在 **OpenObserve 的日志流**里（`scripts/demand-mining.mjs`
读的就是它们，`ASK_DEMAND_CONV_STREAM` 默认 `askdata_trace`）：

| 流 | 用途 | 最后写入 | 近 3 月行数 |
|---|---|---|---|
| `askdata_trace` | 逐轮对话轨迹（role / text / tool_name / tool_args / tool_result） | **2026-11-19 07:23 UTC** | 2,955 |
| `askdata_stuck` | 卡住的会话归因 | **2026-11-16 16:23 UTC** | 23,748 |
| `askdata_stats` | 会话统计 | **2026-11-16 16:23 UTC** | 4,115 |
| `askdata_conv` | 历史对话（**已冻结**，2026-10-16 起停） | — | — |

三个流**分别停在两个时刻**（11-16 16:23 与 11-19 07:23）⇒ 至少有两个写者，先后停了。

## 2. 这意味着什么

两项度量的定义都依赖「真实的问数会话」：

- **首答产出率** = 词表未覆盖的问题里，首答就给出结果（而不是「查不到」）的比例；
- **徽标覆盖率** = 答案里带口径/新鲜度/创建者徽标的比例。

**没有新会话就没有分母**。所以它们不是「再攒攒就有」，而是「**必须先把轨迹导出修好**」。

## 3. 下一步（按顺序）

1. **确认是谁停的**：`askdata_trace` 的写者（`export-transcript.py` 或 openclaw 侧导出）与
   `askdata_stuck`/`stats` 的写者（可能是不同 job）——两者的最后写入时刻不同，先各自定位；
2. 恢复导出后，先用**一周**数据算一版基线（分母可能仍然小，但至少是活的）；
3. 度量口径落成脚本（放 `scripts/askdata/`），进 `data.warehouse_assertions` 的 heavy 档或独立 job，
   避免又变成「一次性口头结论」。

## 4. 顺带记录

`askdata_*` 系列**没有租户字段**（2026-11-07 实测），所以任何按 org 切分的度量都做不了——
这是既有边界，不是本次新发现。
