## §1 终态（可判定形态）

| # | 终态判据 | 怎么量 |

## §3 硬规则（违反即回退，写进 review checklist）

1. **报表 spec 不得重声明**口径、掩码、新鲜度、维度词表——只允许**引用** metricId / 维度名 / 实体。需要不同口径 ⇒ 新建 L2 指标，不是加报表开关。
2. **窗口与对比只有一个实现**（`ReportWindow` + `ComparisonSpec`）——渲染 / facts / 叙事 / lint 共用；新增第二份实现即违规。
3. **没有计算凭证的 A/B 档指标**，不允许进发布快照。
4. **没有通过语义 lint 的 spec**，不允许发布。
5. **版式走模板 + 槽位**，不做自由画布；**L5（任意 HTML/CSS）永不做**。

## §5 表达自由度阶梯（L0–L5）

**原则：扩展自由度 = 增加原语，不是放宽解析器。** 每加一档，都带契约、校验、渲染、空态、移动端与快照测试；「自定义 HTML 后门」不在此列。

| 档 | 能给什么 | 谁用 | 控制机制 |
|---|---|---|---|
| **L0 纯文本** | 现状 `text` 面板（`ReportView.tsx:332-334`，`pre-wrap`、不解析格式） | agent | 长度上限 |
| **L1 受限 Markdown** | 粗体/斜体/行内代码/列表/引用/链接/小标题 | agent + 业务管理员 | 语法白名单；无 HTML；链接协议白名单 |
| **L2 语义内嵌** | 文本里引用**活的**指标：`{{metric:net_sales\|window:range\|fmt:currency}}`、`{{delta:net_sales\|vs:prev_period}}`、`{{as_of}}` | agent | token 只能引用 **plan 中已声明**的指标与窗口；服务端解析，前端只渲染 |
| **L3 布局块** | 分节、双栏、提示框（结论/风险）、指标行、可折叠明细 | agent 填槽，人选择 | 块类型闭集 + 嵌套深度上限 + 每块契约 |
| **L4 图表配置** | 堆叠/组合、目标线、颜色语义、双轴（谨慎） | agent | options 白名单，**不透传**任意 ECharts option |
| **L5 任意 HTML/CSS** | — | — | **永不做**（红线） |

**控制机制三条**

1. **编译期校验**：语法白名单 + token 必须绑定到 plan 中存在的 metric/window + 长度/嵌套/数量上限；不通过 = 发布被拒，并给人话原因。
2. **渲染是纯函数**：spec 存源文本，渲染只产出 React 节点，不用 `innerHTML`（沿用体系地图测试「全文无 innerHTML」的先例）。
3. **扩展走提案**：客户要新玩法 ⇒ 新增块类型或 token（带完整契约），与指标 L1 提案同一套治理。

**现状去重**：`AiTextPanel.tsx:110-119` 的 `renderRich` 与 `system-map/map.ts:1024` 的 `richText` 是两份实现，R3 收敛为一个共享 `RichText` 组件。

**L2 与 claims 的关系**：叙事里的断言引用 plan/凭证项，本质是 L2 token 的另一种用法；R5 的 claims 绑定复用同一条解析通道，避免再造一套。

## §7 每波设计要点

### R0 组合语义地基

- **`ReportPlan` 形状**（组合语义唯一事实源）：
  ```
  { datasets: [{ metricId, dims, filters }],
    analysis: { window, comparisons[], decomposition, recipe? },
    blocks:   [{ type, dataset, layout }] }
  ```
- `daily_ops_v1` 不再是独立代码路径，而是 **recipe → plan** 的编译结果；`report-daily-review.ts` 保留为 recipe 实现，退出「自己算基线」的角色。
- `report-facts.ts` 从「遍历面板再查一遍 + 自己算对比」改为「执行 plan」；同样，`ReportView.tsx` 的对比区间只从 plan 取。
- 验收测试：改 `ReportWindow` 的截止规则，四个消费者在同一次测试里一起变。

### R1 计算凭证与复算

- 凭证是**结构化 JSON**（不是截图文案），前端只渲染；建议形状：
  ```
  { metricId, definition, window: {from,to,basis}, scope: {branch,books},
    asOf, components: [{label, value, op}], samples: {count, exportToken},
    reconciliation: { sourceOfRecord, delta?, candidates: [...] } }
  ```
- **指标分档**（决定给什么凭证）：
  - **A 可手工复算**（营业额/订单/客单/销量/会员销售）→ 组成树 + 明细导出 + 单号可查
  - **B 可与源系统对账**（毛利/报损/费用）→ 源侧对账 + 差异分解
  - **C 只能解释口径**（净毛利/同店/分摊/同比）→ 口径卡 + 假设清单 + 最近复算结论
- **差异分解**做成纯函数：`explainDelta(userValue, receipt) → [{reason, amount, evidence}]`；候选原因可枚举（退货/赠品/跨日/账套/时点/报损），不预设「系统错」。
- 明细导出复用 `drill` 的授权与掩码，**禁止绕过 `authorize()`**；分页上限单列，不沿用 1000 行硬截。

### R2 模板化生成与验收

- agent 的产出物是 **槽位填充 + 说明书**，不是布局；版式由模板决定。
- **语义 lint 四条**（基于 plan，不重新解析 spec）：
  1. 同一指标在同一报表里必须同窗口、同口径；
  2. 有 `ai_text` 的报表，必须包含支撑其结论的面板（分析就绪）；
  3. 有对比的面板，基线覆盖不足应禁用而非画假线；
  4. 同一页不能出现两个互斥口径的同名指标。
- **审阅页三件套**：变更 diff（spec 级）+ 说明书（口径/窗口/范围/排除项）+ 自证报告（lint/锚点/权限预览）。
- 打回必须选原因（口径错/期间错/数据不对/不好看），原因进台账，用于度量与优化 prompt。

### R3 呈现层升级

- **IR v2**：`datasets + blocks + shared filters`；现有 panel 数组做一次迁移，渲染结果逐字节等价（快照测试）。
- **组件白名单 6 个**：交叉表、组合/堆叠、目标对比（bullet）、瀑布（差异分解）、KPI 迷你趋势、可折叠明细。新增组件需证明**复用 ≥3 次**。
- 每组件先有：数据形状契约、空/错/加载三态、移动端行为、无障碍、快照测试，再有视觉。
- **富文本**：共享 `RichText`，语法白名单；`text` 面板加 `format: 'plain' | 'markdown'`（默认 plain 向后兼容）；`ai_text` 与体系地图改为复用。
- L2 token 解析在服务端完成，前端不取数；token 无法解析时整块渲染失败并给出可读原因（fail-closed，不静默降级成空）。

### R4 查询计划与缓存

- 缓存键必须含 **scope hash**（权限变化即失效）；禁止跨租户共享缓存条目。
- 面板去重按 `(metricId, dims, filters, window)`；KPI 与图表共享同一次取数。
- AI 的 facts 必须复用页面已取结果（当前 facts 会把面板再查一遍，缓存也省不掉这部分）——由 plan 执行器统一供给。

### R5 信任闭环

- 叙事只能引用 plan/凭证中的项；引用不到的断言直接判失败（比数字白名单硬）。
- 指标：fallback 率、越界率、生成时长 p95、缓存命中率 → 日报面板 + 阈值告警。
- **20 条金标叙事**：固定 facts → 断言「必含 / 禁含 / 每个数字可溯源」，进 CI。
- 渲染快照：每个组件至少一张 golden，防止「改样式顺手改坏空态」。

### R6 交付与治理

- 山海实例纳入 CI，或至少提供「线上 commit ↔ main」对照页；发布以系统事实为准，不靠人的记忆。
- `report_versions` 的 append-only 下沉到 DB（触发器或撤销 UPDATE/DELETE 权限）。
- 发布前权限预览：谁能看、命中哪条 ACL、是否含敏感列。
- 业务报表管理员角色（每租户），平台只裁决口径；30 天零访问报表提醒归档。

## §8 时间表与依赖

```
阶段 A（第 1–6 周）  信任地基
  R0 ──▶ R1 ──▶ R5-lite（fallback 面板 + 首屏 p95 基线）
  并行：N5 基线测量、明细导出分页

阶段 B（第 7–16 周）  生成与呈现
  R2（模板 + lint + 审阅页） ──▶ R3（IR v2 + 6 组件 + RichText）
  R4 与 R3 并行（先 IR 后缓存 key）

阶段 C（第 17–26 周）  规模化与治理
  R6 + C 档自动对账 + 场景模板库扩充 + 使用度量复盘
```

**为什么这个顺序**：R0 是一切的前提（否则每加一个能力就多一处窗口实现）；R1 先于 R2——先证明「业务人员真的能验收」，再谈大规模生成；R3 的组件必须在 IR v2 之后，否则多页/共享筛选会把现有 panel 模型撕开。

## §10 明确不做

- 通用拖拽画布、自由 SQL、自建 BI 引擎；
- 把版式/报表配置写进 dbt YAML（会污染语义层）；
- 为每个客户定制一次性报表代码（模板槽位不够就扩槽位，不开分支）；
- 在没有凭证的情况下扩大 AI 叙事自由度；
- 饼图/散点/桑基等低价值图表（先把 6 个高价值组件做透）；
- **L5 任意 HTML/CSS**。
