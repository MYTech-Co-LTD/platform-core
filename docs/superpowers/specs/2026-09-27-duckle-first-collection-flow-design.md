4. **CLI 裸跑是「无痕」的**：`duckle-runner run` 直接跑**不写 run 历史、不出现在控制台、不触发告警、不更新 metrics**

5. **失败也返回 HTTP 200**：外部编排器必须自己看 body 的 `status`（`ok|error|cancelled`）（上游 `ci-and-orchestration.md`）。
   ⇒ 任何「用 curl 调 console 就算成功」的写法都是**假绿**，验收里必须显式判 body。

   **一账套一 console 不是选择，是约束**（§1.1.4 已写，本次给它补上「结构性」这个定语）。
7. **观测面：引擎有，我们没用**：`alerts.json`（事件 `Failure/Recovery/Success/Stale/Refreshed` + 冷却 + **恢复通知不受冷却压制** +
   送达超时 10s + **永不失败上游** + 错误脱敏）、`/metrics`（需认证）、receipt、NDJSON 运行日志、**`sla.rs` 新鲜度巡检**
   （按墙钟按 `owners.json` 的 `maximumAge` 评估，专抓「**没有失败的停更**」）。
   我们的现状是 `notify_fail` + `_ops`——而 **#210 实测 `_ops` 这条通道从未接通**
   （数据面机缺 `/etc/openobserve-ingest.env`，每窗打 `OPS_SINK=DISABLED`）⇒ **观测面是空的**。
8. **判据类能力（qa.\*）分两类，别混**：`qa.contract`（我们已在用，**既定**）／
   `qa.baseline`（与**最近 N 次已接受 profile 的中位数**比，观测总是写、接受延迟到整 run 成功）／
   `qa.reconcile`（源↔目标）／`qa.freshness`（⚠️ **按本地墙钟算**，偏 +8h，源码级确认，见分析件 §3.3）。
   ⇒ 「新鲜度」有**两套**：`qa.freshness`（有坑）与 `sla.rs`（UTC 归一）。**别把两者当一个东西。**
9. **水位是引擎原生的，且语义比我们自算的更严**：`xf.incremental` / `src.rest` 的请求侧增量 / `xf.tumble` / `src.spool` / `src.changed`，
   状态落 `<workspace>/state/`，**只在整条 run 成功时才推进**。引擎文档把「自算窗口」的两种失效形态写成了表：
   状态**比汇旧** ⇒ 重复；状态**比汇新** ⇒ **静默缺口**（无报错、无行数异常）——**后者正是我们现在的风险面**。
10. **回填也是原生的**：`/api/backfills`（+ `POST /api/batch/redrive`）、水位 `GET/POST/DELETE /api/watermarks`、
    `backfill` CLI、`retry` CLI（**手动规划器**，会**拒绝**重放会重写 sink 的 run——「拒绝本身就是价值」）。
    ⚠️ **引擎没有运行级自动重试**（只有批次项级指数退避 + 连接器 HTTP 级 429/5xx）⇒
    我们的外层兜底重试**不是重复造轮子**，但要改成**用 catch-up 账本**（`Misfire::{Skip,Latest,All}` + `.duckle/occurrences.ndjson`；
    首次见到一个 schedule **只 ARM 不触发**）。
11. **对象存储 sink 只有 `overwrite`**（`snk.minio` / `snk.s3` / `snk.r2` …）：`capability-matrix.md` 逐行确认。
    ⇒ 我们「**分区单文件覆盖写 + 水位**」的幂等范式**正好是引擎支持的唯一形态**，方向一致，**不是将就**。
    ⚠️ 但没有 upsert/merge（那只有 DB / DuckLake 目标有）。
12. **两个已知会骗人的面**（用前必须挂钩）：
    - `maxPages` **默认 100**，撞上限**报错**（好过静默截断，但 288 窗/天必须显式调或改窗口粒度）；
    - `cursor` 策略**属性缺一会静默降级为不翻页**（`plan/mod.rs:5897-5903`）⇒ 配置**必须成对**。
13. **🔴 我们跑在 v0.7.3，而 v0.7.4 修了一类「绿灯却在丢数据」的 bug，正中我们的写法**：
    单文件 sink 改为**按 rename 发布**（否则下游 glob 会读到被杀的 run 留下的**半写文件**，上游实测 10.5M 行 vs 实际 8M）。
    **我们正是「每分区一个 `all.parquet` + 下游 glob 读」** ⇒ 升级优先级高。
    ⚠️ 升级会换 DuckDB（0.7.3 钉 `1.5.4`、0.7.4 钉 `1.5.5`），而读方 `pg_duckdb` 是 `1.4.3` ⇒
    「**写方比读方新**」那条 gate **必须先验再升**（正典已记为未验）。
14. **计划/编排面也有原生的**：`GET/POST/DELETE /api/plans`、`POST /api/plans/run`（多管线编排）；
    `policy.json`（**计划期**强制、**只能收窄**：`denied_components` / `allowed_domains` / `allowed_s3_prefixes` /
    `allow_state_mutation` / `allow_unsigned_extensions` …）。

## 2 判据：duckle first（写进 §1.1 决策层，宪法级）

> 每接一个能力，**先问「引擎原生怎么做」**。答案必须落在三档之一，**不许含糊**：

| 档 | 判据 | 写法要求 |
|---|---|---|
| **①引擎有 ⇒ 首选** | 源码级确认存在，**且在本环境跑通过** | 写成「首选」，并注明**怎么声明**（组件/字段/端点）与**哪次实测**定的案 |
| **②引擎有但未验 ⇒ 先挂 gate** | 源码级确认存在，**本环境没跑过** | 写成「首选（**未验**）」，**同段给出最小验证动作**；验过才升级为 ① |
| **③结构性没有 ⇒ 归我方** | 不是「不会用」，是**引擎结构里无处安放** | 必须给出**结构性理由**（引 `file:line` 或上游自述）——「嫌麻烦」不算 |

**两条不放松**：
- **禁止把 ② 写成 ①**（这是本 spec 存在的首要理由）；
- **禁止把 ③ 写成 ②**（挂个 gate 拖着，等于永远不做）。

**依据强度**：本条判据的**出处一律是分析件**（`file:line`），**不是引擎文档**——
文档已经漂过（分析件 §3.3 记录了「文档里出现不存在的组件 id」这类）。
⇒ 引能力时**优先级**：**源码 > `capabilities --markdown` 产物 > 文档**。

## 3 资产面：桌面端管什么、怎么到服务器侧

> **与 `handbook` §1.1.6 的关系**：那一节已有「桌面测 → 服务器跑」的**口径**（①资产在哪 ②两端同一内核
> ③四条保真度纪律 ④分发三条路 ⑤两条硬纪律 ⑥观测 ⑦待裁决）。**本节补两件它没做的事**：
> **(a) 把「自定义代码」与「扩展」正式纳入资产面**——§1.1.6 只把扩展当成一条「保真度纪律」（预装数量不同），
> 没回答「扩展这个资产谁维护、放哪、怎么投」；**(b) 给出 资产类 × 谁维护 × 进不进 Git × 怎么投 的矩阵**，
> 让「管资产」逐项有落点，而不是停在一条原则。出处同 §1.1.6：分析件 §6 / §7（v0.7.4 源码级）。

**总拓扑一句话**：**桌面（+Git）= authoring 与唯一事实源；服务器 = runtime，只运行、不编辑**（**单向**）。
⚠️ 上游逐字：桌面与 runner **同时**打开一个 workspace 是「**从笔记本搬到服务器的中途形态**」，
**不是推荐的长期拓扑**。⇒ 「**桌面端永远保留资产**」这个目标**成立**，但它的成立条件是
「**资产在桌面与 Git，服务器不反向持有唯一副本**」——**不是**「两端同时开着同一个 workspace」。

### 3.1 三个动作别混（Deploy / Build / Release）

| 动作 | 产物 | 去向 | 我们用它做什么 |
|---|---|---|---|
| **Deploy** | **pipeline JSON 原文**（⚠️ 占位符**不解析**） | 服务器 workspace **根**（临时文件 + rename，**可覆盖**） | **单份管线快速上线** |
| **Build** | 自包含单文件可执行（内嵌引擎 + DuckDB CLI + 已用扩展 + **已解析**管线 + 密钥） | **本机磁盘**（**不是服务器**） | 交付给无 duckle 环境的场景。⚠️ **不打包 `components/`** ⇒ `ext.*` 节点在没有该 workspace 的机器上**直接失败** |
| **Release** | **控制面全量快照**（hash 寻址）+ 环境指针（`activate`/`rollback`，**单次 rename** ⇒ 读者只会看到上一个完整版本或新的完整版本） | 服务器 workspace 的 release store | **整份版本化 + 可回滚**（⚠️ **不含密钥**，`release.rs:29` 逐字 `## No secrets`）——**未验**，见 §3.5 |

⚠️ **Deploy 与 release 在源码里没有任何调用关系**（`deploy_into` 全文不碰 release）。
**Deploy 是盲覆盖**（只回 `replaced: true/false`，不比对、也不警告「服务器那份更新」）。
⚠️ **Deploy 落的是 workspace 根，不是 `pipelines/`** ⇒ 服务器上同一套管线会有**两种路径风格**
（`catalog` 递归全树所以都发现得到，功能无碍，但**运维要知情**）。

**服务器侧的护栏**（这几条正是我们要的）：落点**词法校验**（拒绝对路径 / 盘符 / `.` / `..` 段）；
写入 = **同目录临时文件 + rename**（「a scheduler tick landing mid-write must never read half a pipeline」）；
**客户端侧拒绝明文凭据**（用**引擎的分类器**查 `literal_secrets`，非空即**拒绝部署**——判断逻辑放引擎里，
保证 build 与 deploy 两条路对「什么算密钥」不产生分歧）。

**两个动作、两个角色**：**Deploy = Admin**（逐字理由：「a deployed pipeline **runs shell and SQL on this host**，
所以部署就是**交出代码执行权**」）；**启用调度 = Operator**。
⇒ **上线是两件事，不是一个动作**（见 §3.4 第 4 条）。

### 3.2 资产分类 × 谁维护 × 怎么投

| 资产类 | 内容 | 进 Git？ | 谁维护 | 怎么到服务器 |
|---|---|---|---|---|
| **管线** | `pipelines/*.json` | ✅ | 桌面（真引擎产出，**仓内不手编**——§4 D 段既有纪律） | Deploy **或** Git seed——**二选一，别混**（混用会让「服务器那份」来源不明） |
| **调度 / 告警 / 所有者 / 编排** | `schedules.json`、`alerts.json`、`owners.json`、`plans.json` | ✅ | 仓内（`deploy/duckle/console/…`） | **seed 进 workspace 卷 + 重建容器**（§1.3.2 **两步都做**——漏一步 = 改了没生效**且不报错**） |
| **契约 / 语义** | `contracts/`、`dbt/`（本仓路径） | ✅ | 仓内 | 随仓（与本 spec 的 A / C 段同源） |
| **连接** | `connections/*.json`（**密文**） | ✅（密文进） | 桌面 | ⚠️ **换机 clone 后解不开**——解它的是 `.duckle/keys/secret.key`，**永不进 Git** ⇒ **密钥另行分发** |
| **上下文 / 例程** | `contexts/`、`routines/` | ✅ | 桌面 | 与管线同路（Deploy / Git seed） |
| **自定义代码** | 见 §3.3（**三种载体**） | ⚠️ 分三种 | 桌面 + 仓 | **三种载体三种投法**（§3.3） |
| **扩展 `ext.*`** | 见 §3.3 | ⚠️ 目录进仓 | 桌面 + 仓 | **`<workspace>/components/<name>/` 一个目录**（docker = **挂卷**）⇒ **seed 进每个账套各自的卷** |
| **运行态正确性状态** | `state/<pipeline>/`（**水位**）、`checkpoints/`、`baselines/` | ❌（**由运行产生**） | 引擎 | ⚠️ **不是缓存，是正确性状态**——它决定「下次采哪些」。**跟着 workspace 卷走**，**不进 Git、别手改**；回填用 `watermarks` API（§4 H 段） |
| **历史与派生物** | `runs/`（50 条/管线）、`runs/receipts/`（200 条）、`logs/`、`cache/`、`manifests/` | ❌ | 引擎 | 不用投——引擎自产（§4 G 段的观测面吃它） |
| **机器本地** | `.duckle/`：`keys/secret.key`、`secrets/`、`locks/`、`settings.json`、`deploy-targets.json`、`console.db`、`alert-state.json`、`environments/`（release 指针） | ❌ **绝不** | 各机自持 | **永不投递**。⚠️ 官方每次 commit 前会重写 `.duckle/.gitignore`，但它**走 `git add -A`** ⇒ **那份 ignore 是最后防线、不是建议** |

**「资产永远留在桌面侧」怎么成立**：人写的那几类**全在桌面与 Git**；服务器只持有**运行态**
（`state/`、`runs/`、`logs/`）与**投递进来的副本**。⇒ **回滚 = Git 里那一版重发**（上游给的口径逐字就是这个），
**不是**「去服务器上改回来」。

### 3.3 自定义代码与扩展：三种载体，三条路线

**引擎侧三条路线（别混）**：

| 路线 | 形态 | 状态 | 分发单元 |
|---|---|---|---|
| **① `ext.*` 外部组件** | `<workspace>/components/<name>/duckle-component.json` + **任意语言可执行文件**；stdin JSON 请求 / stdout JSON 应答；数据走 Parquet（可声明 Arrow IPC） | **生产可用、官方文档化** | **workspace 里一个目录**（docker = 挂卷） |
| **② 管线内 `code.*` 节点** | `code.sql` / `code.sqltemplate` / `code.python` / `code.javascript` / `code.shell` / `code.wasm` **available**；⚠️ **`code.rust` 是 planned 且零实现**（拖不上画布） | 可用 | **随管线** |
| **③ 内建级组件**（`src.*` / `xf.*` 那种） | 改上游 Rust **5 处** + 重生成 catalog；`crates/plugin-sdk` 是**已废弃脚手架**（上游 `CONTRIBUTING.md` 点名） | 只能 fork | 维护分叉——**不做** |

**判定**：我们自建那部分 ⇒ **① `ext.*` 首选、② `code.*` 兜底**（分析件 §7.2 给了**逐件事**的判定表：搬 / 半搬 / 不该搬）。
**不该搬的**：**部署投递**（`data-plane.lock` + 就地核验同步）与**容器生命周期**——**不是 duckle 的领域**（§4.2 已列）。

**`ext.*` 的待遇是「半套」，不是「比 `code.*` 好」的一等公民**（**2026-09-27 实测订正**：
原文写「独立调色板分类 / catalog / MCP / capabilities 注册表 / policy 门禁 / run 回执」一句打包，
**实测与其中两项相反**）：

- ✅ **成立**：**policy 门禁**（`ext.` 前缀 ⇒ `executes_process()=true`）、**run 回执** `Used`/`used_by`，
  以及 **`components conform <id>` 行为验收套件**（先验「initialize 不许干活」「零行进零行出」「20 万行大批」
  「崩了要干净报错」「**secret 脱敏**（查实际发出的字节）」「超时上界」）⇒ **输出 json，能直接卡 CI 门禁**。
  ⚠️ **用例数随组件 kind 变**：source（0 输入）时第 4/5/6/9 条显示 **`n/a`（不适用）——`n/a` 不等于绿**；
  要 10 pass / 0 n/a，须 transform 形态**且**应答里带 `rejects` / `artifacts`。**引用「10 用例」必须带上这两个前提。**
- ❌ **不成立**：**`catalog` 与 MCP 都看不见 `ext.*`** —— `duckle components schema` 导出 **411 条全是内建、
  0 条 `ext.*`**；MCP `list_components` / `get_component_schema` 同样返回不了。
  **唯一**能发现它的列举面是 **`duckle components external --workspace <ws>`**。

🚧 **gate 级 blocker（2026-09-27 实测）**：**MCP `validate_pipeline` 会把含 `ext.*` 的管线判死在门口**
（`(ext.probe) isn't executable on the DuckDB engine yet - it's a preview component.`）
⇒ **我们惯用的 MCP 通道不能用来校验含 `ext.*` 的管线，改用 CLI `validate`**（同一份管线 CLI 放行、`exit 0`）。
⚠️ 但 CLI 也**查不了 ext 组件的属性**（自认 `component_not_in_catalog … its properties cannot be checked`）
⇒ **属性名写错能过 `validate`、到运行时才炸**。

**① 的实测出处（2026-09-27 补验）**：本机隔离实验室（darwin/arm64，**零生产**）、**pip `duckle` 0.7.3** +
`duckdb` CLI 1.5.4；命中 **spawn/干活/数据往返 ✅、子进程继承宿主 env ✅（sha256 前 8 位逐位相符）、
`components conform` 10 passed/0 failed ✅、分发单元（`build` 不打包 `components/`，隔离跑 exit 1 且报错干净）✅**。
原始输出见 `.superpowers/sdd/2026-09-27-duckle-first-collection-flow-p1/task-2b-report.md`。

⇒ **纪律**：**凡「会长期存在的自建逻辑」优先做成 `ext.*`**（有验收套件）；`code.*` 用在「一次性 / 只这一段用」。

⚠️ **两条安全空档（设计如此，不是疏漏）**：
1. **`allowed_paths` 与 `allowed_domains` 对 `code.*` 全部失效** —— `allowed_paths` 只在 `snk.*` 分支生效；
   `outbound_host_allowed` 只挂在**进程内 reqwest resolver** 上 ⇒ **`code.python` 的子进程可以连任意主机、读任意文件，而 policy 看不见**。
   （`code.sql` 那条同族洞**已堵**（`refuse_unsafe_sql`），但 `code.python` / `code.shell` 是**有意留着**的——它们就是「跑任意程序」。）
2. **没有 per-execution 的审计事件** —— 审计日志记的是**鉴权动作**（console/CLI/MCP 的 Allowed/Denied），
   **不记「某个 `code.*` 节点被执行了」** ⇒ 要留痕得靠 **run manifest + retry 回执**，不是审计日志。

⇒ **纪律**：`code.*` 与 `ext.*` 都属于「**在宿主上跑任意程序**」：
- **能进 policy 的尽量进 policy**（`ext.` 前缀 ⇒ `executes_process()=true`；`components.deny:["ext.*"]` **一票否决**）；
- **凭据走引用名，不走值**：`ext.*` 组件**继承宿主 env**（spawn 处无 `env_clear`）⇒ **只传引用名 + 组件自己读 `std::env`**（这是 `plugin.rs` 的设计意图）；
  ⚠️ **别在 ext 组件属性里用 `${ENV:...}`**——宿主会把**真值**替换进属性、再塞进 stdin 的 JSON，**与「secrets absent」的设计相悖**。
  ⚠️ **这与「管线里用 `${ENV:...}`」方向相反**（管线是**从宿主 env 取值**，组件是**读宿主 env 本身**）——**两条路别套用同一条纪律**。
  ⚠️ **静默坑（2026-09-27 实测）**：占位符**未解析时不报错**——只发 warning（`${ENV:…} is unresolved …`）、
  **run 仍 `status: ok`**、且**字面量原样下发**给组件 ⇒ 密钥没配好**不会红**。

### 3.4 投递的五条硬纪律（不守会**静默**坏数 / **静默**覆盖）

1. **服务器只运行、不编辑** —— ⚠️ **没有回拉，也没有漂移检测**（源码里穷举 `reconcile`/`drift`/`desync`/`diverged`/`out_of_sync`
   **均无此语义**；`GET /api/pipeline` 能拉但**桌面 UI 没接**）。⇒ 有人在服务器改了管线，下次 deploy **静默覆盖**它，
   而桌面**不会知道**。这是「桌面为源」模型**唯一的真实风险**，靠**流程纪律**规避。
2. **一个 pipeline 只在一侧跑** —— 桌面**手动 Run 不取运行锁**（引擎注释自认）⇒ 与服务器同管线的调度跑**可并发**、
   **同时写同一 sink、同时推进同一水位** ⇒ **静默丢数**。锁只覆盖「调度触发」那一条路径。
3. **机密只用 `${ENV:...}`**（管线侧）—— 「**已保存连接**」的解密值会被**复制进管线文件、随 deploy 传出去**；
   官方逐字：「**Picking a saved connection does not, by itself, protect the credential**」。
   （`${ENV:}` 本身**不会**随 deploy 传 ✓。）⚠️ **组件侧反例**见 §3.3 末条。
4. **调度随 deploy 一律被强制 `enabled:false`**（服务端**即使客户端送 `true` 也改写**，有专门测试守着；逐字理由：
   「在笔记本上设的节奏不该一到生产就开始点火，**打开它是一个独立的动作**」）
   ⇒ **我们的流程必须显式包含「启用」这一步**（启用 = Operator 角色）。**别指望 deploy 完就在跑。**
5. **两端外壳有缺口，别只在一端验**（内核同一份，缺口在外壳；按风险排序）：
   - 🔴 **占位符替换是两份实现**（桌面 canvas = **TypeScript**、服务端 = **Rust**，**手工同步、无编译期约束**）
     ⇒ **凡涉 `${date}` / context 优先级，必须在 CLI 或 `serve` 上再验一次**；
   - **默认并发桌面 8 / 服务端 1**（源码自认「a pool that means 8 here and 1 there is worth less than no pool at all」）
     ⇒ **桌面跑得动 ≠ 服务器跑得动**；
   - **桌面 Settings 的三项服务端不读**（`spill_dir` / `allow_unsigned_extensions` / `https_proxy`）⇒ 资源 / 代理类设置**要在服务端另配**；
   - **扩展预装两端不同**（桌面 11 / 服务端镜像 12，多 `inet`）⇒ 用 `xf.ip.parse` 这类组件的管线**别只在一端验**。

### 4.1 三条「坑」升格为**设计规则**（§1.3.2 就地改写）

**并保留**「改调度定义后必须两步都做」（① re-seed 进 workspace 卷 ② 重建 console 容器；
文件 bind-mount 钉 inode ⇒ 原子替换后运行中的容器**仍看到旧文件**）——

## 7 风险与未验（别把这份 spec 读成「都能直接用」）

0. **🔴 版本差是当前最大的风险，且它不在这份 spec 的波次里**：我们跑 0.7.3，而 0.7.4 修了「单文件 sink 按 rename 发布」
   （否则下游 glob 读到**半写文件**）——**正中我们「每分区一个 `all.parquet` + glob」的写法**。
   ⇒ **升级应作为独立一件**（带那条「写方比读方新」的 gate：读方 `pg_duckdb` 1.4.3 vs 写方 1.5.5）。
   **本 spec 只登记，不排波**（它跨越 W1–W3，硬塞进任一波都会让它被别的变量拖住）。
1. **`src.rest` 增量依赖上游支持游标**（W3 gate，见上）。
2. **`drift` 未声明 schema 时静默 exit 0**（假绿）⇒ 断言声明存在是**必须**，不是可选。
3. **`qa.freshness` 时区坑**（本地墙钟，+8h）⇒ **新鲜度用 `sla.rs` 那套**（UTC 归一）；两者不是一个东西。
4. **v0.7.4 的「rows-in, rows-out 子作业」可能推翻「块作用域编排必须自研」** ⇒ 升级后**先拿最小例子验**（子作业能否既吃父的行、又把行交回父）。
5. **两套调度器行为有差**（catch-up / FileWatch **只在 serve 一侧**）⇒ **别拿桌面端行为当服务端**。
6. **`pipelineHash` 是代码指纹、不是数据指纹**；`receipt.engine_version` 恒为 `0.0.1`（**别拿它判版本**）。
7. **上游自陈的安全边缘**（对我们有影响的三条）：连接密钥加密**只覆盖白名单字段名**（15 个）；
   `contexts/*.json` 里标 `secret` 的变量**明文落盘**；**`viewer` 能读到已部署管线的完整 JSON**。
   ⇒ **绝不把凭据写进管线文件**（本仓既有纪律：机密一律 `${ENV:...}`，不用「已保存连接」——其值会随 deploy 传出去）。
