# 部署安全化：让「代码变更」不再重启正在跑作业的执行器

> 状态：**方案 B 已被实测证伪（2026-11-20 13:40），改推 A**。本文保留证伪记录，别再按 B 实施。
> 前置事实见 #2567 / #2569 / #2572（排空围栏已上线并实测）、#2574（B 的证伪）。

## 1. 问题（都是同一条链路）

| 证据 | 数值 |
|---|---|
| 2026-11-20 被部署砍掉的作业 | 3 条 `data.dbt_hourly`（01:05 / 03:05 / 05:05，全 `dur=0s`） |
| 单元拆分前 3 天 | 40 次部署 / 13 次 dbt 作业被收成 timeout |
| 单次 hourly 时长 | ~17 分钟；tables ~39 分钟；审计 40–90 分钟 |
| 容器被停时的宽限期 | **10 秒**（openship 未把 `stop_grace_period` 传给 Docker，`HostConfig.StopTimeout=None`） |

链路：**改 `dbt/` 或 `scripts/` → CI 触发数据单元部署 → scheduler 镜像重建 → 容器重建 → 在跑的子进程被 SIGKILL**。

今天已上的「排空围栏」（#2569）把这条链路的伤害面压到「部署窗口内不新起作业」，但**没有改变「容器必须重启」这件事**：
围栏只是让重启变得更安全，没有让重启变得不必要。

## 2. 目标 / 非目标

**目标**：让「改 dbt 模型 / 改脚本 / 改契约」这类**高频变更**不再需要重建并重启执行器容器。
**非目标**：不追求「零重启」——改调度器自身代码（`apps/server/src/scheduler/`）时重启是应该的。

## 3. 方案

### 方案 A（大）：派发 / 执行进程拆分

```
scheduler（派发器）  claim → 建台账 → 心跳 → 健康         ← 随时可重启，容器里没有作业
executor（执行器）   接活 → spawn 子进程 → finishRun       ← 只在「执行器运行时」变更时重建
```

- 交接可选：DB 队列（`job_run` 增加「已派发」态）或本地 HTTP。
- 收益：**任何**代码变更都不影响在跑作业；`dbt/`、`scripts/`、`registry` 全部免疫。
- 成本：迁移 + 新服务 + claim/finish 语义改造 + 故障模型（执行器重启 ⇒ 子进程随之消失，仍需 reap）。**约 2–3 天**，需要一份完整 spec。

### 方案 B（小）：代码挂载 + 部署子集 —— ❌ **前提被证伪，不可行**

两个已具备的事实让这件事比看起来简单：

1. `dbt/`、`scripts/`、`contracts/` 都是**运行时读取**的（`pnpm exec tsx scripts/x.mjs`、`dbt build -s ...` 在 spawn 时才读文件），
   所以把它们从「镜像内容」改成「挂载内容」后，**文件更新即生效，不需要重启进程**。
2. ~~openship 的数据项目在宿主上有固定 checkout~~ —— **这条是错的，见下「证伪」**。
   `data-compose.yml` 的 `dbt` 服务确实挂了 `/opt/.../dbt`，但那个目录**从来没人更新**（11-04 的旧快照）。

做法：

```yaml
# deploy/data-compose.yml · scheduler
volumes:
  - dbt-artifacts:/app/dbt-target
  - /opt/platform-core-data/platform-core/dbt:/app/dbt:ro
  - /opt/platform-core-data/platform-core/scripts:/app/scripts:ro
  - /opt/platform-core-data/platform-core/contracts:/app/contracts:ro
```

CI 侧：当本次变更**只**触及 `dbt/ | scripts/ | contracts/` 时，数据单元部署仍然跑
（要更新宿主 checkout），但 `serviceIds` **不含 scheduler**（例：只重建 `artifacts` 这种无状态服务）。

- 收益：改模型/脚本 → **执行器容器不动**、作业零影响；部署耗时也从「重建镜像 ~6–10 分钟」变成「同步代码 + 重建无状态服务」。
- 成本：约 **0.5–1 天**（compose + CI 判定 + 一次实测）。
- **证伪（2026-11-20 13:40，实施到最后一步时验证）**：方案 B 的隐含前提是「宿主 checkout 随部署更新」。
  实测**不成立**：
  - `/opt/platform-core-data/platform-core` **不是 git 仓**（无 `.git`），内容停在
    `scripts/lemeng/materialize.sh` 2026-11-04 / `deploy/data-compose.yml` 2026-11-06；
  - 全机 `find /opt /srv -name .git -newermt 2026-11-19` **零命中**；
  - 部署日志显示构建上下文是「拉 tarball 到 `/tmp/openship-build-<id>-<svc>`」，**不落到固定宿主路径**。

  ⇒ 按 B 挂载那个目录 = 让执行器跑三周前的代码（连 11-20 新加的 backfill 档都没有）。
  已开的 PR #2575 因此**关闭未合并**。
- （以下为原提案记录，已作废）风险与未验证点：
  - openship 是否允许「部署但不重建任何业务服务」——用重建 `artifacts` 绕开，无需它支持空集；
  - 宿主路径耦合（换机时必须同步改）；这正是 `dbt` 服务今天已经在承担的耦合，不是新增；
  - 镜像里仍保留副本（挂载只覆盖），所以挂载失效时会**静默回落到镜像旧代码** —— 必须加一条启动自检。
    **实现采用「设备号」判据**（比原提案的 `.deployed_sha` 比对更便宜也更硬）：bind mount 的
    `st_dev` 与容器 `/app` 必然不同；`scripts/ | dbt/ | contracts/` 任一与 `/app` 同 `st_dev`
    就说明没挂上，启动即打 `codeMountWarning`（点名目录 + 影响），不静默。

### 方案 B3（备选）：执行器自拉代码

让 scheduler 自己从仓库拉一份代码到**容器内可写卷**（`git clone --depth 1`，启动时 + 定时刷新），
脚本与 dbt 都从那份跑。CI 对纯代码变更**不再触发数据单元部署**。

- 收益：不依赖宿主路径、不依赖部署同步代码；改代码后**下一次 job 直接生效**。
- 成本：容器镜像要装 git；仓库是私有的 ⇒ 需要一份只读克隆凭据进容器 env（**新增密钥面**）；
  还要定义「拉取失败时用上一版」的回退（保留上一份 checkout，失败不切换）。
- 风险：执行器里多一条出网依赖；凭据管理要按公司规矩（写密钥要用户点名）。

### 方案 C（现状）：只靠排空围栏

- 成本：已完成。
- 局限：部署仍会重建容器；围栏只保证「没有作业在跑时才重建」。

## 4. 对比

| | **A 进程拆分（推荐）** | B 挂载 + 子集（❌ 证伪） | B3 执行器自拉 | C 仅围栏（现状） |
|---|---|---|---|---|
| 改 `dbt/`/`scripts/` 是否影响作业 | **不影响** | 不可行 | 不影响 | 不影响（但短暂停机 + 依赖围栏） |
| 改 `registry` 是否影响作业 | 不影响 | — | 影响（不重启不生效） | 影响 |
| 部署耗时 | 不变 | — | **显著下降**（纯代码变更不部署） | 不变 |
| 工作量 | **2–3 天 + spec** | — | 1–1.5 天（含凭据） | 0（已完成） |
| 新增故障面 | 交接语义、双进程健康 | — | 出网依赖、克隆凭据、回退策略 | 无 |

## 5. 推荐路径

1. **做 A（派发/执行进程拆分）**：它是唯一不依赖「代码怎么送达」的方案——B 依赖宿主 checkout，
   B3 依赖容器出网与克隆凭据，两者都把风险换了个位置；A 直接消除「代码变更 ⇒ 执行器重启」这条边。
2. 在 A 落地前，**围栏（已上线）就是现状的正确答案**：它把「部署砍作业」压到「只有绕过协议的部署才会」。
   今天三次事故里，围栏覆盖后只剩「手工部署不排空」这一条，已由 `drain.sh` 补上。
3. B3 只在 A 的成本不可接受时才考虑；且必须先解决凭据（写密钥要用户点名）。

## 6. 验收判据（A）

1. **派发器重建不影响在跑作业**：故意在一条 20 分钟作业运行中重建 `scheduler`（派发器）⇒ 该作业终态 `ok`，
   未被收成 timeout（对比今天的三次 `dur=0s`）。
2. **执行器重建的触发面收窄**：统计「因代码变更导致执行器重建」的次数；A 之后应只剩「执行器运行时
   （镜像/dbt 版本/依赖）变更」这一类。
3. **台账语义不变**：`job_run` 的 claim → running → 终态三段仍由同一处收口，健康面判据不放宽。
