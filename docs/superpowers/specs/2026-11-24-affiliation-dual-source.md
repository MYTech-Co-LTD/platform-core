# 归属双源：目录同步 + 自助声明（决策记录）

> 状态：✅ **已定（2026-11-24 人裁：同意双源口径）**；P1 待落，P2/P3 见 §7。
> 性质：归属层 ADR。它**不推翻**《Casdoor 职责边界》（身份绑定归平台）、《组织架构一等公民》（目录归平台），
> 而是在两者之间补一条此前没有的规则：**组织架构覆盖不到的人，其门店归属从哪来**。
> 不变量拟挂 `docs/architecture.md` §4.2「归属双源」。

## 1 背景

售后模块的员工注册是**访客自助**路径：员工在公众号里填姓名/手机/门店 → 管理端审批 → 获得提售后单的资格。

平台同时有一套**组织架构**（`platform.org_node` / `org_membership`，由企微通讯录同步而来），门店在其中已经是节点（「品品甜文山麻栗坡1店」等）。

两条线都在回答「谁属于哪家店」。问题由此而来：

1. 售后能不能直接读组织架构判归属？
2. 员工没加入企微、却在公众号注册了，怎么处理？
3. 两套归属打架时以谁为准？

## 2 实测事实（2026-11-24，platform-core-shanhai 生产）

| 指标 | 实测 |
|---|---|
| `org_node` 总节点 | 282 |
| 其中门店类节点（`name like '%店%'`） | **226** |
| `org_membership` 行数 / 去重人数 | 539 / 513 |
| 挂在门店节点下的去重人数 | 385 |
| 平台门店维表 `data.dim_branch`（两账套） | **365** |
| **目录门店覆盖率** | **226 / 365 ≈ 62%** |
| `platform.identity_link` | 1 行（试运行） |
| `aftersales.employee` / `employee_store` | 0 行（本期才接入） |

**结论**：近四成门店不在目录里。所以「以目录为唯一事实源」在当前数据下是空话——自助声明不是例外路径，是主路径之一。

### 2.1 硬约束（决定方案形状）

`apps/server/src/org-sync.ts:268`：

```sql
delete from platform.org_membership where tenant_id = $1
```

membership 是**纯投影，整组重写**（源码注释：「≈520 行，量级无负担，天然幂等且清除悬挂行」）。

⇒ **任何人工写入 `org_membership` 的归属行，下一次企微同步必被抹掉。**
⇒ 目录之外的归属**不能**放进组织架构；它必须活在业务/平台侧的独立载体里。

## 3 决策：**双源归属**，不假装单一事实

采用 **authoritative source + fallback source + reconciliation**（身份治理里的标准模型）：

| 归属来源 | 权威性 | 载体 | 覆盖（现状） |
|---|---|---|---|
| `directory` | 有则**优先** | `platform.org_membership`（同步器独占写） | 226/365 店 |
| `self_declared` | 目录无此人时**生效** | 业务资格行（售后模块内） | 补齐剩余 |

**解析规则（唯一入口）**：

1. 先查目录：该主体是否在目标门店节点下有 membership
2. 目录命中 → 用目录（`source='directory'`），自助声明不参与
3. 目录未命中 → 用自助声明（`source='self_declared'`），资格行必须带 `approval_id` 留痕
4. 两边都有但门店不一致 → **不自动选边**，进裁决队列，管理端可见

解析只能经由一个函数完成（拟 `resolveAffiliation(org, subject, storeExtId)`），**禁止各端点自行拼装**——否则「先查目录」的规则会在某个角落里被绕过。

## 4 四种情形与确定行为

| 情形 | 行为 |
|---|---|
| 不在目录 + 公众号注册 | ✅ 允许。资格行 `source='self_declared'`；不进 `org_membership`；正常提售后单 |
| 在目录，门店一致 | 资格行 `source='directory'`；`reconciled_at` 记录收敛时刻 |
| 在目录，门店不一致 | 不自动改；生成差异项进裁决队列（调店与注册填错都可能是真的） |
| 在目录但已离职（status 禁用/退出企业） | `identity_link` 失效 + 资格行 `revoked`，不再能提单 |

补充语义：

- **同一人两个身份**（公众号 openid + 企微 userid）：`identity_link` 天然支持多 provider 绑定同一 `casdoor_name`（唯一约束在 `provider, org, external_id`）。合并 = 两条 link 指同一人，**复用既有能力，不新造机制**。
- **权限边界不受归属影响**：`self_declared` 只决定「能提哪个店的单」；管理端动作仍由 Casdoor 权限码（`aftersales:manage`）控制。
- **部门接收人展开自动正确**：`notify` 的 `kind: dept` 展开读 `org_membership`，不在目录的人自然不展开——这是兜底正确，不是缺陷。
- **防重复效力不降**：审批闸门（部分唯一索引 `APPROVAL_PENDING`）不变。

## 5 为什么不上提到平台层（现在）

「目录 + 自助」的洞是任何「同步型目录 + 自助注册」系统共有的，长期上提为 `platform.org_affiliation_override` 是对的。

**但现在不做**——除售后外无第二个消费者。按数据宪法「不预建 seam」，等出现第二消费者再上提；届时售后侧的资格行退化为该表的租户视图。

## 6 与既有裁决的关系

| 既有裁决 | 本 ADR 的关系 |
|---|---|
| Casdoor 边界（#2727）：身份绑定归平台、不做 broker | 沿用，无冲突 |
| 组织架构一等公民（D-O1/O2/O5）：目录自有存储、自建同步器 | 沿用；本 ADR 只规定「目录覆盖不到时」的补充 |
| 数据宪法（#2711）：所有权三分法 | 一致——目录归平台，门店资格是模块原生 |
| 售后账户统一（Phase 1）：人归 Casdoor、微信号归 identity_link | 沿用，无冲突 |

## 7 落地清单

### P1（现在就该做；`aftersales.employee` 生产 0 行 = 迁移成本最低点）

1. 资格行加 `source`（`directory` / `self_declared`）+ `reconciled_at`
2. `resolveAffiliation()` 单入口：目录优先 → fallback 自助声明
3. 管理端员工列表加筛选：**未进组织架构**
4. **审批页显示「该手机号在企微通讯录：有/无」**——把「认人」从盲批变成有据可依（价值最高的一步）

### P2（有数据再谈）

5. 对账 job：目录 vs 自助声明差异报表（门店不一致、已离职仍在提单）
6. 契约钉死 `source` 语义，防某处私自写死 `directory`

### P3（条件触发，不是排期）

7. 目录覆盖达到门店全量后再收紧为「以目录为准」

## 8 待确认（阻塞 P3 的判断，不阻塞 P1/P2）

**226 家不在企微门店节点的门店，是「加盟店/已关店」（永远不该进目录），还是「只是没同步」（将来会补）？**

- 前者 ⇒ P3 永远不会发生，双源是**永久形态**，应把它当稳态设计（含长期对账成本）
- 后者 ⇒ P3 有未来，双源是**过渡形态**，应控制自助声明的功能膨胀，别在上面长出第二套人事系统

在答复之前，P1/P2 按「双源可能永久」设计（更保守、两种情况下都不返工）。

## 9 已知边界

- 手机号是自助声明与目录的唯一连接键（`identity_link.phone`）；员工换号会导致对账失配——需在审批页提示「换号请重新提交」。
- 目录同步器写入的 `external_id`（企微 userid）与 `identity_link.external_id`（公众号 openid）都是「渠道原生地址」但来源不同：**禁止双写**，需要时由解析函数按 provider 取。
- 本 ADR 不覆盖「员工离职后售后单归属」的数据保留问题（见模块 spec 的边界节）。
