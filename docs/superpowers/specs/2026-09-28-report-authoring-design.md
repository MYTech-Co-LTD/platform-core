# 报表制作域设计：agent 与人在同一张报表上协作

> 日期：2026-09-28 · 状态：**设计稿（待评审后进实施计划）**

> `2026-09-21-data-query-channels-design.md`（问数三通道，本域是它的**报表侧**对偶）
> 追踪：issue **#311**（不变量与待办）、**#297 / #298**（接线与权限供给）、**#299**（部署通路）
> **论证依据**：本机**隔离实验室**（零生产）与生产**同镜像**的实测，逐条读数写在本稿「证据」列。

## 0 一句话

**报表的「口径」与「数据门」唯一地落在平台；Metabase 退为「标准图 + 协作编辑面」；
渲染可以有两条路（Metabase 标准图 / 平台自绘），但管理面、口径、租户隔离**只有一套**。**

⚠️ 一处**必须说破的定义**：本稿里的「平台语义（L1）」**不是跨源通用语义**，是**逐源的标准口径**
（依据与实测见 §3⑧）。它的价值在**权威与可追溯**，不在跨源复用；**跨源通用是待决事项**（§7 待办 6/7）。

---

## 1 为什么需要这份设计（问题陈述）

现状：观看面（清单 + 嵌入）已实现；**制作面与管理面没有入口**；而「让 agent 参与造报表」这件事，
一旦做错会同时打破本仓两条既有纪律——**口径只定义一次**、**权限必须落平台层**。

三条实测把它们逼到台面上：

| # | 事实 | 出处 |
|---|---|---|
| 1 | **Metabase 的仪表盘列表没有租户维度**：以管理员身份列出，返回的是**全局列表**（样例库与所有租户的报表并排返回） | 实验室实测 |
| 2 | **Metabase OSS 的 59 个企业版开关一个都没开**：自定义可视化 / 行级沙箱 / 任意 SSO / AI 全部不可用；`/api/ee/*` 路由不存在 | 实验室实测（同版本镜像） |
| 3 | **它没有任何原生实时机制**（前端 bundle 里 websocket / SSE / 轮询命中均为 0），且**「更新时间」字段不反映卡片层改动** | 实验室实测 |

⇒ 结论：**「让 Metabase 自己当管理面 + 自己管租户」这条路在 OSS 上不成立**（不是取舍问题，是被堵死）。
本设计据此把三条面切开。

## 2 三个面（本设计的骨架）

| 面 | 归谁 | 为什么 |
|---|---|---|
| **制作** | **可以是多个**：Metabase 编辑器（标准图，人 + agent 协作）／平台的表单（结构化声明） | 两种产物最终都落进**同一张登记表** |
| **管理** | **只有平台**（console）。页门 / 发布 / 回收 / 审计 | Metabase 的列表是**引擎内部状态**，不是管理面（§1 事实 1） |
| **渲染** | **两条路**：Metabase 标准图（嵌入）／平台自绘 | 表现力上限不该由单一产品的图表个数决定（§5） |

**统一的事实源是平台的报表登记表**（现有 `data.reports`，本设计**新增一列 `renderer`**）：

```
data.reports
  id | org | title | metabase_id | renderer            | required_scope | …
                                ↑
                       'metabase' 或 'platform'
```

⇒ `renderer` **只影响「点开时谁渲染」**，不影响任何管理动作 ⇒ **自绘不产生第二个管理面**（实验室已验：
两种渲染器在同一张表、同一组动作里）。

## 3 不变量（本设计的硬核，逐条带证据）

### ① 口径只定义一次：报表 SQL 由平台按**已声明口径**编译

- agent 的工具面**不提供任何收裸 SQL 的工具**；它只能「选指标 + 选维度」。
- 落库图表里的语句与平台编译的**逐字一致**（独立回读比对，不采信 agent 自述）。
- 词表外指标 ⇒ `METRIC_NOT_DECLARED` 拒绝；维度不在该指标 grain 内 ⇒ `DIMENSION_NOT_IN_GRAIN` 拒绝并回报允许集。
- 实测：被问「要一个词表里没有的指标」时，agent **拒绝硬凑**，并指出「比率型不能靠分组拼出来、要在指标层先声明」。

### ② 租户绑定要**一次做全三件**（本域最要紧的一条）

> **光把嵌入参数里的租户值设成 locked 是不够的。**

还必须：**(a) 报表页面声明一个名为 `tenant` 的参数**；**(b) 把用到了该模板参数的图表映射到它**。
少 (b) 的实测症状：取嵌入图数据报「找不到匹配的参数」；**更坏的形态是页面照常显示未过滤的数据**。

⚠️ **而只回读 `embedding_params` 的对账会把它判成 OK** ⇒ 对账判据必须加厚（见 §7 待办 2）。

**数据门正反面实测**（同一张报表、同一张图）：同一份签名令牌只改令牌里写死的租户值 ⇒
一个租户出 4 行、另一个出 2 行，与种子数据逐值吻合；令牌里不带该参数 ⇒ 拒绝；签名被篡改 ⇒ 拒绝。

**发布时只映射真正用到该模板参数的图表**（实测：不带该参数的图表若被乱映射会报错）。

### ③ 写不静默覆盖：**内容指纹 + 每对象一把锁**

**问题先被复现**（两条，缺一不可）：

| 现象 | 实测 |
|---|---|
| agent 拿自己记忆里的图表数组写回 | 请求成功、**无任何报错**，人的两张图**被静默抹掉**（3 张变 1 张） |
| 6 个并发写拿**同一个**基准版本 | **全部返回成功**，实际只落 **2 条** ⇒ 静默丢失 |

⚠️ **一个把问题藏起来的坑**：若服务是**单线程**的，它自己会把请求串起来执行，**竞态根本复现不出来**。
要暴露它必须换成并发服务器。**「测不出来」不等于「不存在」。**

**修法与实测**：

- **内容指纹**（覆盖图表布局 + 每张图 SQL 的摘要 + 页面参数 + 锁参状态）——
  不能用「更新时间」字段（实测它**不反映卡片层改动**）。
  ⚠️ 本稿把「指纹」与「版本号」当**同义词**用：前者是对对象内容取摘要（Metabase 那条路的形态），
  后者是登记表上的单调计数（自绘那条路的形态）。**两者都必须由平台算、且必须覆盖内容本身**
  ——选哪种是实现细节，见 §7 待拍 1。
- **乐观比对 + 每对象一把锁**。加锁后：1 个成功 + 5 个**明确被拒**，账实相符；
  陈旧写拿到的是一句可解释的拒绝 + 当前版本号（让它重读再试），而不是被覆盖。


> ✅ **已落地（计划 4，2026-09-29）**：内容侧**现算指纹**（`readDashboardContent`）、登记侧 `version` 计数列（迁移 `005`）、
> **每对象一把锁**（进程内，`withObjectLock`）、陈旧写/缺版本的 **409**（带 `currentVersion`/`currentFingerprint`）。
> 版本比对**必填（fail-closed）**：更新既有对象不带版本一律拒。调用方义务与边界见 `modules/data/README.md`「写保护」小节。

### ④ agent 不持任何 Metabase 凭据

- 第一版实现让 agent 直连，结果它**同时持有内容接口密钥与嵌入签名密钥**——后者泄露 = **能签任意租户的嵌入凭证**。
- 改成**全部经平台**后，实测在**刻意不给它任何凭据**的环境下全链路照跑。
- 推论：**凭据面收口**是本域的硬约束，不是优化项。

### ⑤ 管理面唯一，且覆盖两种渲染器

同租户内分级 + 跨租户隔离，**浏览器实渲**验证：

| 身份 | 渲染出的内容 |
|---|---|
| 租户管理员 | 3 行（含一张**平台自绘**的、一张未发布的）；页门可改、发布/回收可点 |
| 普通员工 | **1 行**——页门未放行的那张**在列表里就不存在**；操作列**只读** |
| 另一租户管理员 | 1 行（只有它自己的）——跨租户隔离 |

外加：越权改页门 `403`、跨租户改 `404`（不给存在性探针）、陈旧版本写 `409`。

### ⑥ 语义层驱动的**自绘**：agent 出**声明式规格**，不出代码

- 在租户 console 里执行 agent 生成的**代码** = 跨站脚本 / 偷会话 / 跨租户面，且**不可审计**。
  声明式规格则可以被**校验**（schema + 语义层白名单）、也能被人接手改。
- **严格字段白名单不是风格，是机检落点**：实测过一版没有它的校验——规格里多塞一个可执行字段
  **被照单接受**。当时渲染器恰好不读它所以没出事，但「未知键静默放行」意味着
  **下游任何一次顺手多读一个键就变成注入面**。
- 实测：agent 写三 panel 规格 ⇒ 成功；改图型为白名单外 ⇒ 拒绝并列出白名单；
  换词表外指标 ⇒ 拒绝；**两次越界后版本号不变**（没有部分写入）。

### ⑦ 编辑页可以搬进平台后台（「甲」形态）——三条硬约束

| # | 约束 | 依据 |
|---|---|---|
| 1 | **必须专用入口，不能挂子路径** | 它的前端用**绝对路径**；挂子路径整站资源 404 |
| 2 | **认证必须走服务端会话 Cookie** | 页面自己发的异步请求**不带**地址栏里的令牌 ⇒ 只认查询串时页面壳能开、数据全被判未认证 |
| 3 | **租户隔离由反代补**：只放行本租户**已登记**的对象，并**封掉「列出全站」的搜索面**；非接口的页面壳也要判 | Metabase 侧只有一个身份，它自己不区分租户（§1 事实 1） |

实测：本租户 200（页面与数据都出得来、参数可改）；别租户 403；无凭证 401；搜索面 403；样例对象 403。

**顺带一条设计事实**：编辑态下租户参数是**普通参数（可改、可为空）**，**锁定只在「嵌入观看」时生效**
——这正是「人也能手动调」需要的行为。

### ⑧ 语义必须带**源维度**：裁剪 + 写入闸，**两道缺一不可**

**先说清楚 L1 的真实身份**：它**不是跨源通用语义**，是**逐源的标准口径**。
依据：声明的 `expression` 字段自述为「口径的**实现表达式**（指向哪个模型的哪些列）」，
值形如 `sum(<某源模型>.<列>)` ⇒ **概念与实现压在同一层**，实现是逐源的。

**"同名业务概念在第二个源上"的结构性障碍（实测）**：
照生产结构（主键 `(org, id)`）复刻词表，让第二个源声明同一个业务概念 ⇒ **存储层直接拒绝**
（`duplicate key … (platform, retail:net_sales)`）。改名能进，但结果是**两条标题一模一样、口径不同**，
而**没有任何字段**能表达"这是哪个源"。

**实测后果**：面对两条同名指标，agent **只能停下来问人**
（它的行为是对的——拒绝替人猜；但这说明**设计缺了一个维度**）。

**修法（本轮已验证，两道都要）**：

| 道 | 作用 | 实测 |
|---|---|---|
| **词表裁剪** | 只回**该租户已接入源**的指标 ⇒ 对单源租户**歧义直接消失** | 只接一个源的租户看到 1 条；接两个源的看到 2 条**但能按 source 区分** |
| **写入闸** | 指标存在、但属于**本租户未接入的源** ⇒ **拒绝**（回报 `its_source` / `your_sources`） | `METRIC_SOURCE_NOT_ADOPTED`（403） |

⚠️ **只装一道都不够**：只裁剪的话，agent 一旦记住 id 就能绕过去（写成硬编码）；
只装闸的话，单源租户仍要面对两条同名（体验退化成人人必答的裁决题）。

⚠️ **同批还修了一个 fail-open**：**「无身份」与「没接入任何源」原本长得一样**（都回空列表）
⇒ agent 把"没认证"误读成"平台词表坏了"。**无身份必须是 401**，不能是空列表。

**⇒ 前提（本节的落地依赖它，见 §7 待办 6）**：「**某租户接了哪些源**」这条事实**今天无处可取**——
契约在仓里（per 源，且是资产不是运行时数据）、`data-tenants` 只管 schema/凭据、
平台侧没有任何登记、采集侧只在**命名**里隐含（调度按账套、管线按源，两者正交）。
**这条不定，"裁剪"就没有判据面。**

## 4 语义的写入面：agent 能动哪一层、由谁批

（§3⑧ 说清了语义要带**源维度**；本节说**写入路径**——这是"agent 管理语义"这句话的准确展开。）

### 4.1 三个落点，不是一个

| agent 想干的事 | 落点 | 谁批 |
|---|---|---|
| 在**已有 L1** 上裁剪 / 别名 / 过滤 | **L2**（运行时行：`data.metrics` 里 `source='l2'`，**永不进 git**） | **租户管理员一键** |
| 提出**新口径本体**（新聚合 / 新列 / 新基底） | **L1 草案 → PR**（**必须含对账 test**） | **我方评审**（代提；过脱敏与影响面） |
| 一次性 / 探索性查询（**不成声明**） | 图上标「**未声明口径**」 | 不用批，但**必须可见 + 可晋升** |

**L2 是"受限的写"，不是随便写**：只能选基底 + 裁剪 / 别名 / 过滤；
带 `selectSql` / `subjectColumn` / `groupBy` / `params` / `source` ⇒ **400 拒绝**（`.strict()`，**不是忽略**——
静默忽略会让调用方以为自己写的 SQL 生效了）。且 **L1 行对 API 只读**：`DELETE` 打到 L1 的 id ⇒ **409 `READONLY_L1`**。

### 4.2 判据是机械的，且由平台判

> **它能不能只用「已有 L1 指标的表达式」表达出来？** 能 ⇒ L2；不能 ⇒ L1 草案。

**这条不能交给 agent 自报**：它判不了「对**所有**租户都成立」，也判不了「这是不是平台口径本身的缺陷」。

### 4.3 三条防「词表变垃圾场」的门（缺一不可）

1. **提议 ≠ 直接新建**：agent 的工具面**没有"直接新建"**，只有「**提议**」，而提议会**先让它看到候选**
   （强制搜词表查重）。⚠️ 这条**不能只写在提示词里**——它得是**工具面的结构**。
2. **agent 提的只能落 `experimental`**；升 `certified` **必须人评**（`tier` 是标记不是强制——本仓既有口径：
   「不靠它挡谁，靠它让人一眼看见成熟度」）。
3. **自由发挥必须可见**：每次未声明口径的产出落一条记录（谁 / 哪张报表 / 什么查询 / 涉及哪些表），
   管理面显示「这张报表里有 N 张图是**未声明口径**」⇒ 风险从「结构性」降为「可治理」。

### 4.4 确认时给人看的是**口径**，不是 SQL

> 「净销售额（本租户口径）＝ `retail:net_sales` 的合计，按业务日切，**排除某账套**」
> 　[固化为本租户指标]　[不要]

人确认的应该是**业务含义**。这与 L2 的表达力边界一致（**L2 本来就写不了 SQL**）。

### 4.5 一条反直觉的推论：把「上升」定位成**报缺陷**，不是**报需求**

**"租户能一键把自己的东西变成平台口径"这件事本身，就是词表被稀释的入口。**
⇒ 「上升为 L1」应当**默认收起**：

- **报需求**（我要按门店看、我要排除某账套）⇒ **L2 就够**，一键，**永不进 git**
- **报缺陷**（你们的净销售额没剔作废，我们对不上账）⇒ 走上升通道 → PR → 人评

⇒ PR 通道因此是**稀有的、且由证据驱动**（有人对不上账），而不是由「agent 觉得这样更好」驱动。
这正好合本仓那句：**无案例不立标准**——**"有租户对不上账"就是那个案例**。

## 5 渲染两条路的边界（为什么需要自绘）

**Metabase 的图表是封闭集合**：实测 `custom-viz` / `custom-viz-available` 均为 **false** ⇒
**图型集合封顶、加不了**（从前端 bundle 里能数出二十来种图型名，但「数出几个」不是判据，
**「能不能加」才是**）。而它**之下**的配置面其实很深（多序列 / 每列格式 / 条件格式 / 目标线 /
趋势线 / 轴刻度 / 点击行为，全部可程序化设置）。

⇒ 因此：

| 走哪条 | 什么时候 |
|---|---|
| **Metabase 标准图** | 常规报表面（趋势/对比/明细）。**零成本、可协作编辑、可订阅** |
| **平台自绘** | 标准图做不出来的（大屏布局、特殊图形、强联动、按租户定制的版式） |

**两条路共用一个口径与一个数据门**：平台自绘**直连物化层、按调用者身份注入主体值**，
不依赖 Metabase 的锁定参数；Metabase 那条路靠锁定嵌入参数。**判据同源（同一套语义声明）**。

**代价明写**：自绘的**渲染器质量归我们**。实验室这一轮就踩了两个——分组数据按「过滤同组」塞进系列
会把多出来的点连成一条线（应改成透视数据集）；图表画布会**溢出到隔壁格子**（要收 `overflow`）。
这两条都不是数据问题，是渲染层的活。

### 建议方案：「租户 ↔ 已接入源」（待办 6 的展开，**待拍**）

先说一条**实测到的现成资产**：**「源」其实已经是契约里的一个显式字段**，叫 `domain`
（例：某契约里 `domain: lemeng`）——显式、有元 schema 校验、走 PR、人可读。

而采集侧**没有**承载它的地方（实测）：管线 JSON 的顶层键只有 `name / nodes / edges / version / id`
（**源只在文件名的前缀里**）；调度条目**连 env 都没有**。
⚠️ **一条硬约束**：管线 JSON 是**桌面真引擎产出的、仓内不手编**（本仓纪律）
⇒ **别想着给管线加字段**，要显式化只能落在**我们能控制的地方**。

**三件，各归各位**：

| # | 管什么 | 落在哪 | 为什么 |
|---|---|---|---|
| ① | **源是什么**（有哪些源、什么形态） | **契约的 `domain`**（**已存在，不用新建**） | 显式 + schema 校验 + 走 PR；平台登记里引用的源**必须在该租户的契约集合里存在** ⇒ 一条校验就把两侧接上 |
| ② | **谁接了哪个源**（绑定） | **平台侧登记**（新表），接入流程写入 | 平台做裁决**必须自足**（词表裁剪在**请求路径**上，不能每次去读数据面）；与既有 `tenant_module`（平台启用集）**同构** |
| ③ | **防漂对账** | **console 的 env 声明**（`一账套一 console`，加一个"已接入源"的键） | env 是**注入面**——**不动引擎产出物**、不破「仓内不手编」；且 console 的 env 里已有一堆同类键 |

⚠️ ② 本质是**声明不是事实** ⇒ **必须配 ③**，否则会漂（有人接了源没登记）。
③ 的形态照抄既有那套：**平台登记 ↔ console env 声明，双向差集，漂移响亮**
（`scripts/reconcile-data-tenants.mjs` 就是这个形态：平台启用集 ↔ 数据面已建，撞名必报、exit 1）。

**为什么不是另外三条**：

| 方案 | 为什么不 |
|---|---|
| **纯从采集侧派生为主** | 平台裁决不自足（每请求读数据面）；且采集侧「源」是**隐式命名** ⇒ 派生等价于解析文件名，**脆** |
| **从湖路径前缀派生** | 路径约定会变、且隐式（§3⑧ 已明确排除） |
| **给管线加字段** | 引擎产出、仓内不手编 ⇒ **此路不通** |

**顺带一个好处**：源有了正式身份之后，**「跨源通用语义」（拆概念/绑定两层）才有地方挂**
——那件事本来就等第二个源才做，而**源有了身份，「第二个源」才有可判据的定义**。

### **未验**（诚实边界，别当已验）

1. **登录跳转**：Casdoor 登录 → 平台会话 → 报表管理面这一跳**没跑过**。
   本仓对三通道授权核心有端到端回归锁，但**与报表管理面的组合**未验。
2. **排序在目标物化层上的行为**：物化层是 pg_duckdb / DuckDB，本轮验的是普通 Postgres。
3. **真实平台的锁实现**未定（进程内锁 / 数据库行锁 / 单写队列）。
4. **写保护只在本机模型上验**；真实并发压力下的表现未测。

## 8 落地顺序（建议）

1. **底座**：`renderer` 列 + 发布路径三件套 + 对账判据加厚（**不依赖 agent**，先让人的路径正确）
2. **写保护**：版本守卫 + 锁 + 冲突拒绝的人话文案
3. **管理面**：console 的列表/页门/发布/回收（**统一管理面**）
4. **反代与会话**：编辑页进 console（§3 ⑦ 三约束）
5. **agent 制作通路**：工具面（选指标/选维度；写规格）——**放最后**，因为前四步是它的前提
