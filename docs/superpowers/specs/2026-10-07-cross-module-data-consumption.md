# 跨模块数据消费契约（维表为例）——决策记录

> 状态：✅ **已定（人裁 2026-10-07）**；**未实施**——触发条件见 §7（首个真实消费需求立项时按本决策走）。
> 性质：架构决策记录（ADR）。不变量条目已挂 `docs/architecture.md` §4.2（第二档：仅文档）。
> 提问原话：「我们是模块化的框架，比如售后模块要依赖采集模块采集出来的维表，
> 这种模块间的协作是通过 API 好，还是直接读数据库表好？」

## 1 背景

platform-core 是模块化框架：业务模块（`modules/<id>`）经 manifest 协议接入宿主，
采集/数据链路产出的语义资产（维表、指标）落在数据面 warehouse（pg_duckdb `staging`）。
业务模块（如售后）出现真实需求：要消费采集产出的维表（门店、商品等）。
需要定下**模块间数据协作的形状**——API 还是直连库——否则每个消费方各自发明，散点耦合不可逆。

## 2 决策

**默认走 API（经模块协议），不允许业务模块直连其他模块的生产表/生产库。**
但「API」按消费模式分**两种形状**，二者都是契约、都不碰生产中间态：

| 形状 | 适用 | 载体 | 执法点 |
|---|---|---|---|
| **① 同步查询** | 交互/校验类：下拉、单据校验、少量 lookup（少量行 × 多次） | owner 模块的声明路由（如 `GET /api/modules/data/dims/branches`），分页+过滤 | **读时**：scope 门卫 + 词表裁剪 + 审计，逐调用 |
| **② 发布快照** | 批量/计算类：模块要在自己逻辑里对**全量**维表 join/校验 | owner 发布的**带版本快照**（落 owner schema，如 `data.dim_branch`，带 `bizday`/`version`），消费方经批量端点（ETag/版本）拉取、经宿主投影读发布表，或——**同库部署形态下**——对发布表的**只读 SQL 引用**（B1 只读白名单 `data.dim_*`：from/join 放行、into/update 仍红；发布表只许 owner 写。首例 #476） | **发布时**：裁剪与版本在发布那刻烤进快照 |

两个形状**常常并存**于同一消费方（建单选门店走①；夜间批量对账走②）。

## 3 为什么分两种：四个本质区别

①与②不是同一访问的两种实现，是**两种消费契约**：①卖「此刻的答案」，②卖「某一版的数据集」。

1. **读的时机**：①在请求路径上（用户在等，取不到即阻塞）；②在请求路径外（提前拉好，与业务时刻解耦）。
2. **读的形状**：①少量行×多次；②全量×一次（4 万行分页 = 几百次授权审计，荒谬）。
3. **一致性语义**：①要「当前值」（刚建的门店立刻能选）；②要「**钉住的某一版**」（批跑五分钟必须同一版，
   否则跑到一半维表变了，结果前后矛盾）。每次点查都是 latest，**给不了版本钉住**。
4. **失败语义**：①失败=当场暴露给用户；②「用上一版」**不是错误是常态**——快照天然容旧降级。
   用①做②会把 99% 时间容得下旧数据的场景做成 100% 实时依赖。

反向混用的坏法：用②做①⇒本地副本滞后，用户刚建好的门店选不到（把最终一致强加给需要当前值的场景），
且每个消费方都要自造「副本同步+过期发现」——把 owner 的活复制到每个消费方。
分页拉全量还带来「分页间不一致」：拿到的是穿越多个时刻的缝合怪。

## 4 判定方法（消费方三问）

1. 消费发生在**请求路径上**吗？在 ⇒ ①。
2. 单次要**全量/大块**吗？是 ⇒ ②。
3. 失败时需要**当场给答案**，还是**容得下旧版继续跑**？前者 ①，后者 ②。

## 5 规则（守约与越界的判定）

1. **谁的数据谁出契约**：维表是采集/语义域资产 ⇒ API 与发布表都归 data 侧定义，消费方只消费。
2. **消费方只读「发布物」，不读「生产中间态」**：staging/湖/duckle 工作区一律不对业务模块暴露。
3. **跨库连接只许出现在 owner 内部**（物化 job / 语义编译器）；**任何情况下不给业务模块发
   `DATA_WAREHOUSE_URL`**。
4. **第二个消费方出现时更要走这条路**：一处授权、一处裁剪、一处探活，而不是 N 份直连配置 N 种租户写法。
5. **分析型 join 不进模块代码**：要「报表/统计里跟维表 join」就下沉成 dbt mart 走问数出；
   模块干业务事务，不干分析 join。
6. **微小事实才走宿主投影**（`TENANT_SOURCES` 先例）：投影机制是为单值事实设计的，**成表的维度数据不适用**。

## 6 依据：直连的失效模式（本仓真实案例，非假想）

| 直连破坏的机制 | 失效形态 | 本仓对应案例 |
|---|---|---|
| 架构边界 B1 | 跨 schema 耦合藏进存储层，lint 看不见、manifest 管不着 | B1 存在的全部理由（`docs/architecture.md` §4.1） |
| schema 契约 | 消费方 SQL 焊死在 staging 列形上，采集侧重构 ⇒ 运行时静默炸 | **契约生成器**（#460：列集是会变的，变化必须走生成器） |
| 租户隔离 | 主体绑定只存在于语义编译器；直连方各自重造，错一次 = fail-open 跨租户 | 问数链专门建了编译器 + `query_audit` |
| 事实源分叉 | 「镜像快照 vs 检出」两份无比对 ⇒ 物化出旧口径 | **#300** |
| 部署拓扑 | warehouse 在数据面；模块凭空多一条跨机连接，本地开发/测试被拖累 | **#297** Gate-B 接线 |
| 读取竞态 | 直连读湖/中间态撞写入窗 | **#452** ETag 竞态（读今天产物的咽喉重试） |

## 7 未实施：触发条件与落地清单

**触发**：第一个真实消费需求（售后 × 维表）立项时。届时按消费模式选形状，落实施计划，要点：

- [ ] owner 侧：dims 声明路由（①）或发布清单条目（②，与 dbt 物化 job 同管道，探活盯新鲜度）；
- [ ] manifest 声明 + scope（复用 `data:query` 还是新 scope，届时裁）；
- [ ] ② 的快照表带 `bizday`/`version`，消费方本地缓存**必须标 version**（过期显式可对账，不是隐式耦合）；
- [ ] 不给消费方任何直连 warehouse 的凭据；
- [ ] 门禁化评估（把 §5 升成第一档 lint 规则）**单独决定**——按本仓规矩「无案例不立标准」，
      等第一个真实案例暴露出可机检的违例形态再升。
