## 0. 一句话

余量的阻塞**从来不是「层缺失」**，而是**客户侧输入未就位**；
而「报表面」**不是一个层**——它是「落点未判」的临时堆放。
本文的交付是**落点判定三问**（穷尽，无第四种归宿）+ **余量逐项重判** + **客户输入的按形状选通路**
（既有主路 = git 受控 CSV seed；forms 是另一条，见 §6）。

## 1. 落点判定三问（本 spec 的核心裁决，取代原「三层」表）

任何一条口径，按序问三问，**答案必落在三种归宿之一**：

| # | 问 | 判据 | 归宿 |
|---|---|---|---|
| **1** | **形状**：能否写成「单一关系上的聚合」？ | `from` 一个关系；`GROUP BY <grain>` 由外层拼 | **L1 声明面**（38 条，`dbt/semantics/l1_metrics.yml`） |
| **2** | **预算**：若交给消费方现拼，**行数 ≤ 1000 且轮数 ≤ 6** 吗？ | `MAX_QUERY_ROWS=1000`（`authz.ts:114`）；`MAX_AGENT_TURNS=6`（`agent-loop.ts:30`） | **消费方能力**（平台零工作量） |
| **3** | 否 ⇒ **把窗口/排序/配对在 dbt 里算掉**，输出一张单关系宽表 | 回到问 1 | **mart + L1/L2** |

**问 3 的输出仍回到问 1**（mart 就是「单一关系」）——所以三问闭合。

**关键结论**：
- **「报表面」不存在**。原 spec 把它当成与 L1/L2 并列的第三个层，是**把两个不同归宿混装**：
  一类**下沉**到 mart（窗口/归因/配对），一类**上浮**到消费方（两期对比/月内极值）。
- **L2 只吃问 3 的产物**：同一张 mart 上、同 grain 的**分量列算术组合**（02-05 的四效应就是）。
  同一张 mart 上**两列之比**更简单——那是 **L1 ratio**（`expense:loss_rate` 同形），**不必上 L2**。
- **平台不建表达式引擎 / 窗口 DSL / 看板前端**（原判不变）——因为窗口由 mart 吸收，
  而 mart 是 dbt 模型，不是运行时设施。

## 2. 为什么余量进不了 L1（问 1 为何失败）

`from` 只能一个关系 ⇒ **任何跨域组合（费用×出库、库存×销量、入库×出库、商品×两期）写不出声明**，
必须先落一张 mart（这正是 #744 建 `fct_contribution` / `fct_purchase_concentration` 的原因）。
**跨粒度（战区 vs 总仓）、窗口（连续天数、期间极值）、排序（Top-N）、跨期配对**同理——全部先落 mart。

## 4. 消费方的真实包线（判 §1 问 2 的实测依据）

问 2 不是「消费方理论上能不能」，而是**在这条真实通路里能不能**：

| 事实 | 值 | 出处 |
|---|---|---|
| 最大轮数 | **6** | `modules/data/domain/agent-loop.ts:30` |
| 单次返回行帽 | **1000**（超出置 `truncated`） | `modules/data/domain/authz.ts:114` |
| 行数实测 | `net_sales` ≈ **147 行/天**（3120）/ **74 行/天**（64188），grain 含 `branch_num` | 参数面 spec §8.3 |
| **`total` 自动伴随** | `expression` 以 `sum(` 开头 ⇒ 任何查询**自动附合计值**；比率/去重计数 = false | 参数面 spec §8.4 |
| 问数参数白名单 | 仅 `bizday`（`date_range`）/ `system_book` / `domain` | 参数面 spec §2.2 |

**由此得两条判据**（这就是问 2 的可执行形态）：

- **两期对比 = 消费方能力，且平台已支撑**：`total` 自动伴随 ⇒ **2 次调用各得合计，1 次相除**
  ⇒ 增长率/变化率**今天就能答**（不含「可比集合」这一口径输入）。占 6 轮里的 2 轮。
- **窗口/streak/Top-N = 消费方**能力**不足**：门店×月 = 300×30 = 9000 行 ≫ 1000 帽；
  逐日累计还要 N 轮 ≫ 6 ⇒ **必须落 mart**（问 3）。

> 这条实测把「窗口归谁」从**口味问题**变成了**可机检的预算问题**——这是原 spec 缺的一环。

### 5.1 01-08「缺成本金额面」在本源**无数据** ⇒ 声明即恒 0

只读探针（山海数据面 `pg_duckdb` → 湖，2026-10-17）：

| 证据 | 值 |
|---|---|
| `lemeng/transfer_out` 湖全景 | **6561 行**，bizday 2026-10-07 ~ 10-15（9 天） |
| 其中 `subtotal IS NULL` | **0 行** |
| 其中 `subtotal = 0 且 out_money≠0` | 13 行，合计 **2924.00** |
| `staging.fct_transfer_line_quality`（989 粒度）`missing_cost_amount <> 0` | **0 个**（合计 **0.00**） |
| `zero_cost_amount` 合计 / 非零粒度 | 2924.00 / 13（与湖侧逐字吻合 ✓） |
| 契约 `contracts/common/lemeng.transfer_out.json` 的 `subtotal` | `nullable: true`（schema 允许，数据从未出现） |

⇒ 落这条 L1 会得到一个**永远返回 0 的指标**，问数 bot 会自信地回答「缺成本金额 0」——
而真实语义是「**本源从不报 null**」，**不是**「没有未核金额」。
**恒 0 的指标比没有更有害**：它把「无数据」说成「零暴露」。故**不落**。

**由此冒出的口径问题（待客户确认，issue #816，见 §11.7）**：客户 04-06 要求区分「**已知**成本=0」与
「成本 null」，但**本源上这两态不可分**（13 行是 0、0 行 null）。若源把「成本未知」编码成了 0，
则 `zero_cost_amount` 里那 2924 元**就是**「未核金额」，01-08 ① **已被 04-06 覆盖、不该另立**。
⇒ **01-08 的实质面是 ② 未归属金额（挂 X01a）与 ③ 失败率（挂 X09）**，两者皆阻塞。

### 5.2 实际交付：零成本面边界修复（潜伏缺陷，数值零影响；issue #815）

**缺陷**：`fct_transfer_line_quality` 的零成本面用 `coalesce(b.subtotal, 0) = 0` ⇒ **把成本 null 的行并进零成本**，
与 `missing_cost_amount` **重叠**，违反客户总册 04-06「**已知**成本=0」+「成本 null **另列**」、
01-08「零成本金额**另算**」，也违反仓库内**四处**文字（mart 头注 / `schema.yml` 表说明与列说明 /
`l1_metrics.yml` 声明）自述的「两类暴露**不相加**」。**不是口径歧义，是代码没实现它自己写明的意图。**

**修复**：`coalesce(b.subtotal, 0) = 0` → **`b.subtotal = 0`**（mart 金额面 + 行数面；SQL 里 `null = 0` 求值为 NULL ⇒ 天然排除 null）。
对账侧**同款错法**（同构复算 ⇒ 口径错两边同错、恒绿）一并订正，并**新增两条断言**：
缺成本面复算 vs 物化、以及**互斥断言**（`zero_cost_amount + missing_cost_amount` 必须等于基面「无正成本」金额）。

**射程（已知且刻意）**：互斥断言只在源出现 `subtotal is null` 时有区分度——今日全湖 0 行 null ⇒ **空转过绿**；
null 一旦出现即生效。**数值零影响**（`zero_cost_amount` 修前修后同为 2924.00，实测）。

**RED/GREEN 取证**（本地无 duckdb/dbt 二进制，故在数据面 `pg_duckdb` 上用**合成行集**跑表达式）：

| 表达式 | 值 |
|---|---|
| 现写法 `coalesce(subtotal,0)=0` | **150.00** |
| 修正 `subtotal=0` | **50.00** |
| 缺成本面 `subtotal IS NULL` | **100.00** |
| 基面「无正成本」`=0 OR IS NULL` | **150.00** |

⇒ 互斥断言在**现写法上失败**（150+100=250 ≠ 150）＝ RED；修正后成立（50+100=150）＝ GREEN。
真数据复跑：`zc=2924.00 / mc=0.00 / npc=2924.00`，2924+0=2924 ✓ 且 zc 与修前逐字相同。

### 6.2 ② 另一条：契约驱动的表单（`modules/forms`）

- **契约驱动**：draft-07 JSON Schema + uiSchema，服务端 ajv 与渲染端同源；发布门机检
  （方言/编译/条件字段/widget 白名单/两半漂移）；**契约里永不含值，只含引用**（`x-dict`/`x-binding`）。

- 通路：`POST /defs/:assetId/submissions`（一提交一记录）→ `GET /export/submissions`（键集游标）→ duckle `src.rest` → 湖。

  无批量导入 / CSV 通路**；`SUPPORTED_WIDGETS` **不含 `file`**（ADR-0005 §9：附件控件需自研、尚未实现）。

### 6.3 两条通路的分工（判据）

| 判据 | **git 受控 seed** | **forms 表单** |
|---|---|---|
| 更新频率 | 低频 / 慢变（年、季度、一次性） | 高频 / 随时 |
| 批量 | **大批量（整张 CSV）** ✅ | 逐条 ❌（无批量导入、无 `file` widget） |
| 可审 | **进 PR 可审** ✅ | 提交即入库，无 PR 审 |
| 谁动手 | 研发代填（客户给数据 → 我们进 PR） | **客户自助**（console 填，免 PR） |
| 既有落点 | **X01 / X08（空占位已建）** | 无（X02/X04/X07/X03 未建） |

**⇒ 本 spec 不主张「唯一通路」**，主张**按台账形状选通路**，并**优先走既有定案的 seed**
（无案例不立标准：seed 已建就不另起 forms）。逐台账建议：

| 台账 | 建议通路 | 判据 |
|---|---|---|

### 12.1 案例结论：03-05 已出数，「营业日历」不是前置

**已落**：`fct_branch_day_activity`（门店×日骨架）+ L1 `lemeng:retail:consecutive_no_sales_days`（03-05）。

⇒ 「门店是否存在 / 是否营业 / 属哪个战区」**可从自有数据推出**，客户日历（`x01_branch_calendar`）

2. **弱代理的边界写死**：`collection_covered` 只到「账套×日」层，判不了单店断数

### 12.2 落点判定补第四问：**可推导吗？**

§1 的三问（形状 / 预算 / mart）只问「怎么算」，没问「输入从哪来」。补一问，插在问 1 之前：

> **问 0：这个输入能不能从自有数据推导？**
> 能 → **先推**，并把推导的边界（射程、弱代理、盲区）**写成列与口径**；
> 不能 → 才是客户输入。

判据来源：**每日快照 + 事实的 as-of 连接**能回答绝大多数「这个实体那天在不在 / 是不是在营 / 属谁」。
**待改的条目**（按此重判）：
- **01-05 / 07-06 可比门店集合**：零售业标准定义「开业满 N 期且两期均在营」——**开闭店日期可从快照推出**
  ⇒ 与 03-05 同招，**不必等客户日历**。
- **X01b 营业日历**：从「客户输入（阻塞）」降级为「**override**」。

### 12.3 可加性必须**显式登记**，不能从 `sum(` 形状推（**线上已有错数**）

**实证（2026-10-17 生产库）**：`lemeng:inventory:quantity` / `lemeng:inventory:money` 的 `totalable = true`。
它们是**日快照存量（stock）**，跨时间求和无业务含义；而自动合计的 SQL 是
`SELECT sum(value) FROM (<whereAndGroup>) t` ⇒ 问「近 7 天库存合计」会得到「7 天快照相加」。

**裁决**：`totalable` 的来源从「expression 形状」改为**声明的 `additivity`**：

| additivity | 跨实体 | 跨时间 | 合计语义 |
|---|---|---|---|
| `flow`（销售额/订单数/费用） | 求和 | 求和 | `sum` |
| `stock`（库存/应收应付/余额） | 求和 | **禁止** | **取范围末日**（期末值），不是求和 |
| `non_additive`（率/去重计数/连续天数） | 禁止 | 禁止 | 无合计 |

**落地分两步**（无案例不立标准）：
1. **先关错**：`stock` 指标**不自动附合计**（`totalable=false`），消灭线上错数——零查询面风险；
2. **再补对**：出现真实「期末值」问法时，再加 `total_aggregation='last'`（按 `bizday` 末日切片求和）。

**⚠️ 2026-10-18 订正：源锚点不是「没有」，是「已建但只覆盖零售净额、且证据不落仓」。**

**已建的（不要重复造）**：`deploy/duckle/console/pipelines/lemeng.recon.preagg.item.json` ——
逐日拿湖侧自算与**乐檬自家报表** `nhsoft.report.ai.itemsales.find`（`summary_types:["branch"]`）

### 12.5 分解是**技术**，不是指标

- **02-05 毛利变化原因** 的四效应 = 零售业标准的 **variance decomposition**（价量结构桥）。
  它是**技术**，会随口径争论变 ⇒ 正确落点是保证**输入齐**（收入/成本/数量 × 商品 × 两期宽表），
  让消费者做分解，**不要把它固化成四条分量指标**。
- **可比门店（like-for-like）** 同理：是标准定义，不是客户输入（见 §12.2）。

### 12.6 答案必须自带**分母、覆盖与排除声明**

现行响应只有 `total` + `data_as_of`（两行）。行业标准是五行：**口径名 / 时间窗 / 数据截止 / 分母与样本 / 排除项**。

**判据（以 03-05 为例）**：只报「5 家」是错的；正确形态是
「**在 227 家零售门店中**，5 家连续 ≥10 天无销售（最长 20 天）。**173 个非零售节点已排除**；数据截止 10-16」。
**排除项本身是结论的一部分**——没有它，看数的人会以为「全部门店都没问题」。

**为什么必须由平台自动附加**：参数面 spec §8.4 已实证「SKILL 正文对 flash 级模型是弱引导」
⇒ **对的路必须由平台自动发生**，不能靠提示词。

### 12.7 指标生命周期与「不可用于」

- 现行 tier 只有 `certified | experimental`，缺 **`deprecated` / `superseded`**。
  issue #816（`missing_cost_amount` 该不该退役）本质上是生命周期问题——没有这个状态，废弃只能靠人记。
- 「不衡量员工违规」「不当作净利润」「不能只对有单日求日均」——客户文档里全是这类**禁止性说明**。
  现在写在 `definition` 文字里，**没有结构化字段** ⇒ bot 不会自动带进答案。
  缺 `do_not_use_for: []`（建议必填于 certified）。
