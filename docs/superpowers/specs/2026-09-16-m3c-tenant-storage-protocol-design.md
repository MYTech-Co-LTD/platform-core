## 0. 本文是什么 / 不是什么

**是**：一次**模块接入协议的扩展**提案——把「宿主按请求向模块注入**本租户的**存储配置」
这件事的载体、来源、兜底语义、声明方式与迁移路径定清楚。

**不是**：

- 不是「修隔离漏洞」——**隔离本身没破**，见 §1.4。缺的是**可配置性**。
- 不是存储客户端抽象的提案——spec §2.3 已定「`storage.ts` 模块内自持，**第二个消费者出现再抽公共包**」，
  本文不推翻它（§4.3 说明协议层与实现层各在哪）。目前仍只有 aftersales 一个消费者。
- 不是 `modules/aftersales` 的改造计划——本文只定**协议**；模块侧的改造是协议的**第一个消费者**，
  在 §5 的步 4 出现。

## 1. 问题陈述

### 1.1 现状（代码事实，逐条可核）

| 事实 | 出处 |
|---|---|
| `ModuleContext` **只有** `pool` 一个字段 | `packages/platform-sdk/src/module.ts:20-22` |
| `createRouter(ctx)` **全进程只调一次**（装载期） | `apps/server/src/loader.ts:294`：`def.createRouter({ pool: deps.pool })` |
| 模块装载发生在**启动期**，早于任何请求 | `apps/server/src/app.ts:276` 的 `runtime.mount(app)` 在 ③ 装载段之后 |
| aftersales 在装载期把 env 读成**一个常量**并闭包进所有路由 | `modules/aftersales/index.ts:27-28`：`const config = zosConfigFromEnv(process.env)` |
| 五个 env 键缺任一 ⇒ `null` ⇒ 附件端点 503 | `modules/aftersales/storage.ts:61-68`、`routes/attachment.ts:36,85` |
| `identity` 是**按请求**注入的宿主上下文键 | `apps/server/src/app.ts:214` 挂 `sessionMiddleware` → `session-middleware.ts:217,221` 的 `c.set('identity', …)` |
| `tenant` 同样是按请求注入，且**已经 `select t.*`** | `apps/server/src/tenant.ts:65-66`（`select t.* from platform.tenant t join …`）→ `:103-105` 的 `c.set('tenant', row)` |
| 租户行配置的**既有先例**是 `wechat_oa_app_id/secret`，但**消费方是宿主路由**，不是模块 | `apps/server/src/migrations/005_tenant_wechat_oa.sql`、`apps/server/src/tenant.ts:30-31`、`apps/server/src/routes/auth-wechat-oa.ts:110,148` |

### 1.2 为什么 env 形态只对单租户成立

两个独立的结构性原因，缺一条都不成立：

1. **`.env` 是进程级的**——一个进程只有一份 `AFTERSALES_ZOS_*`。多租户同进程部署时，
   所有租户必然共用一个桶 + 一套 AK/SK。
2. **`createRouter` 装载期只调一次**（`loader.ts:294`）——即使有人想按租户读配置，
   装载期也**没有租户**可读：租户是**按请求**由 Host 解析出来的（`tenant.ts:65`）。

所以这不是「配错了」，而是**协议里没有承载它的位置**。

### 1.3 收口要解决的三件事

| # | 问题 | 收口后 |
|---|---|---|
| 1 | **BYO**（租户自带存储）做不到 | 租户可在自己的桶里放附件 |
| 2 | **密钥爆炸半径 = 全租户**（一把 AK/SK 泄露波及所有租户） | 半径收缩到单租户 |
| 3 | **无法按租户归集存储成本** | 每租户一个桶 ⇒ 成本天然可归集 |

### 1.4 ⚠️ 先澄清：**隔离没有破**

**本提案不是安全修复，别把它写成「修隔离漏洞」。** 现有实现的三道隔离都是完好的：

- key 规范 `aftersales/{org}/{ticket_ref}/{uuid}` 带 `{org}` 段（`storage.ts:52-54`）；
- 每次读都 `where org = $1`，参数取 `identity.orgId`（`routes/attachment.ts:72`）；
- 预签名 URL 由**服务端按 DB 行**生成，客户端拿不到拼接权（`routes/attachment.ts:96`）。

缺的是**可配置性**：一个进程只能有一份配置。把这句话写反，会让后续评审去防守一个不存在的洞，
并让真正的决定（配置从哪来、怎么声明、兜底怎么算）失去注意力。

## 2. 方案对比

四个轴各自独立，但**推荐方案是一个组合**（§2.5）。每个轴给 ≥2 个方案 + 明确取舍。

### 2.1 轴一：注入的**载体**——模块怎么拿到这份配置

#### A1（推荐）宿主中间件 → **请求上下文键** `c.get(TENANT_STORAGE)`

宿主在**模块 API 子树**上挂一条中间件，按请求把**本次请求所属租户**的配置投影进 Hono context；
模块在自己的 handler 里 `c.get(...)` 读。与 `identity` 的做法**逐字同构**。

- ✅ **与既有范式同构**——`identity` 就是这么做的（`session-middleware.ts:217` 写、模块
  `c.get('identity')` 读），评审与新人零学习成本。
- ✅ **`ModuleContext` 一字不改**（见轴四）——兼容性最强的一条论证。
- ✅ **天然满足 I-1 挂载顺序**：中间件挂在 `runtime.mount()` 内部（`loader.ts:364-437`），
  而 ⑨ 整体在 ⑥（租户+会话）之后 ⇒ 顺序无法被写错。
- ✅ **零额外 DB 往返**：`resolveTenantMiddleware` 已经 `select t.*`（`tenant.ts:65`），
  配置列若落在 `platform.tenant`，**投影是纯函数**（§2.2-B1）。
- ⚠️ 代价：模块要自己写 context 变量类型（与 `identity` 今天的处境完全相同，见
  `modules/aftersales/index.ts:25` 的 `new Hono<{ Variables: { identity: Identity } }>()`）。
- ⚠️ 代价：键名是**约定**而非契约（宿主 set、模块 get，编译器不连线）。用 `platform.` 前缀
  避撞（照 `DECLARED_GATE_APPROVED` 的既有做法，`packages/platform-sdk/src/module.ts:92`）。

#### A2 `ModuleContext` 上挂**按请求的解析器** `ctx.storageFor(c)`

`createRouter` 拿到的 `ctx` 上多一个函数，模块在 handler 里调 `await ctx.storageFor(c)`。

- ✅ 把能力**显式写进协议**（`ModuleContext` 是「宿主递给 `createRouter` 的运行时上下文」，
  加一个解析器是它的自然延伸），模块不必记 context 键名。
- ❌ **签名里仍然必须带 `c`**（或等价的 per-request 载体）——因为租户是请求期材料。
  于是它实质是「用函数调用模拟一次 context 读」，多一层间接，**没有任何结构收益**。
- ❌ **不解除对宿主的顺序依赖**：`resolveTenantMiddleware`（`app.ts:206`）仍必须先跑，
  否则 `storageFor` 无从取租户。载体换了，约束没换。
- ❌ **改动面更大**：`ModuleContext` 是共享接口，加字段波及 `apps/server/src/loader.ts`、
  `packages/platform-sdk`、**每个模块**的类型（含 `modules/demo`）。而它有
  `module.ts:27-43` 详述的 Hono 泛型不变性摩擦史——接口越宽，摩擦面越大。
- ❌ **对「模块声明」不提供任何结构约束**：谁来表达「我需要租户级存储配置」仍需另想办法
  （轴四/§3），A2 没帮上忙。

#### A3 模块自己去读 `platform.tenant`（自带一份查询）

- ❌ **直接违反 B1**（`docs/architecture.md` §4.1：模块只许自身 id 的 schema，平台代码只许
  `platform.*`）。不是权衡项，是硬约束，**排除**。

#### A4 装载期把「按 org 的配置缓存」给模块，模块自己带 org 查

- ❌ 把「模块可以指定 org」这件事**写进协议**——正是 §3 要防的
  「随便声明就能拿到别人的凭证」。**排除**。

### 2.2 轴二：**配置来源**

#### B1（推荐）**租户行**——`platform.tenant` 加列

形态与 `wechat_oa_app_id/secret`（`migrations/005_tenant_wechat_oa.sql`）**同构**，spec §2.3 定的目标形态。

- ✅ **`select *` 自动带出**：`tenant.ts:65` 是 `select t.*`，加列后**查询零改动**，
  `TenantRow` 加两个字段即可（`tenant.ts:12-32` 的既有注释已把这个模式写清）。
- ✅ **零额外查询**：租户行**本来就在本次请求的 context 里**（`c.get('tenant')`），
  投影是纯函数 ⇒ 不新增 DB 往返。
- ✅ **权威租户清单已在 DB**（loader.ts:107 的既有口径），不引入第二处真相。
- ⚠️ **代价：列会变多**。五元组（endpoint/region/bucket/AK/SK）＝ 5 列，叠加
  `platform.tenant` 上已有的 wecom×3 + wechat_oa×2。**这是真实的设计味道**，
  由 §8 待拍板清单第 3 条决定是否接受。

#### B2 独立表 `platform.tenant_storage`

一个租户多行（多桶 / 按用途分桶 / 轮换留旧）。

- ✅ **形态上更对**：配置是 1:N 关系，且「一个租户多个桶」是可信的未来需求；
  还顺手解决 §7.2 的 bucket 归属问题（有一条配置行可以被 object_key 引用）。
- ✅ 不污染 `platform.tenant` 的列宽。
- ❌ **多一次查询**：`c.get('tenant')` 那条 `select t.*` 带不出它，要在中间件里 **join 或补一次
  select** ⇒ 每请求 +1 DB 往返（对照 `loader.ts:386-388` 对 `enabledFor` 每请求一查的**刻意**
  不缓存：本仓接受这种代价，但**要显式记账**）。
- ❌ **与 spec §2.3 的「与 `wechat_oa_app_id/secret` 同构」承诺分叉**——同构是 spec 的
  显式取舍，改它属于改 spec，不是实现细节。
- ❌ 当前只有**一处**消费（aftersales 附件），YAGNI。

> **推荐 B1，但把 B2 记为演进方向**：若 §8 第 3 条裁定「未来要一租户多桶」，B1→B2 的迁移
> 是「建表 + 回填 + 改投影」，**不需要改协议**（模块看到的是投影后的值，来源变了它不知道）。
> 这正是 A1 把「来源」和「载体」解耦的收益。

#### B3 配置进 Casdoor（订阅源已在 Casdoor）

- ❌ 订阅是**授权**，存储凭据是**资源**，两者语义不同；且模块读不到 Casdoor（B2 边界：
  `docs/architecture.md` §2，「`@platform/auth-core` 只许 `apps/server` 引」）。**排除**。

### 2.3 轴三：**兜底与故障语义**（本轴是本提案最容易出错的地方）

spec §2.3 定「env 退化为**平台默认/兜底**（租户未配时用平台桶）」。这句话需要补三个决定：

#### C1 兜底的**方向**：只在「租户没配」时生效，配了**绝不回退**

- ❌ **不推荐**「租户配置有问题就回落平台桶」。这不是容错，是**把红改成绿**：
  - 租户以为附件在自己的桶里，**实际落在平台桶** ⇒ 数据位置被误述；
  - 租户的 500GB 视频灌进平台桶 ⇒ **成本事故**，且违反 §1.3 的第 3 条（成本归集）。
- ✅ **推荐 fail-explicit**：租户行**只要部分存在**（如只填了 endpoint，没填 AK/SK）⇒
  **视为「配置存在但无效」⇒ 不注入 ⇒ 模块 503**，**不回落平台桶**。
  「部分填写」没有任何可能是有意为之。

> 由此推出：**「租户未配」的判据必须是「五列全空」**，而不是「投影失败」。

#### C2 「没配」与「配了但坏」必须分开

| 情形 | 平台侧可观测性 | 建议处置 |
|---|---|---|
| 没配（租户行全空 **且** 无平台 env 兜底） | 确定 | 不注入 ⇒ 模块 503 `ZOS_NOT_CONFIGURED`（**与现状逐字同形**，见 `routes/attachment.ts:36`） |
| 配了但**字段残缺** | 确定 | 不注入 ⇒ 503（**不回落**，见 C1） |
| 配了、字段全、但**连不上 / 凭据无效** | ⚠️ **平台侧完全静默** | 见 C3 |

#### C3 ⚠️ **「配了但连不上」在请求路径上是不可观测的**——这是本提案最需要人知道的发现

`presignPut` / `presignGet`（`storage.ts:83-101`）走的是 `getSignedUrl` ——**SigV4 是纯本地计算，
不发起任何网络请求**。因此：

- 宿主的投影中间件**永远无法**通过「试着用一下」发现配置坏；
- 错误只在**客户端**拿着预签名 URL 去 `PUT`/`GET` 时才出现，而那是**浏览器/手机直连 ZOS**，
  **平台根本看不到**；
- 表现是「用户上传失败」，而平台侧**零日志、零告警、各处都绿**——正是本仓反复标记的那类
  假绿（对照 `~/.claude/rules/common/deploy-verify.md` §3）。

**建议处置（两条，都放请求路径之外）：**

1. **保存时探测**：管理端保存配置时跑一次 `HeadBucket`（或 `ListObjectsV2` with `max-keys=0`），
   失败即拒绝保存并回显原因。这是**唯一**能在平台侧发现配置错的位置。
2. **显式「测试连接」动作**：配置页上一个按钮，重跑同一个探测；用于「当时好的、后来端点挂了」
   这类事后发现的场景（轮换 AK、桶被删、网络策略变更）。

**明确不做**：**不在请求路径上探测**。理由：每请求一次网络往返，把存储侧的抖动
**放大成平台 5xx**，且把一个可选依赖变成硬依赖。

#### C4 平台 env 的角色（与 spec 的一处张力，见 §7.1）

env 五键（`.env.example:34-38`）在收口后**保留**，语义是「**平台默认桶**」。
`zosConfigFromEnv` 现成的「缺任一键 ⇒ `null`」（`storage.ts:61-68`）**正好承接**「没有平台兜底」
这个状态，无需修改。

### 2.4 轴四：**兼容**——现有模块与 `ModuleContext` 怎么过渡

| 方案 | 评价 |
|---|---|
| **D1（推荐）加而不改**：`ModuleContext` 保持 `{ pool }` 一字不动；新能力 = manifest 可选字段（默认缺省）+ context 键（不声明就不 set）。 | ✅ 现有 `modules/demo` 与 `modules/aftersales` **一行不改**仍装载通过——这是最强形式的兼容论证：不是「我们改了但保证不破坏」，而是**根本没改**。✅ 装载期双向核对（`loader.ts:145-189`）不受影响（它管路由集合，本文不动路由）。 |
| D2 给 `ModuleContext` 加**可选**字段（如 `storage?: boolean`） | ⚠️ 可选字段确实向后兼容，但 `module.ts:27-43` 记录了 Hono 泛型不变性带来的摩擦史：`ModuleContext` 接口每宽一分，摩擦面就大一分。**收益为零**（D1 也能表达同样的事），**不建议**。 |
| D3 改 `ModuleContext` 为泛型 / 版本化 | ❌ 远超本次需要，且会把泛型不变性摩擦传染给 `ModuleDefinition`（`module.ts:36-38` 已实证这条路走不通）。**排除**。 |

### 2.5 推荐组合与一句话理由

> **A1 + B1 + C1/C3/C4 + D1**
>
> **载体用请求上下文键（与 `identity` 同构），来源用租户行列（与 `wechat_oa_*` 同构），
> `ModuleContext` 一字不改。**

理由集中在一点：**这条路让本仓已有的三套约定（`identity` 的注入姿势、`wechat_oa_*` 的
租户行配置姿势、`ModuleContext` 的装载期契约）一条都不用动**。协议扩展的风险主要在「改到
别人」，而这条路改的只有「加」。

## 3. 模块侧怎么声明「我需要租户级存储配置」

### 3.1 问题

如果宿主**无条件**把配置注入每个模块请求，则：

- 「note 便签模块」也拿得到租户存储凭据——**违反最小权限**；
- 审计面消失：看 manifest 看不出某模块用不用存储。

### 3.2 候选

| 方案 | 评价 |
|---|---|
| **声明进 manifest（推荐）** | ✅ 延续**声明即授权**——manifest 是本仓模块能力的**唯一审计面**，「模块要什么」看 manifest 就够（与 `permissions` / `api.internal` / `guest.scope` 同一逻辑）。✅ 可静态校验（schema 收窄 kind 枚举 ⇒ 写错即装载失败）。✅ 条件化挂载是**一行**：`if (m.manifest.storage) app.use(...)`。 |
| 模块不声明，`c.get` 拿到 `undefined` 自己降级 | ❌ 等于**任何模块都能读到租户存储凭据**；❌ 无静态面。 |
| `ModuleContext` 加布尔位 | ❌ 见 D2：与 D1 收益相同、摩擦更大。 |

### 3.3 ⚠️ 关键安全性质：**声明的是「能力」，不是「租户」**

这是本提案里必须写死的边界（也是任务简报点名要防的那件事）：

1. **配置的作用域永远是「本次请求所属的租户」**——宿主从 `c.get('tenant')`（`tenant.ts:103-105`）
   取，模块**没有任何途径指定 org**。
2. **投影后的值是窄视图，不是 `TenantRow`**——⚠️ **绝不把 `c.get('tenant')` 直接递给模块**：
   `TenantRow` 里坐着 `wecom_secret`、`wechat_oa_secret`、`casdoor_org`
   （`tenant.ts:12-32`）。把它给模块 = 每个模块都能读到该租户的**企微/公众号密钥**，
   还等于把模块引到 `platform` schema 的语义上（B1 的精神）。**必须只投影出存储五元组**。
3. **声明不含凭据名的任何自由度**——manifest 只写 `kind`，写不出 bucket / access key / org。

## 4. 目标形态（契约草案）

**以下为提案形状，供评审；不是要落地的最终代码。**

### 4.1 manifest（新增**可选**字段）

```yaml
# modules/aftersales/manifest.yaml
storage: { kind: s3 }     # 缺省 = 不声明 = 宿主不注入（本模块行为与今天完全一致）
```

- `kind` 是**收窄的枚举**（MVP 只允许 `'s3'`）。写错 ⇒ schema 拒绝 ⇒ 装载失败
  （与 `api.internal[].scope` / `guest.scope` 的 fail-fast 同风格，`manifest.ts:72-121`）。
- ⚠️ **同步改动**：`packages/platform-sdk/src/manifest.ts` 的 `ModuleManifest` 接口 +
  `ManifestObject`（两边有编译期双向断言，`manifest.ts:130-134`——**漏改一边会 typecheck 红**，
  这正是那条断言存在的意义）。
- ⚠️ `scripts/check-manifests.mjs` 是 manifest 的**静态消费方**（该文件头注释自述）。
  zod 对象默认剥离未知键，故加字段**不会**让现有 manifest 挂；但该脚本**要不要认这个新字段**
  是落地时的一步（**不是**门禁升级——按本仓规矩，门禁升级是单独的决定）。

### 4.2 SDK：类型 + context 键常量

```ts
// packages/platform-sdk/src/module.ts（形状草案）
/** 宿主按【本次请求所属租户】投影出的存储配置。kind 由 manifest.storage.kind 选定。 */
export interface TenantStorageConfig {
  kind: 's3'
  endpoint: string        // 已规范化（含协议、无尾斜杠），见 storage.ts:37-40
  region: string
  bucket: string
  accessKeyId: string
  secretAccessKey: string
}
/** Hono context 变量键。带 platform. 前缀避撞（照 DECLARED_GATE_APPROVED，module.ts:92）。 */
export const TENANT_STORAGE = 'platform.tenantStorage'
```

**边界**：SDK 只定义**配置的形状**，**不定义客户端**——`ZosStorage` 类继续留在
`modules/aftersales/storage.ts`（spec §2.3：第二个消费者出现再抽公共包）。协议管「数据怎么到
模块手里」，不管「模块拿它做什么」。

### 4.3 宿主：在模块子树里挂投影中间件

挂在 `runtime.mount()` 的每模块循环内（`loader.ts:364-437`），**位置**：

```
app.use(base + '/*', 启用闸门)          // loader.ts:412（既有，先）
app.use(base + '/*', 存储投影中间件)     // ← 新增（中）
app.route(base, m.router)               // loader.ts:414（既有，后）
```

- **必须在 `route` 之前**：Hono「handler 先注册、`use` 后注册 ⇒ 中间件永不执行」已实证两次
  （`docs/module-protocol.md`「实现注意」第 2 条、`loader.ts:376-378`）——顺序错了就是
  **静默洞**（模块 `c.get` 恒 `undefined`，表现为附件全线 503）。
- **在启用闸门之后**：停用模块该拿 404 就先拿 404，不必先花代价解配置；
  且启停语义的生效点更早（对照 `module-protocol.md`「停用语义」）。
- **中间件体内是纯函数、零 IO**：读 `c.get('tenant')` → 投影 → `c.set(TENANT_STORAGE, cfg)`。
  租户行已经被 ⑥ 取过（`tenant.ts:65`），**没有新增 DB 往返**。

### 4.4 模块：从「装载期常量」改为「按请求解析」

```ts
// modules/aftersales 的目标形状（草案）
createRouter: ({ pool }) => {
  const r = new Hono<{ Variables: { identity: Identity; [TENANT_STORAGE]?: TenantStorageConfig } }>()
  // …
  const cfg = c.get(TENANT_STORAGE)
  if (!cfg) return c.json({ error: 'ZOS_NOT_CONFIGURED' }, 503)
  const storage = storageFor(cfg)     // ← 见下
}
```

⚠️ **实现注意（值得写进协议/计划）**：现状是**装载期 new 一个 `S3Client` 并闭包复用**
（`index.ts:28`）。改成按请求后，**不能每请求 `new S3Client`**（凭据解析 + 连接池建设，
且会让 keep-alive 失效）。建议模块侧持一个**按配置指纹缓存的 client 池**：

- 缓存键 = `endpoint + bucket + accessKeyId` 的摘要（**不含 secret 明文**）；
- 容量有界（租户数量级，非请求量级）；
- 这是**模块内的实现细节**，不是协议内容——协议只说「宿主给你配置」。

## 7. 与 spec §2.3 的不符 / 缺口（**任务简报点名要如实指出**）

### 7.1 ⚠️ spec §2.3 内部有一处**自相矛盾**（需要人裁定）

原文（同一段落内）：

> 「**启用判定 = 租户行存储配置存在**；env 退化为**平台默认/兜底**（租户未配时用平台桶）。」

这两句**不能同时成立**：如果平台 env 是兜底，那么「租户行无配置」的租户**依然有可用存储**
（用的是平台桶），此时「启用判定 = 租户行配置存在」判的到底是什么？

三种可能的读法，**必须由人拍板**（列入 §8 第 1 条）：

| 读法 | 含义 | 影响 |
|---|---|---|
| (a) 判「是否 BYO」 | 租户行有配置 = 该租户自带存储；无 = 用平台桶 | 「启用」是 UI/运营概念，不影响 503 语义。**本文按此读法写的**。 |
| (b) 判「附件功能是否可用」 | 租户行有配置**或**平台 env 有 ⇒ 可用 | 则「启用判定」应写成「租户行配置 ∪ 平台默认」，spec 措辞需订正。 |
| (c) 平台 env 在 M3c 后**不再作为兜底**（只在单租户形态下作为唯一来源） | 多租户部署下**必须**每租户配，否则 503 | 与 §2.3 的「租户未配时用平台桶」直接冲突，但与「启用判定 = 租户行配置存在」一致。 |

**注意 (c) 是一个真实的分叉**：它意味着多租户部署**强制** BYO。本文 §§2.3 按 (a)/(b) 的
「env 可作兜底」写；若裁定 (c)，则 §2.3 的 C1 与 C4 需要重写（兜底整条去掉）。

> **✅ 已裁定（2026-09-16）：(a)。** 判「是否 BYO」——租户行有配置 = 该租户自带存储，无 = 用平台桶；
> **「启用」是运营/UI 概念，不影响 503 语义**。env 照 C4 保留为**平台默认**⇒ 本节的 C1 与 C4
> **按 (a) 原样成立，无需重写**；(c) 这条分叉**未被采纳**（多租户部署不强制 BYO）。

### 7.2 ⚠️ **`object_key` 不足以定位对象**——spec §2.3 未覆盖的缺口

这是本次实读发现的最大缺口，**且它不是协议问题而是数据模型问题**，但**由协议变更直接引发**。

**事实**：`aftersales.ticket_attachment` 只有 `object_key` 一列，**没有 bucket / endpoint**
（`modules/aftersales/migrations/001_init.sql:148-160`）。而预签名使用的是**当次请求解析出的
配置**（`routes/attachment.ts:96`）。

**后果**：一旦租户的存储配置发生变化，**存量行的下载链接会指向新桶** ⇒ `NoSuchKey`。
触发场景全部是真实会发生的事：

- 租户从**未配**（走平台桶）→ **配了自己的桶**：切换前上传的附件**全部读不到**；
- 租户**换桶** / 换 AK 对应的账号；
- 步 5 的回滚（清空租户行 ⇒ 回落平台桶）：**租户桶里的对象全部读不到**。

**spec 的既有口径「附件存量不搬运」（§2.3）指的是无极 COS 的历史附件，不是这一类。**

**三个处置方向（列入 §8 第 2 条，需人拍板）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **① 记 `storage_ref`（推荐）** | 附件行增一列记录写入时的配置标识（最小可用：`bucket` + `endpoint`，或一个配置行的 id）。读时按它取配置。 | 改 aftersales 的迁移 + 写入路径 ⇒ **跨出「纯协议」范围**，要么纳入 M3c 范围、要么明记为 M3c 的已知边界。**但这是唯一不依赖人记性的选项。** |
| ② 配置冻结 | 规定「桶里一旦有对象，配置不可变更」，只允许在空桶时改。 | 简单、零迁移；但对租户是硬限制，且**无法用技术手段强制**（平台无法在不联网的情况下知道桶里有没有对象——见 §2.3 C3）。 |
| ③ 接受断链 + 人工迁移 | 出问题时人工搬对象。 | 成本最低，但**故障在客户端表现为「附件打不开」、平台侧静默**；与 `deploy-verify.md` §3「别用容错掩盖失败」的精神相反。 |

> 若选 B2（独立配置表），`storage_ref` 天然有归属（引用配置行 id）——这是 B2 的一个额外加分项，
> 已在 §2.2 记过。

> **✅ 已裁定（2026-09-16）：①，且明确纳入 M3c 范围（不另开一期）。** ②③ 落选——②「配置冻结」
> **无法用技术手段强制**（平台不联网就不可能知道桶里有没有对象，见 §2.3 C3）；③「接受断链」与
> `~/.claude/rules/common/deploy-verify.md` §3「别用容错掩盖失败」的精神相反。
> 来源仍是 **B1**（租户行加列，§8 第 3 条），故 `storage_ref` 记的是**写入当时的配置标识**
> （最小可用：`bucket` + `endpoint`），不是配置行 id。
> ⇒ 数据面的落地订正已写进 `2026-09-15-aftersales-module-design.md` §2.3；
> 落地步位见本文 §5 的「拍板补记」。**协议层不需要为此改形状**——模块看到的仍是投影后的值。

### 7.3 ✅ spec 与代码**相符**的部分（已逐条核对）

- 「`ModuleContext` 目前**只有 `pool`**」——**相符**（`module.ts:20-22`）。
