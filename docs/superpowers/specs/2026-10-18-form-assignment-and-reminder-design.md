# forms 指派与催办：名单从哪来（设计稿，待人审）

> 状态：**✅ 已人审（2026-10-19）**——§7-1 定案：**v1 名单 = 人**（Casdoor 用户名；门店 subject 记演进项）。正典已落档：platform-core `docs/architecture.md` §2.4「指派与催办：名单只存引用」。
> 上游：`docs/architecture.md` §2.4（受管数据集）、§2.6（通知规则层）；ADR 0005 §18（通知）；实施计划 `2026-10-18-notification-rules-layer.md` 的 **T9/T11 前置**。
> 日期 2026-10-18。

## 1. 问题（实测，不是推演）

通知层的 `form.assigned` / `form.due_reminder` 需要一个「**谁该填**」的答案，但：

| 事实 | 依据 |
|---|---|
| forms 只有 6 张表（`kind` / `asset_version` / `asset_head` / `submission` / `dict_item` / `dict_global_item`） | `modules/forms/migrations/001_kernel.sql` |
| 全模块搜 `assign` / `due` / `deadline` / `remind` / 催办 / 指派——**零命中** | 实测 grep |
| 正典也没定义「催办策略」是什么 | §2.6 只写了「表单声明了催办策略即派生 `form.due_reminder` 规则」，**未定义** |

⇒ **T9/T11 的真实前置 = 先定义「名单从哪来、截止怎么定」。** 这不是接线问题。

## 2. 核心判断

**名单是「会变的运营数据」，不是「表单的语义」** ⇒ 按 §2.4 铁律「**契约里永不含值，只含引用**」，表单契约里**只写对名单的引用**，名单本体由**受管数据集（字典）**承载。

这条同时满足 §2.4 的「何时才配得上受管值集」四判据里的三条以上：名单会被多个表单引用、会变、需要「某次提交对应当时的名单」的历史可解释。

## 3. 方案对比（我推荐 B）

| | 方案 | 优 | 劣 | 判断 |
|---|---|---|---|---|
| A | 表单契约里**写死名单** `assignees: string[]` | 最简，零新概念 | 名单一变就要改表单（走版本化）；大名单（几百门店）不合适；历史解释要翻版本 | 可作 v0，但会把「运营数据」冻进「契约」 |
| **B** | **名单 = 字典引用** `assignees: { dictRef: 'dict:<id>' }` | **符合契约铁律**；复用字典已有的软删 / key 不可变 / 租户 vs 全局双档纪律；名单可变而契约不变 | 需要字典里有一条「人」的名单（按本租户建） | ✅ **推荐** |
| C | 外部权威（组织架构 / 门店系统） | 名单自动同步 | §2.4 明说**今天无合法通路**（操作面未落地，跨 schema 读 = B1 违规） | 今天不可行 |
| D | 填写任务 = case（assignee 由 case routing 给） | 复用 case 的指派与 SLA | 跨服务；把 forms 的填写强绑 case-engine；且每客户引擎实例 → forms 的可用性被 case-engine 拖住 | 与 §15 边界冲突 |

## 4. 契约形状（草案）

表单定义（`asset_version.body`）新增两个**可选**顶层键：

```jsonc
{
  "schema": { /* … 既有 draft-07 契约 … */ },
  "uiSchema": { /* … */ },
  // 新增：谁该填 —— 只存引用
  "assignees": { "dictRef": "dict:store-staff" },
  // 新增：截止 —— 从发布时刻起算（v1 只这一种；字段驱动的截止不做）
  "due": { "afterDays": 7 }
}
```

- `dictRef` 语法与字段里的字典引用**完全一致**（`dict:<id>` / `gdict:<id>`）——解析走同一套 `dictOptions`，不新增解析器。
- 名单条目的 **key = Casdoor 用户名**（不是显示名）。⚠️ **待验**：v1 先按「名单里放 Casdoor 用户名」实现；若运营场景是「门店」而非「人」，需另定映射（见 §7）。
- 两个键都缺省 ⇒ 该表单**没有指派语义**：不派生 `form.assigned`、不派生催办规则。**向后兼容**：存量表单不受影响。

## 5. 执行流

```
发布（人 gate 通过）
  └─ 若契约含 assignees：
       解析 dictRef → 名单（只取 enabled 的条目）
       → 逐人 emit `form.assigned`（event_id = 确定性：form:<assetId>:<version>:assigned:<user>）
       → POST /derive {kind:'reminder', mount:<formId>}（声明派生催办规则，幂等）

定时（T11，openship job）
  └─ 对每个「含 assignees + due」的已发布表单：
       due = published_at + afterDays
       未提交 = 名单 − { submission.submitted_by（该版本）}
       → 逐人 emit `form.due_reminder`（event_id 含日期：form:<assetId>:<version>:remind:<user>:<YYYY-MM-DD>）
```

**幂等**：两处的 `event_id` 都是确定性的 ⇒ 重复发布/重复调度天然去重（回执表 `unique(event_id, rule_id)` 兜底）。

**量**：一份名单 N 人 ⇒ 发布时 N 条 emit、每次调度 N 条 emit。v1 接受（名单量级是「一店一人」百级）。⚠️ **待实测**：N=500 时的调度耗时与 Novu 限速（这是 T11 的验收项）。

## 6. 不做什么（v1 写死）

| 反模式 | 为什么 |
|---|---|
| 多级 / 条件指派 | 无真实案例；与「无案例不立标准」冲突 |
| 按角色/组织架构自动展开名单 | 需要外部权威通路（§2.4 今天无） |
| 字段驱动的截止（从提交里取日期） | v1 只做「发布后 N 天」；真需求出现再加 |
| 补填 / 代填 | 提交面只认 `submitted_by`；代填是另一套权限语义 |
| 名单变更后重发 `form.assigned` | v1 只在发布时发一次；名单变更走**催办**兜底（下次调度自然覆盖） |

## 7. 待验 / 待定

1. **名单条目是「人」还是「门店」**——本设计按「Casdoor 用户名」实现。若运营场景是「N 家门店各交一份」，则名单是**门店**，需要「门店 → 提交人」的映射（或提交里带门店号 + `submitted_by` 对账）。**这条会改变契约形状，实施前必须定。**

   > **证据（2026-10-18 追加调研）**：仓里唯一的真实表单样本是
   > `modules/forms/domain/materials.ts:75` 的「**门店巡检登记**」（`site-inspection`），其 `storeNo`
   > 声明为 **`readOnly: true`**——即**门店由服务端决定**，不是用户填的。**这指向「门店是主体、人是填表人」。**
   >
   > 但同一调研发现一个**前置缺口**：`readOnly` 字段今天**只拒不留**——
   > `modules/forms/domain/contract.ts:337-344` 的闸 4 是「契约声明 `readOnly` 的字段**出现在提交体里即拒**」，
   > **全链路没有任何「服务端注入只读字段值」的通路**。
   > ⇒ 「门店是 subject」需要先补一个**主体注入机制**（从身份/上下文填 readOnly 字段），
   > 而这是比「名单」大得多的设计。
   >
   > **本稿的推荐（据此调整）**：**v1 名单 = 人**（`submitted_by` 与名单直接对账，**零新机制**）；
   > **门店作为 subject** 记为演进项，触发条件 = 首个真实门店巡检表单上线，届时要连带设计
   > 「主体注入」（readOnly 字段从哪来）。**理由：无案例不立标准——今天没有已上线的门店表单样本，
   > 为它先造主体注入机制属于为假想需求付基建成本。**
2. **N=500 的量级**（§5 待实测）。
3. **`due` 的语义**：`published_at + afterDays`——若表单被回滚/重发，截止是否重算？（本稿按「以当前 published 版本的发布时间为准」，需确认。）

## 8. 验收（写进实施 PR）

- 契约含 `assignees` 的表单发布后：名单里每人各收到一次 `form.assigned`；控制台规则列表出现一条「声明派生」的 `form.due_reminder` 规则
- 到期未提交的人收到**一次** `form.due_reminder`（同日重跑不重复）
- 已提交的人**不收**催办
- 契约**不含** `assignees` 的存量表单：行为完全不变（负对照）
- 名单条目被软删后：新调度不再催该条目；历史提交仍可解释
