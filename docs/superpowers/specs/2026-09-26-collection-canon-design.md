## 1 现状清点：为什么是「补入口」而不是「再开一份」

### 1.1 既有正典自称（数据面相关，不含历史 spec）

| 文件 | 自称是什么的正典 | 性质 |
|---|---|---|
| `docs/architecture.md` §2.2 | 数据栈**职责边界** | 架构文档的一节 |
| `contracts/README.md` | 契约**形态与纪律** | **目录自述** |
| `duckle/README.md` §7 | duckle **能力接入口径** | **目录自述** |
| `deploy/duckle/console/README.md` | 调度器**机制** | **目录自述** |

**这四者不互相冲突**——各讲一个不同的主语（组件边界 / 文件格式 / 引擎能力 / 调度机制）。
它们的问题是**没有一个总入口**，且**没有一份讲「流程」**。

### 1.2 真病根：文档地图没有采集这一行

`AGENTS.md` 的「文档地图」里，改模块、部署/接入/回滚、冒烟验收、提交纪律**都有路由**，
**唯独数据面/采集没有** ⇒ 接采集任务的人没有入口，只能到处翻。**这才是「感觉有好几个正典」的来源。**

### 1.3 为什么不能「把所有采集的都塞进一个文件」

那四份**大多是目录自述**（「这个目录里有什么、这个组件是什么」），合计约 60KB。
字面合并会把它们抽空——而改契约的人就在 `contracts/` 目录里，抽走正文等于让他每次多跳一次，
且这三份现在**已三向互指**，指针网只会更密。
⇒ **正典只管「流程与决策」，下钻给指针**；目录自述留在原处。

### 1.4 既有材料缺的是「怎么办」四件事

| 缺口 | 现状 |
|---|---|
| **选型没有判据** | 拍板散在 spec（「duckle 能力可覆盖的绝不自建」是结论，不是判据），没有「给定一个源，走哪条通道」的判定 |
| **流程散落** | 七层分工在 layered spec、SOP 在 deploy SOP、引擎坑在 duckle README、调度在 console README —— 接一个源要读 6 份、且不知道顺序 |
| **运维没有入口** | 「失败看哪 / 漂移怎么处置 / 容量什么时候撞顶」只在各处零散提及 |
| **生命周期缺后半段** | 回填只在乐檬 spec §9 有、**退役任何地方都没有** |

> `docs/data-platform-handbook.md` 指向的 `team-harness/docs/standards/data-platform.md`
> **尚未合入**（挂起于 PR #79，因 Actions 账单额度）；且那份 2026-09-21 稿**早于乐檬 S1–S3 的全部实测**
> （无选型决策 / 无写模型 / 无自然键与粒度纪律 / 无末页守卫 / 无调度归口 / 无四层对账与回填纪律）
> ⇒ **不能当现行正典用**，只能作将来的纪律提炼目标。

## 2 决策层：怎么选「最合适的方式」

> 这是本正典区别于既有材料的地方。**一张表定案，不靠临场判断。**

### 2.1 通道选型

**默认**：duckle 管线（含 job 层薄 wrapper）。依据见乐檬 spec §4（决策 5）。

**例外条件**（命中须在决策记录里写明**命中了哪一条 + 证据**）：

| # | 例外条件 | 案例 | 状态 |
|---|---|---|---|
| E1 | **推送式 / 需长驻接收**（源主动推给我们，duckle 是一次性 runner） | 抖音：生产上 `dy-upload` 以 `bare` runtime 跑 `/opt/douyin-life/capture/dy_receiver_run.py` | **有案例**（细节待核实后补） |
| E2 | **需登录态交互 / 浏览器自动化**（无稳定 API） | 无 | **预留，无案例 → 标「待沉淀」，不编** |
| E3 | **引擎能力缺口** | `snk.parquet` / `snk.s3` 都不通 ≠ 引擎不支持——`snk.minio` 可直写 ZOS | **有案例**（`duckle/README.md` §1.4） |

**E3 的证成方法学（硬要求，不许省）**：判「引擎不支持」前必须
① **横向试遍同类组件**（对象存储有 s3 / minio / r2 / b2 四个候选）；
② **先问引擎**（`list_components(kind=sink)` / `get_component_schema` 列真实字段），比外推可靠。
「试了一个不行」**不构成**能力缺口证据。

**例外的红线**：例外的是**执行器**，不是标准。走例外通道的采集必须**同样**满足：
① hive 分区 + `all.parquet` + 落盘即定型；② 幂等可重跑；③ 有契约（`contracts/`）；
④ 过 §4 的四层验收；⑤ 有失败告警。**缺任一条 ⇒ 不是例外，是欠账。**

### 2.2 落地形态（**无例外**）

| 项 | 定死为 | 出处 |
|---|---|---|
| 分区命名 | **hive**（`system_book=3120/`），非 hive 直接校验失败 | `contracts/_schema.schema.json` `const` |
| 文件名 | **`all.parquet`**（唯一），一个叶子分区一个文件 | 同上 |
| 写模型 | **分区单文件覆盖写**：内容 = 该分区**当前完整内容**；历史修正靠重放层幂等覆盖 | 乐檬 spec §5 |
| 定型 | **落盘即定型**（金额 numeric / 时间 timestamp / 日期 date，**不落字符串**） | layered §7 硬约束 1 |
| 身份 | **主体（账套/租户）既是 hive 分区键、也是行内列** | 欠账 C3 的解法 |
| 批次 | 批次标记列（`batch_id` 等）随载荷落盘 | 乐檬 spec §10 |
| 嵌套 | 管线内展开成**行粒度**（湖里落平的行），消费侧免二次展开 | 乐檬 spec §5 |

> ⚠️ **粒度纪律**（2026-09-26 订正过的真实教训）：全量快照类（维度）**湖里一行 = 一个实体 × 一个快照日**
> ⇒ 行粒度键**必须含 `snapshot`**。`(system_book, item_num)` 是**实体粒度**，不是湖行粒度，两者别混用。

### 2.3 节奏选型（由消费侧 SLA 倒推）

- 依据：`docs/architecture.md` §2.3 ②——**订单类高频（小时级或 15 分钟起步，按业务定），档案类日批**；
  **不为实时把批处理改流式**；**采集频率即消费方的 SLA**。
- **分区粒度不得细于采集间隔**（`采集间隔 ≤ 分区时间粒度`）：5min 采集 ⇒ `hour=` 分区
  （每个分区当日被覆盖写多次，终态 = 该小时完整内容）；日更 ⇒ `bizday=` / `snapshot=` 分区。
  ⚠️ 反过来（日更却按 `hour=` 分区）会让 24 个分区里 23 个永远空着——**分区粒度比采集间隔细 = 结构性欠账**。
- 高频率的代价要**写进决策记录**（乐檬单据系 5min 的实测代价：~2.3k 请求/天）。

### 2.4 调度归口（「何时跑」归谁）

| 被调度的东西 | 归口 | 依据 |
|---|---|---|
| **duckle 管线** | **duckle 自带调度器**（常驻 console，`duckle-runner serve` 的 tick 循环） | ADR-0014；`deploy/data-plane-deploy-sop.md` §F |
| **非 duckle 的 runner**（dbt、自建脚本） | **openship job** | 同上（dbt 是另一个 runner，容器内没有 docker，丢不进 console） |

- 判据一句话：**能不能被 duckle console 调度？能就 console。**
- ⚠️ **现状与目标的差**：零售链路（`lemeng-retail-3120-runner`）**仍在 openship job 上**，
  本次**未动**它（正在跑的生产链路，迁移需单独决定与观察，见 SOP §F.5）⇒ 本表是**归口口径**，
  不是「现在已经全迁完」。
- **时区一律 UTC**（容器 TZ 实测为 UTC，openship cron 同口径）；「日期类」参数必须由 wrapper
  **显式钉 `Asia/Shanghai`** 推算——否则 UTC 夜间跑会算成前一天、**写进前一天的分区且不报错**（SOP §F.3）。
- **一账套一个 console**：调度条目带不了自己的 env（实测塞 `env`/`args`/`params` 被静默丢弃）
  ⇒ 共用必然有账套拿到错 token，**且静默采错数据**。

### 2.5 一源一路（禁双采集）

一个源**只有一条采集链路**（`docs/architecture.md` §2.3 明列的反模式：
两个采集器各拉同一源 ⇒ 两份数据必然漂移、对账永远追不上）。

### 2.6 汇总决策表（正典正文里就是这个形态）

| 判定项 | 取值 | 判据 |
|---|---|---|
| 通道 | duckle / E1 / E2 / E3 | §2.1（例外须写证据） |
| 落点前缀 | `<域>/<表>` | 契约 `layout.prefix` |
| 分区键 | `system_book=` + `hour=`/`bizday=`/`snapshot=` | §2.3（粒度 ≥ 频率） |
| 写模型 | 分区单文件覆盖写 | §2.2 |
| 调度归口 | console / job | §2.4 |
| 节奏 | cron + 窗口 | §2.3（消费侧 SLA） |
| 验收 | 四层 | §4 |

## 3 生命周期 SOP（A→I，每步带验收与回退）

> **没有验收的步骤等于没有步骤。** 验收不过不许进下一步。

| 阶段 | 动作 | 验收 | 回退 |
|---|---|---|---|
| **A 摸清源**（不写码） | 字段清单（**每列的正确类型有人签字**）；主体维度有几个；**自然键（行粒度，含 snapshot）**；增量字段；抽样看**真实值**；**网关/接口语义探针** | 能写出幂等采集策略；能说出分页风格、跨度上限、**有无 count**、时间过滤是否**真生效** | — |
| **B 选型定案** | 按 §2 逐项定案，**命中例外须写证据** | 产出**决策记录**：写进正典的**逐源决策登记区**（一源一段；若该源另有 spec，则在 spec 里写、正典只留指针）。**不留在对话里** | — |
| **C 契约** | `contracts/<域>/<源>.<表>.json`（**人写的意图源**） | 元 schema 校验过；与 `layout.prefix` 一致 | 改契约（改前先想清楚 `contractVersion`） |
| **D 管线** | duckle 管线，**由真引擎产出**（MCP `create_pipeline`/`validate`），**仓内不手编**；含 `data.schema` + `qa.contract` gate + `drift` 门禁 + 末页守卫 | 引擎 `validate` 过；`drift` 有效（**先断言声明存在**，防假绿） | 回退到上一版管线 JSON |
| **E 调度** | 按 §2.4 定归口；薄 wrapper 只做三件事（算窗口 env / 注入 / 调 runner） | 排班触发一次且**如实入账**；改定义**两步都做了**（re-seed + 重建容器） | 停服务即回到「没有调度」 |
| **F 验收** | **四层**（见 §4） | 四层缺一层不算过 | 拒写湖是正确行为，不是故障 |
| **G 运维** | 按 §5 速查处置 | 告警可达；容量有余量；观测有数据 | 按 §5 各条 |
| **H 变更与回填** | 改契约 / 改节奏 / 加域；**回填 = 同一管线换窗口参数** | 回填期逐日对账全绿 + 总量 sanity | 回填不影响在线链路（同管线同写出通道） |
| **I 退役** | 旧前缀下线**前**必须：① 已有替代且对账过；② 消费面已切；③ 观察期 | 三项齐备才下前缀 | 保留前缀至观察期结束 |

### 3.1 A 阶段的方法学（最容易省、也最贵）

乐檬的实测教训，全部来自「跳过 A 直接写码」：

- **看真实值，不看文档**：`date_type` 文档写 `format=date-time`，实测**时间分量被网关静默忽略**（06-07 点窗返回 10:43 的单）。
- **能力探针要反着问**：响应**无 total** ⇒ 翻页只能到短页 + 末页守卫；文档写「上限 200」而非 100，
  早期误读直接改变页容量规划。
- **跨度上限分域实测**：单店 ≤3 个月 / 多店 ≤1 个月 / 单据系 >7 天直接拒绝 —— 决定回填分批策略。
- **主体要探到 whoami 级**：PAT 实测**绑定单账套**；且单店单日可能空窗 ⇒ 探针须多店合查。

### 3.2 E 阶段的三个实测坑（写进正文，别让下一个人重踩）

1. **`code.shell` 节点非零退出不让管线失败** —— 整条管线仍 `status: ok`，退出码只是**一行数据**
   ⇒ 必须跟 `qa.contract` 判红（`in_range:0,0`）。
2. **判据后面必须有 sink** —— 引擎是惰性的，gate 当叶子时**判据根本不被求值**。
3. **console 必须显式给 `--duckdb`** —— 否则每次触发都记 `last_run_error: "DuckDB engine isn't installed yet."`。

### 3.3 薄 wrapper 的职责边界（唯一自建增补）

只做三件：按当前时刻**算窗口 env**（`TIME_FROM/TIME_TO/BIZDAY/HOUR`）、**清晨追加昨日**、**调 runner**。
**无状态**：窗口全部由时钟推导（重叠式），**不需要水位持久化**。
凭据走 **job/项目 env**，**不放宽** `deploy/duckle/entrypoint.sh` 的安全闸。

## 4 验收四层（缺一层不算过）

| 层 | 机制 | 抓什么 | 乐檬实测结果 |
|---|---|---|---|
| **自证** | 写后**回读对象存储**（行数/金额） | 上传/转换失败 | 过（19,678 行 / 1,622,276.08） |
| **幂等** | **同 `batch_id`** 重跑 ETag/Size **逐字节一致**；换 `batch_id` 则 ETag 变（**by design**，`batch_id` 是载荷列） | 不确定性 / 重复累积 | 强判通过 |
| **独立通道** | 预聚合端点 vs 明细聚合（dbt audit） | 引擎 / 口径侧 bug | **未归零**（+1.15%，全正偏置 ⇒ 疑口径差，非抽取缺失） |
| **跨系统** | 与旧平台同期关键指标一次性对比 | 口径 / 语义分歧 | 待回填后做 |

> ⚠️ 「引擎说 ok」≠「对象真的到了」——`k1 ok (3 rows)` 只是引擎自认为成功，**必须回读**才算数。

## 5 运维与故障速查（入口式，不复制正文）

| 现象 | 先看哪 |
|---|---|
| 排班没触发 / console 本身有问题 | `docker logs <console>`（正常四行：console on / workspace / DuckDB / **sign-in required**） |
| 跑了但失败 | `schedules.json` 的 `last_run_status` / `last_run_error`；账套卷里 `logs/*.csv` |
| ⚠️ **`/api/schedules` 的 GET 不回运行状态** | 文件里已有、GET 恒 `null` ⇒ **别信那个 GET**，读 `schedules.json` 或 serve 日志 |
| 自证没过（`ASSERT_FAIL` / `DIM_FAILED`） | **拒写湖是正确行为**，不是故障 |
| 容量撞顶 | 末页哨兵命中 ⇒ fail-loud 不丢数；**余量按阈值算，不按页数×容量算** |
| 漂移 | 先看**声明是否存在**（`drift` 在未声明 schema 时**静默 exit 0 = 假绿**） |
| 观测没数据 | `OPS_SINK=DISABLED reason=no_ingest_env` ⇒ 见 issue **#210** |
| **下游数据陈旧（采集绿、报表陈）** | **先查物化有没有在跑**——2026-09-26 实测：37 个 job 无一跑 dbt，PG 停在 09-23 |
