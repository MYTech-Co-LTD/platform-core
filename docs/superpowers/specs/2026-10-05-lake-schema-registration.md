# 湖 schema 的注册机制：契约注册 + 表级封版 + 读侧断言（设计稿 · 已定方案）

> 2026-10-05 ｜ 触发案例：`order_total_money` 补采（#430/#432）暴露的 flag day
> 状态：**方案已定**（架构先行：本文即提案；经同意后更新 `docs/architecture.md` 再写码）
> 真机验证：§2 的探针在数据面机 `8281d598` 上跑过（CLI 路径 + **pg_duckdb 生产读路径**两条都验），原始输出逐条抄录

## 0. 结论先行

**选「中」：契约注册 + 生成下游 + 三向门禁 + 表级封版标记 + 读侧 fail-closed 断言 + 注册表驱动回填，
配合「展开 → 迁移」的投递顺序。**

**不改湖的路径布局。** §2 的 P4 推翻了「版本化前缀」的必要性——它买的是
「消费者可任意时刻插队迁移」，而我们**两侧都自己控制、可以排期**；
真正要的不是"多一条路径"，而是**"读者不可能静默读到没齐的湖"**，
那条用一个**表根封版标记**就能拿到，代价是零布局变更。

## 1. 问题：为什么会有 flag day

### 1.1 三层里只有最上面那层是注册制

| 层 | 谁声明 | 谁保证 | 现状 |
|---|---|---|---|
| 源（网关） | 无 | — | 靠人读文档 |
| **契约**（列集） | `contracts/*.json` | **无** | `check-data-models.mjs` 头注明写「`contracts/` **不在任何扫描面内**」⇒ **注释性文档** |
| 物理（湖） | 路径即 schema | 无 | 分区**无版本**；读者用**一条 glob 读整湖** |
| 语义（staging/marts） | `sources.yml` + `schema.yml` + `staging/*.sql` | 规则④ | 只与**源声明**双向对上，**不保证与契约对上** |
| **语义层（指标）** | `dbt/semantics/l1_metrics.yml` | 规则⑤/⑥ + `sync-data-semantics.mjs` **同步进平台库** | ✅ **已经是注册制** |

**缺口就在「列」这一层**。指标层早已是「声明 → 门禁 → 同步 → 下游知道有什么」，
把同一套往下一层铺，就是本设计。加一列现在要人手改 **5 处**
（契约 / `window` / `tick` / staging / lock），**漏改任一处没有门禁会拦**。

### 1.2 flag day 的三个成因

1. 湖的分区**不可变**（历史分区只能整份重写）；
2. 读者用**一条 glob 读整湖**（`system_book=*/**/*.parquet`）；
3. **同前缀混 schema 时，点名取新列的读者在旧分区上必挂**（§2 P3 实测）。

⇒ 「生产者写新列」与「消费者读新列」之间必须有一次跨越全湖的切换。
**但它不必是"同时"的**（§3.2）；真正危险的是切换**半途**且**无人知道**（§2 P4）。

## 2. 真机验证

构造（scratch 前缀 `lemeng/_caliber-probe/`，**未动生产湖**）：
`v_old` = 拷贝现网 64188/2026-10-02/hour=10 分区（24 列）；`v_new` = 同源 + 常量列 `order_total_money`（25 列）。

### 2.1 CLI 路径（容器内 `duckdb`）

| 探针 | 结果 |
|---|---|
| P1 旧点名（24 列）读 `v_old/**` | ✅ rc=0，`{"n":392}` |
| P2 旧点名读**混合** glob（v_old+v_new） | ✅ rc=0，`{"n":784}` —— **旧读者在过渡期不受影响** |
| P3 新点名（含 `order_total_money`）读 `v_old/**` | ❌ `Binder Error: Could not find key "order_total_money" in struct` —— **flag day 复现** |
| **P4** 新点名读**半写**的 `v_new/**`（只写 1/2 分区） | ⚠️ **rc=0，`{"n":392}`——静默给部分数据**（完整应 796） |
| P5 写齐后再读 | ✅ rc=0，`{"n":796}` |
| DuckDB 版本 / `error()` | **v1.5.5** / ✅ 有（`Invalid Input Error: BOOM`） |
| 读**不存在**的标记 | ✅ rc=1（404，**非静默**） |

### 2.2 pg_duckdb（**生产读路径**）

| 探针 | 结果 |
|---|---|
| 读**已存在**的封版标记 | ✅ `796|2` |
| 读**不存在**的标记 | ✅ `ERROR: HTTP Error: … 404 (Not Found)` —— **非静默** |
| `error('LAKE_UNSEALED: v3')` | ✅ `ERROR: … Invalid Input Error: LAKE_UNSEALED: v3` |

### 2.3 三条结论（第三条是推翻性的）

1. **病灶确认**：同前缀混 schema = `Could not find key`（P3）。且 P2 说明混合 glob 只在
   **首个文件列更少**时安全 —— 即 `/opt/lemeng-backfill.sh` 头注那条不变量，**风险是单向的**。
2. **旧读者在过渡期天然安全**（P1/P2）⇒ 「展开 → 迁移」的窗口成本本来就是 0。
3. ⚠️ **"多开一条版本路径"解决不了要害**：P4 证明**半写状态会被静默读成完整**。
   换成版本前缀只是把"混 schema"这个响亮失败换成了"读到一半"这个**静默错**。
   ⇒ 要害从来不是路径，是**读者无法判断湖齐没齐**。

## 3. 设计

### 3.1 四件套

**① 契约注册表（单一事实源）**
`contracts/*.json` 增 `schemaVersion`（整数）+ 列集，成为**参与机检**的注册物，并**生成**：
管线 `flatten` 投影 / staging 投影 / `sources.yml` 列。加一列 = 改契约一行 + 重新生成。

**② 三向双向门禁**
契约 ↔ 管线 ↔ staging 三个方向互相核对（照抄规则④ 已证明有效的做法：staging ↔ sources 双向）。
**漏改任一处 = CI 红**，不再靠人记得。

**③ 表级封版标记**
```
lemeng/retail_order_line/_SCHEMA/v<N>.parquet    ← 整表在该版本上写全之后才落
   内容：schema_version / column_fingerprint / partitions / rows_expected / sealed_at
```
**放在表根、不在 `system_book=*` 之下** ⇒ 不进任何读湖 glob，不污染数据面。
它是「**这套文件是齐的**」的唯一凭据（与投递程序 `.data-plane-revision` 同一思想：
**标记在 = 齐**）。

**④ 读侧 fail-closed 断言**
读者路径**不变**，但**必须带封版断言**：
```sql
SELECT ... FROM read_parquet('…/system_book=*/**/*.parquet') r,
                read_parquet('…/_SCHEMA/v<N>.parquet') s
```
- 未封版 ⇒ 读到标记**404 ⇒ 带名字地失败**（§2.2 已验证）；
- 要更可读就用 `error('LAKE_UNSEALED: v<N>')`（pg_duckdb 上已验证可用）。

### 3.2 于是 flag day 消失，靠的是**顺序**而不是**多一条路径**

```
展开(expand)  ：只上生产者（管线写新列）→ 回填历史 → 湖齐版 → **落封版标记**
迁移(migrate) ：再上消费者（staging/marts 引用新列 + 断言封版）
```
- 展开期：旧读者**不受影响**（§2 P2），dbt 跑旧模型，**零窗口**；
- 若有人**提前**上消费者：读到未封版 ⇒ **响亮报错**，而不是静默算错（§2 P4 的反面）；
- 顺序不再靠纪律——**③④ 把它变成了闸**（`/opt/lemeng-backfill.sh` 那条"最老那天最后"也就不必再写在注释里）。

### 3.3 注册表驱动回填

回填计划**从注册表算**（哪些分区在哪个版本、差集是什么），不再写死批次表；
顺序不变量做成**前置闸**（v2 那次已有雏形，泛化即可）。

## 4. 本次落地：`order_total_money` 是第一个用例

1. **拆投递**：#432 已合进 main，含「生产者（管线）」与「消费者（staging）」两部分。
   按本设计**分成两次生效**——生产者先上 + 回填 + 封版，消费者后上。
2. 回填：两账套共 **24 个营业日分区**（3120 13 天 09-23~10-05 / 64188 11 天 09-25~10-05），
   **3120/2026-09-23 最后**（顺序不变量）。
3. 封版 → 才让 staging 引用新列。
4. 之后 `recon-preagg` 换口径（#431）跑全店归零。

> ⚠️ **当前状态有时效性**：`stg_lemeng_retail_order_line.sql` 已在 main（#432，v0.68.0）
> 并引用 v3 的列；机器**尚未投递** ⇒ 现在一切正常，但**任何一次同步都会开始 flag day**。
> 本设计要解决的正是这一幕。

## 5. 方案对比（推荐已落到「中」）

| | flag day | 静默风险 | 代价 | 判定 |
|---|---|---|---|---|
| 轻（契约注册 + 生成 + 三向门禁） | 仍有（但漏改会被拦） | 无 | 小 | **是③的前置，必做** |
| **中（+ 表级封版 + 读侧断言 + 注册表驱动回填）** | **消失**（靠展开→迁移顺序，③④ 兜底） | 无 | 小 | ✅ **选它** |
| 重（版本化前缀 + 封版 + 断言） | 消失（消费者可任意插队） | 无 | 大：改路径布局、留"隐式 v2"遗留路径 | ✗ 不必要（两侧都我们控，可排期） |
| 旁挂（新事实放独立旁表） | 消失 | 无 | 中；只覆盖**可加性**事实 | ✗ 只解决一半问题 |

**为什么不选「重」**：它唯一多买到的是「消费者可任意时刻插队」——
而本项目**两侧投递都由我们控制，可以排期**（§3.2 已证展开期零窗口）。
为这点自由度去改湖的路径布局、并永久保留一条遗留路径，**不划算**。
若将来出现无法排期的消费者（24/7 多团队并发），或需要**原地改名/改类型**而不留旧列，
再升级到「重」——届时本设计的 ③④ 可直接复用。

## 6. 未覆盖 / 风险

- 本稿**未写任何代码**；`docs/architecture.md` 未动。
- **未验**：`_SCHEMA/*.parquet` 在大前缀（数千分区）下的落盘耗时（本次 24 分区不构成问题）。
- **未验**：封版标记与回填的**原子性**——回填中途失败会留下"未封版但部分已升级"的湖；
  这正是 ③④ 存在的理由（读者会响亮拒绝），但**回填自身的可重入与进度**要在 `/opt/lemeng-backfill.sh` 里表态。
- 契约改 `schemaVersion` 后，**旧的无版本读者**（若有第三方直接读 S3）不受保护——需在架构文档里写明读湖的**唯一合法姿势**。
- 本文**不是**正典；正典落 `docs/architecture.md`，本稿是提案。
