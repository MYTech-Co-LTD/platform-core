# 湖 schema 的注册机制：版本化前缀 + 封版标记 + 读侧断言（设计稿）

> 2026-10-05 ｜ 触发案例：`order_total_money` 补采（#430/#432）暴露的 flag day
> 状态：**待裁决**（架构先行：先经同意 → 更新 `docs/architecture.md` → 再写码）
> 真机验证：本节 §2 的探针在数据面机 `8281d598` 容器 `lemeng-console-64188` 上跑过，原始输出逐条抄录

## 0. 一句话

**加一列不该是一场"所有人同时换衣服"的舞蹈。** 把「契约」变成真正参与机检的注册物、
给湖的每个版本一个**可断言的封版标记**，下游就能**各自选时刻迁移**——而不是被一次原子切换绑在一起。

## 1. 问题：为什么会有 flag day

### 1.1 三层各自为政，只有中间那层是注册制

| 层 | 谁声明 | 谁保证 | 现状 |
|---|---|---|---|
| 源（网关） | 无 | — | 靠人读文档 |
| **契约**（列集） | `contracts/*.json` | **无** | `check-data-models.mjs` 头注明写「`duckle/` 与 `contracts/` **不在任何扫描面内**」⇒ **契约是注释性文档** |
| 物理（湖） | 路径即 schema | 无 | 分区是**无版本**的集合；读者用**一条 glob 读整湖** |
| 语义（staging/marts） | `sources.yml` + `schema.yml` + `staging/*.sql` | 规则④（staging ↔ sources **双向**） | 只保证与**源声明**对上，**不保证与契约对上** |
| **语义层（指标）** | `dbt/semantics/l1_metrics.yml` | 规则⑤/⑥ + `sync-data-semantics.mjs` **同步进平台库** | ✅ **这里已经是注册制** |

**缺口在中间**：指标层是注册制（声明 → 门禁 → 同步 → 下游据此知道有什么），
**但「列」这一层不是**。加一列要人手改 5 处（契约 / `window` / `tick` / staging / lock），
漏改任一处**没有门禁**会拦。

### 1.2 于是 flag day 不可避免

三个事实叠在一起：

1. 湖的分区是**不可变**的（历史分区只能整份重写）；
2. 读者用**一条 glob 读整湖**（`system_book=*/**/*.parquet`）；
3. **同一个前缀承载两个 schema 时，点名取新列的读者在旧分区上必挂**（§2 P3 实测）。

⇒ 「生产者写新列」与「消费者读新列」之间**必须有一次跨越全湖的原子切换**，
而生产者的投递（`data-plane.lock` 整套同步）与消费者的投递（同上）**是两个时刻**——中间那段就是 flag day。

### 1.3 今天这个 flag day 的具体现状

`/opt/lemeng-backfill.sh` 的判据正典已经识别了**风险方向**：

> glob 展开后**第一个文件的列集必须是其后每个文件列集的子集**；第一个恰是
> `system_book=3120/bizday=2026-09-23/hour=00/all.parquet` ⇒ 它一变，其后任何旧列文件都会让整湖
> `schema mismatch in glob` 整挂。

⇒ 目前的做法是把这条**纪律写在脚本头注里**，靠回填**顺序**（bizday 降序、最老那天最后）绕开。
**它是纪律不是闸**（脚本自己也这么写：「那条不变量不是引擎强制的，是本仓的纪律」）。

## 2. 真机验证（2026-10-05，scratch 前缀 `lemeng/_caliber-probe/`，未动生产湖）

构造：`v_old`（拷贝现网 64188/2026-10-02/hour=10 分区，24 列）+ `v_new`（同源 + 常量列 `order_total_money`，25 列）。

| 探针 | 命令要点 | 结果 |
|---|---|---|
| P1 | 旧点名（24 列）读 `v_old/**` | ✅ rc=0，`{"n":392}` |
| P2 | 旧点名读**混合** `…/_caliber-probe/**`（v_old+v_new 同一 glob） | ✅ rc=0，`{"n":784}` —— **旧读者在过渡期不受影响** |
| P3 | 新点名（含 `order_total_money`）读 `v_old/**` | ❌ rc=1 `Binder Error: Could not find key "order_total_money" in struct` —— **flag day 复现** |
| **P4** | 新点名读**半写**的 `v_new/**`（只写了 1/2 个分区） | ⚠️ **rc=0，`{"n":392}`** —— **静默给部分数据**（完整应 796） |
| P5 | 写齐后再读 `v_new/**` | ✅ rc=0，`{"n":796}` |
| P6 | 同读者比 `v_old`(392) vs `v_new`(796) | 确认 P4 少了整整一半 |
| 补 1 | `SELECT error('BOOM')` on **DuckDB v1.5.5** | ✅ rc=1 `Invalid Input Error: BOOM` ⇒ **可写带名字的 fail-closed** |
| 补 2 | 写/读 `v_new/_COMPLETE.parquet`（`rows_expected`/`partitions`/`sealed_at`） | ✅ 可写可读 |
| 补 3 | 读**不存在**的标记（`v_old/_COMPLETE.parquet`） | ✅ rc=1 `HTTP 404 Not Found` —— **非静默** |
| 补 4 | **fail-closed 读者**（标记内连接）：已封版→出数；未封版→报错 | ✅ 成立 |

### 结论（三条，第三条是推翻性的）

1. **病灶确认**：同前缀混版本 = `Could not find key`（P3）。这也解释了为什么"旧读者在过渡期没事"（P2）——
   混合 glob 只有在**第一个文件列更少**时才安全，风险是**单向**的。
2. **版本化前缀把病灶隔离**：v_old 与 v_new 各自内部同构，互不干扰（P1/P5）。
3. ⚠️ **但版本前缀单靠自己不够**：半写状态被**静默**读成完整（P4）。**这比现状更危险**——
   现状至少响亮地报 `column does not exist`。⇒ 必须配**封版标记 + 读侧断言**（补 1–4 已证可实现）。

## 3. 设计：三层注册物

```
网关能力 ─▶ 契约(列 + schemaVersion) ─▶ 湖(v<N>/ 前缀 + _SEALED) ─▶ staging/marts(声明所需版本) ─▶ 消费
              ▲ 单一事实源                 ▲ 写时封版                 ▲ fail-closed 断言              ▲ 查注册表
              └────────── 生成 ────────────┴────────── 生成 ──────────┴──────── 门禁三向核对 ─────────┘
```

### 3.1 契约层（注册表，单一事实源）

`contracts/*.json` 增：`schemaVersion`（整数）+ `layout` 里带版本段：

```
prefix:      lemeng/retail_order_line/v<N>
partitionBy: [system_book, bizday, hour]
sealedBy:    _SEALED.parquet      # 封版标记载体
```

并由契约**生成**（不再手抄）：管线 `flatten` 投影、staging 投影、`sources.yml` 列、lock 里的路径。
**门禁做三向双向核对**（照抄规则④ 已证明有效的做法）：契约 ↔ 管线 ↔ staging。

### 3.2 物理层（湖）

- 写侧**只写当前目标版本前缀**（不做双写）；
- 一个版本前缀**写全后**落 `_SEALED.parquet`（内容：`rows_expected` / `partitions` / `sealed_at` / `schemaVersion`）；
- **glob 顺序不变量在单版本前缀内自然消失**（同版本同构）——那条纪律可以删掉。

### 3.3 语义层（读侧）

- 读者路径带版本段，并**断言封版**：
  ```sql
  -- 未封版 ⇒ 带名字地失败，而不是静默给部分数据
  SELECT ... FROM read_parquet('<prefix>/v<N>/**/*.parquet') r,
                  read_parquet('<prefix>/v<N>/_SEALED.parquet') s
  WHERE s.schemaVersion = <N>
  ```
  （标记缺失 = 404，本身就是响亮的；要更可读就用 `error('LAKE_UNSEALED: v<N>')`，v1.5.5 已证可用。）
- `sources.yml` 声明**所需版本**；版本不符 = 装载期失败，不是告警。

### 3.4 回填

- 计划**从注册表算**（哪些分区在哪个版本、差集是什么），不再写死批次表；
- 回填 = 往**新前缀**写全 → 封版 → 读侧翻版本 → 删旧前缀。
- **旧消费者全程读旧前缀**（P2 已证不受影响）⇒ **没有 flag day**。

## 4. 迁移：本次 `order_total_money` 就是第一个用例

1. 新前缀 `lemeng/retail_order_line/v3/`（25 列）；**遗留的无版本段路径原地冻结，文档记作「v2(遗留)」**——
   不移动、不改写 ⇒ 零窗口。
2. 管线写 v3；回填两账套 24 个营业日分区（3120 13 天 / 64188 11 天）；写 `_SEALED`。
3. 读侧（staging/marts）翻到 v3；`#430/#432` 已进 main 的那一列**此时才真正被读到**。
4. 消费方（Metabase/模块）无感——它们读的是物化表。
5. 遗留路径在确认无读者后删除（独立动作，不阻塞）。

> ⚠️ 在这之前，**`stg_lemeng_retail_order_line.sql`（已在 main）引用 v3 的列**——
> 它必须与第 2 步的封版**同批或之后**生效。这正是当前需要处理的那次「顺序」，在新机制下会变成
> **读侧断言**：v3 未封版就报 `LAKE_UNSEALED`，而不是现在这样安静地写错。

## 5. 方案对比

| | 做法 | flag day | 静默风险 | 代价 |
|---|---|---|---|---|
| **轻** | 契约注册表 + 生成 + 三向门禁 | 仍有，但顺序/完整性由机器保证 | 无 | 小；不改湖布局 |
| **中** | 轻 + 湖级版本断言 + 注册表驱动回填 | 仍在，但从"记得住"变"机器挡" | 无 | 中 |
| **重** | **版本化前缀 + 封版标记 + 读侧断言** | **消失**（消费者各自选时刻） | **无**（需三件套齐全，见 §2.3） | 大：改 `layout`（架构变更）、迁移期两前缀并存 |
| 旁挂 | 新事实放**独立旁表**（如 `…_order_totals`），主表 schema 不变 | 消失 | 无 | 中；但只适用**可加性**事实，且建模碎片化、语义层要声明关系 |

**推荐「重」**：只有它能同时覆盖加列 / 改类型 / 改名（旁挂只覆盖加列），
且验证已证明**三件套齐全时没有静默面**。旁挂作为「只加一个可加性事实」时的轻量备选留档。
