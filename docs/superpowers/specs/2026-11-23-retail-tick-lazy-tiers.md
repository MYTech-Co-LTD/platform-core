# 零售 tick 页容量懒扩容（lazy tiers）设计 —— 2026-11-23

> issue #2713。前置实测：正典案例 53 + `docs/superpowers/plans/`（2026-11-23 会话，mock 三案 + 真机峰值窗 1,011 单逐单吻合）。
> 本文件是**形态正典**；判据数值以正典（`docs/data-platform-handbook.md`）与本文为准。

## 1. 问题

- 静态 12 页 × `page_size=200` 的**静默通过阈值 = 2,200 单/时**（p12 哨兵 `ctl.die`）。历史峰值 1,459（2026-09-24 19 点）曾击穿当时 8 页阈值 1,400（#197，连夜改码扩容）——「大促临时改代码」已经发生过一次。
- 引擎原生分页（`paginationType: page`）**对本网关不可用**：页号只拼 URL query，网关只读 body（案例 41 订正 / 案例 53）。
- 单纯加静态页（B 方案）线性烧 tick 时长与**网关调用额度**（空页也吃额度，案例 42② 额度可耗尽），且仍有上限。
- 同修：页节点只申报 10/~56 列 + 多页 `ctl.merge`，未申报列**逐页推断**翻类型即炸（案例 36/46 同族；2026-11-23 在本源实测复现）——生产 tick 潜伏同款风险。

## 2. 形态（定案）

子管线 `lemeng.retail_order_line.tick` v2（父管线 `lemeng.retail.tick.l1` **不动**；湖布局**不动**，仍 `hour=<H>/all.parquet` 单文件覆盖写）：

```
p1..p4 静态页 → c1..c4 投影(10 申报列) → m1 merge ──┬→ seed(空 part ×5: t2..t6) ─┬→ …串行排序…
                                                    │                            │
p4 视图 → t2list「p4 满 200 行?」→ fe2 → t2 子管线(5–8)  → part t2 ───────────────┤
            t3list「t2 的 p8 满?」→ fe3 → t3 子管线(9–16)  → part t3               │
            t4list「t3 的 p16 满?」→ fe4 → t4(17–32) → t5「p32 满?」→ t5(33–64) → t6(65–128)
            fuseSql「t6 的 p128 满?」→ fuse(ctl.die, 25,600 单/时)                  │
                                                                                    ↓
      combine(m1 ∪ read_parquet(t2..t6)) → flatten → gate → sink(minio) → receipt → cuT2…cuT6(逐个删除 part)
```

- **段界（2026-11-23 按实测小时分布下调：v1 固定 12 页，多数小时 7–11 页是空页白烧额度）**：t1 = p1–4（800/时）→ t2 = 5–8（1,600）→ t3 = 9–16（3,200）→ t4 = 17–32（6,400）→ t5 = 33–64（12,800）→ t6 = 65–128（25,600，p128 满 = die）。每段页数翻倍、逐级链式，常态只请求 4 页。
- **触发判据**：某段**末页满页（=200 行）**才拉下一段——不是「有行」（末页 1–199 行 = 数据到此为止，零浪费）。累积窗单调性保证「满过的页永远满」，无跨 tick 误判。
- **常态开销 = 4 个页请求**（v1 是 12 个）+ 5 个 seed 本地小文件写；只在溢出时加段。每段一个 foreach 子 run（1 item），子 run 开销 ~0.5s。
- **五个新子管线文件**（tier2..tier6：静态页 + 投影 + merge + part 写出），页数在文件内写死（manifest 快车道表达不了 foreach 懒扩容，§1.7 登记）。
- **part 语义（2026-11-23 容器实测定形）**：`/workspace/tmp/retail-tier/t<N>-<bizday>-h<hour>.parquet`，带 `page` 列。
  - **必须用 parquet，不能用 CSV**：json 列（`branch` / `pos_order_details`）经 `CAST … AS VARCHAR` 出来的是 dict repr（单引号、非合法 JSON），下游 `flatten` 的 `from_json` 与 `qa.contract` 直接炸「Malformed JSON」；parquet 保类型，`read_parquet` 无需 columns 声明（顺带消灭「18 位 order_no 被嗅探成整数丢前导零」这类风险）。
  - **投影节点只选列、不 CAST**（`SELECT <申报 10 列> FROM input`）：作用是切断 merge 对未申报列的逐页推断，不是改类型。
  - seed 每 tick 先写 0 行 parquet（保留 schema），保证读侧不因文件缺席报错并清掉上轮残留；实测 0 行 parquet 正常落盘、`read_parquet` 读到 0 行不报错。
- **checkpoint 保持 false**（复用键无上游内容指纹，沿用现注记）。

## 4. 风险与边界

- **12 页仍非同一快照**（页间漂移 = 既有已知残余风险，spec 2026-09-24 已记）；懒扩容把漂移面从 12 页扩到「实际页数」，自愈机制不变（整分区覆盖写 + staging 自然键唯一断言）。
- **溢出小时的 tick 变长**：47 页 ≈ 33s/窗（0.7s/页串行）；95 页 ≈ 67s/窗——均在 10 分钟节拍内。控制台串行执行器期间独占，与现状同量级。
- **控制台一次只跑一条管线（运维事实）**：`lemeng.dim.item.l0` 每小时 :02 起跑约 10 分钟，占住串行执行器 ⇒ 同一时段的手动 run / 探针会长时间排队（2026-11-23 实测排队 4+ 分钟且无日志）。验收与回填一律错开该窗口；「run 无日志且 state=running」先判排队再判故障。
- **429**：段内页请求串行（concurrency=1）+ 每段末才决定下一段，请求速率与现状同族；额度耗尽（42②）仍靠人充值，非本设计范围。
- **失败语义**：任一段子 run 失败 ⇒ 整窗 run 红、不写湖（continueOnFailure=false）——与今天的哨兵语义一致，下轮 tick 自然重试。
- **不做**（另行立项）：day.json 96 页日窗同形态改造；dim.item.l0 提速/错峰；tick 双窗并发（vendor 并发 ≤3 需独立验证）。
