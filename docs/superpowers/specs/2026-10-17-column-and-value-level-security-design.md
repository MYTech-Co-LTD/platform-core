# 列级与值级权限（CLS + 动态脱敏）—— 设计（spec）

> 日期 2026-10-17 · issue #764 · 状态：**待评审**（P1 列级 / P2 值级；P3 只登记不设计）
> 本文 §2 每条事实都标了**文件:行**；凡标「未验」的一律**不许当已知**（本仓规矩：无案例不立标准）。

## §0 问题

平台的划线依据今天只有**一处**——`modules/data/domain/authz.ts` 的 org 谓词 + scope 矩阵
（`docs/architecture.md` §2.2 末注：「**这条通路唯一的划线依据**」）。但它只划到两档：

| 已有 | 在哪 | 划什么 |
|---|---|---|
| 路由级 | `modules/data/manifest.yaml` 的 `api.internal[].scope` | 这个端点你能不能打 |
| **指标级** | `metric.requiredScope`（`authz.ts:20-38`） | 这个**指标**你能不能看到 |

**列级与值级是空的**，于是两个真实需求今天无解：

| # | 情形 | 例子 |
|---|---|---|
| **① 列级** | 同一指标，不同的人**看得到不同的列** | 店长看得到「销售额」，看不到「成本 / 毛利」 |
| **② 值级** | 同一指标同一列，不同的人看到**不同的精度** | 老板看「¥1,234,567.89」，店长看「约 ¥123 万」 |

⚠️ **不能靠「从词表里藏起来」来解决**——架构已明确：

> 「**词表裁剪**是一种**能力**，**不是闸**——它给 AI 一份理解口径用的词表，**不构成「不在词表即不可见」**。」
> —— `docs/architecture.md:194-195`

`visibleMetrics()`（`authz.ts:120-128`）只是过滤器，绕过它（直打 `/query`、MCP、报表）仍然拿得到数。
**真要裁剪，只能落在查询网关组装的 SQL 投影上。**

## §1 目标与判据

**目标**：在**既有唯一划线依据**上**加一维**（列 / 值），**不新增权限组件、不新增第二划线依据**。

| 段 | 判据（可机器判） |
|---|---|
| **列级** | 不满足某指标 `requiredScope`（如新码 `data:cost`）的人打 `/query`，回包 `columns` 里**不含**成本/毛利列，且**SQL 里也不含**（不是前端隐藏） |
| **值级** | 有 `data:query` 无 `data:precise` 的人查同一个指标，**明细行与 `total` 都是掩码后的值**，且 `total` == 展示行之和 |
| **不可绕** | 换过滤条件 / 换时间窗 / 换分组 / 走 MCP / 走报表，**掩码恒定**，差分不出精确值 |
| **默认严档** | 指标**不声明** `mask` 而读了带 `sensitivity` 的列 ⇒ 无特权者拿到 **NULL**（不是原值、不是"忘了就漏"） |
| **血缘单调** | 给源列加限制后，**读它的指标**若未同步收窄 ⇒ CI **红**（不是告警） |

## §2 现状取证

### 2.1 执法点在哪（已验）

**唯一执法点是 `authorize()`**（`modules/data/domain/authz.ts`）——它组装 SQL，所有查询面都经过它：

```
routes/query.ts:31  POST /query ─┐
routes/mcp.ts:69    MCP         ├─▶ runQuery()  ──▶ authorize() ──▶ authz.plan.sql
domain/agent-loop.ts:158  chat  ┘   query-service.ts:200   authz.ts:255-271
报表渲染 ──(HTTP)──▶ /query ────────┘        ← ⚠️ 报表**不是**直接调 runQuery，是打 HTTP
```

**「报表打 HTTP」这条有明文纪律撑腰**（2026-10-17 核实，不是我从调用图猜的）——
`modules/data/console/reports/SpecView.tsx:200` 逐面板 `apiSend('/query', 'POST', { metricId, args })`，
其头顶注释（`:10-12`）写着：

> **通路纪律**（spec §5 / 计划 6 裁决 5）：面板数据走既有 `POST /query`，**一个面板一次**——
> 语义裁剪、授权、按调用者身份注入主体值、逐查询落 `data.query_audit` 全部复用；
> **不造「整报表数据」端点（那会把 N 次授权/审计合并成一次）**。

⇒ 这条**既支持本设计、也约束本设计**：报表面**天然继承**列级/值级执法（无需另做），
但也**不许**为了它去造一个合并端点——那会把 N 次授权/审计合并成一次，正是这条纪律禁止的。

- `runQuery` 自己**不拼 SQL**，执行的是 `authz.plan.sql`（`query-service.ts:279`）。
- SQL 形状（`authz.ts:255-271`）：

```ts
const whereAndGroup = `${metric.selectSql} WHERE ${metric.subjectColumn} = ${sqlQuote(subject)}`
  + filters.join('') + (metric.groupBy ? ` GROUP BY ${metric.groupBy}` : '')
const sql = wantTotal
  ? `SELECT sum(value) AS total FROM ( ${whereAndGroup} ) t`
  : `${whereAndGroup}${detailOrder} LIMIT ${MAX_QUERY_ROWS}`
```

- `metric.selectSql` 由**编译期**产出：L1 走 `buildSelectSql(expression, grain, relation)`
  （`scripts/sync-data-semantics.mjs:228-231`），L2 走 `compileL2`（`semantic-compiler.ts:641`）。
  形态：`select <expression> as value[, <dims>] from <relation>`。
- 回包 `QueryOk`（`query-service.ts:156-187`）：`status/subject/metricId/columns/rows/truncated/total?/data_as_of?/watermark?/freshness_status?/freshness_line?`。

**⇒ 加一维授权，只改 `authorize()` 一处；四个消费面（`/query`、MCP、chat、报表）自动全覆盖。**

### 2.2 两个已确认的缺口

1. **契约列没有授权位。** 全仓 grep `masking|列级权限|sensitivity` **零命中**（只在无关的
   「secret 脱敏」语境出现过）。契约列的 schema 是 `contracts/common/_schema.schema.json` 的
   `$defs.column`（`:157-217`），字段只有 `name/type/nullable/precision/scale/description/expr`。

   ⚠️ **订正（2026-10-17 写计划时查证）**：初稿在此写「`additionalProperties: false` ⇒ 加字段必须先改
   schema（这本身就是一道真闸）」——**那是错的**。`contracts/README.md` §4.3 自陈：
   **「校验器：当前不存在（这是本任务最大的一条欠账）」**，并明确「§4.2 那六条跨字段规则**仍不在任何
   CI 里**」。⇒ **元 schema 是纯文档，没有任何东西拿它校验契约。**
   ⇒ 直接后果：**闭集必须在 `scripts/check-data-contract.mjs` 里实现**（那是唯一进 CI 的契约检查），
   否则打错的 `sensitivity: "coast"` 会被血缘门当成「**不敏感**」而**静默放行**——正是本设计最怕的漏。
2. **报表面有一条已确认的旁路。** `modules/data/routes/reports.ts:350-352` 的注释自陈：

   > 「规格里的 metricId 可见性**另由 /query 的语义裁剪兜底**」

   即：发布报表时**不校验面板指标的 scope**。今天靠 `/query` 兜底还成立；一旦引入列级/值级，
   这条兜底就**不够**了（报表是**冻结的规格**，不是实时查询）⇒ P1 必须补发布门（§4.4）。

## §3 架构

### 3.1 三层声明 + 一个执法点

```
[源列]  contracts/*.json   columns[].sensitivity   ← 声明「这一列敏感」，不直接执法
   │                                                    只作 §4.3 血缘门的输入
   │  血缘（U1：今天靠申报，非机械）
   ▼
[指标]  dbt YAML / L2 定义 ──编译期──▶ data.metrics ──▶ MetricDef
        requiredScope（已有，= 整指标隐藏）
        mask          （新增，= 值级；**按列解析**，R10/§5.3.1）
   │
   ▼
[执法]  authorize()  ← 唯一执法点；按 requester 展开投影
   │
   ▼
[报表]  report_specs ── 发布门（新增）+ /query 兜底（已有）
```

**三层各自管什么**（别混）：

| 层 | 声明在哪 | 语义 | 谁来执法 |
|---|---|---|---|
| **源列** | `contracts/*.json` | 「这一列敏感」 | **不直接执法**——它从不被直接返回给用户，只喂指标表达式 |
| **指标** | dbt YAML → `data.metrics` | 隐藏（`requiredScope`）/ 脱敏（`mask`） | `authorize()` |
| **报表** | `report_specs` | 发布门 | `PUT /reports/:id` + `/query` |

> **为什么源列不直接执法**：查询面返回的是 `value` + dims（`QueryOk.columns`），**契约列从不出现在回包里**。
> 所以「隐藏成本价」在问数语境里 = **隐藏读它的指标**，不是隐藏那一列本身。

> 🔴 **`mask` 的声明点是「指标 YAML」，但它的语义单位是「列」**（R10，2026-10-17 裁决）。
> 一条 `mask` 声明的是「**这个列**在任何人读它时都要被掩」——指标 YAML 只是**记录点**。
> ⇒ 同一个列被另一条指标读到，同样被掩；L2 因为 `selectSql` **保留源列引用**（§5.3.1 实测）
> 而**自动**被覆盖。这条是 P2 的解析地基，**别按「掩码是某条指标的属性」去读 §5**。

### 3.2 三条不变量

1. **执法点唯一。** 裁剪与脱敏**只**发生在 `authorize()` 组装的 SQL 里。
   前端、词表、报表渲染、MCP 一律**不承担安全职责**（前端脱敏 = 没脱敏）。
2. **掩码先于聚合**（对可下推的 kind）。`sum(round(x,-1000))`，**不是** `round(sum(x),-1000)`。
   后者可被差分攻击逼近精确值；前者用户**最多**看到掩码允许的值，与查询模式无关。
   不可下推的 kind（`bucket`）必须显式声明其**防护强度 = 桶宽**，且**不得附 `total`**（§5.1）。
3. **血缘单调。** `policy(指标) ⊇ ∪ policy(该指标读到的源列)`。
   给源列加限制而读它的指标没收窄 ⇒ **CI 红**。违反的表现是隐蔽泄漏：
   藏了 `item_cost_price`，但「毛利率」照旧能算出来。

### 3.3 射程边界（**必须写在 spec 里，不许含糊**）

本机制**只覆盖 `modules/data` 这条腿**（`/query`、MCP、chat、报表经 HTTP 打 `/query`）。
**直读面不在射程内**：Metabase 直连 pg_duckdb、AI 直读数据面湖，**不经过 `authorize()`**
（架构 §2.2 末注已接受此形态，合规判据是「受授权面约束 + 入审计」）。

⇒ 直读面的列级/值级要落到**数据面自己的授权**（pg_duckdb 的 USER MAPPING / dbt view 列裁剪），
那是**另一条腿、另一个 spec**。**本 spec 不得声称「全平台列级权限已解决」。**

## §4 P1：列级（隐藏）

### 4.1 契约列加 `sensitivity`

`contracts/common/_schema.schema.json` 的 `$defs.column` 增**可选**字段（`additionalProperties:false` ⇒ 必须同改 schema）：

```jsonc
"sensitivity": {
  "description": "敏感标记。只作血缘门（§4.3）的输入；不改变本列的落盘与投影。",
  "enum": ["cost", "pii", "none"]      // 封闭词表，加值 = 改常量 + 改 schema + 改门禁 + 走 PR
}
```

⚠️ **光改 schema 不生效**（元 schema 无校验器，见 §2.2 订正）——闭集必须**同时**写进
`scripts/check-data-contract.mjs` 的校验规则，那里才是进 CI 的那道闸。**两处一起改，缺一处 = 打错的
标记被当「不敏感」静默放行。**

**为什么是标记而不是策略**：源列不直接执法（§3.1），所以这一层只需要回答「敏感吗、哪一类」。
真正的策略（谁能看、看多精确）在**指标层**——那里才有 requester。

#### 4.1.1 默认档：**打了标记就自动套最严**（R1 已裁决，2026-10-17）

**裁决**：指标**不声明** `mask` 时，**按源列 `sensitivity` 自动套默认掩码**（fail-closed），
不采用「默认原值」。误伤由租户管理员改（§5.6）。

> ⚠️ **触发条件的措辞按 R10 收严**：默认档是**兜底档**，它的准确触发条件是
> 「**本指标一条列键声明都没命中**（§5.2 ①）」，**不是**「本指标的 YAML 里没有 `mask` 字段」——
> 一条声明**别的**指标写的、但列出现在本指标 `selectSql` 里，① 就已命中 ⇒ **声明赢、默认档不叠**。
> 解析顺序的唯一正文在 **§5.2**（①/②/③），别在别处重述。

**默认值 = `nullify`（置 NULL），不是某个取整步长。** 两个理由：

1. **`nullify` 不需要编造任何数字**。默认 `round:1000` 得先回答「为什么是 1000」——本仓规矩是
   **无案例不立标准**，凭空定一个平台级步长正是「编标准」。
2. **它响亮，取整不响亮**。取整出的数看着像真数，没人会察觉「这个数被抹了精度」，
   于是全租户拿着略错的数做决策而无人投诉；NULL 会立刻被看见、被报、被修。
   **静默的错比响亮的缺更坏。**

**中间档（`round` / `bucket`）必须显式声明**，走 PR 改 dbt YAML。⚠️ **因此它是「非自助」的**——
这是本设计**有意**的取舍（§5.6 写明）。

> ⚠️ **`sensitivity` 是新的必答题，不是免费标签**：给一个已被指标读的列打标记 = **当场改变那些指标的
> 行为**（对无特权者变 NULL）。⇒ 见 §8 的上线顺序硬约束。

**默认档的豁免码 = `data:precise`（专用码；R8 已裁决，2026-10-17）。**

本节初稿只写了「默认套最严」，**没写谁不受默认档约束**——这个洞必须堵：不写死 ⇒ 要么无人可豁免
（全租户黑屏，§7 R6），要么每处各发明一个码。**裁决：一个平台级专用码 `data:precise`，覆盖全部默认档**
（与 §5.5 第三档一致）。它与指标自带的 `grantedBy` 的关系在 **§5.2 的「豁免码解析」**里写死。

两个候选（A 已选）：

| | **A. 专用码 `data:precise`（已选）** | B. 复用该指标的 `requiredScope` |
|---|---|---|
| 语义 | 「能不能看精确值」与「能不能看这条指标」是**两个正交维度**，分开表达 | 把两个正交维度**压成一维** |
| 想只收窄精确值时 | 只动码的授予面，**指标可见性不变** | 只能连**指标可见性**一起收窄 ⇒ **永久语义塌陷**，收不回来 |
| 代价 | 拿到它 = 该租户**全部**敏感指标都能看精确值 | —— |

**已知代价写下来，别当没有**：`data:precise` 是租户内的**万能钥匙**（一次授权覆盖所有敏感指标）。
**未来若要按敏感级别分档**（成本价 / 手机号各一档），需要细分码（如 `data:precise:cost`）并让
`mask[]` 能按级别选码——那时是**新增**（`data:precise` 继续表示「全部」），**不是改语义**。
⇒ 今天不预做（无案例不立标准）；**但 `manifest.yaml` 那行注释要留一句**，免得后来者把
「一码走天下」当成终态。

### 4.2 指标层：`requiredScope` 已有，补**报表发布门**

指标级隐藏**已经存在**（`metric.requiredScope`，`authz.ts:210-212` 的 `metric_not_authorized`），
P1 **不改它**。要补的是报表面那条旁路（§2.2 第 2 条）：

**发布门（新增，`PUT /reports/:id`）**：报表 `requiredScope` 不再由调用者随手给，
改为**从面板指标推导**，保证「**报表可见 ⇒ 每个面板的指标都可见**」。

⚠️ **订正（2026-10-17 写计划时验算）**：本节初稿写的是「取 `max(面板 scope)`」——**`max` 无定义**。
scope 是**不透明字符串**，这套模型里**没有 scope 层级**（`hasScope` 就是「集合里有没有这个码」），
所以 `hasScope(A) ⇒ hasScope(B)` **当且仅当 `A == B`**。⇒ 正确规则是按**集合**判，不是按大小：

| 面板指标里**非 null** 的 `requiredScope` 集合 | 发布结果 |
|---|---|
| 空集（都无限制） | 报表 `requiredScope = null`（与今天一致） |
| **单元素** `{C}` | 报表 `requiredScope = C` |
| **多元素** `{C1, C2, …}` | **拒绝发布**，错误信息**点名**是哪些指标、哪些码——单值列**表达不了**「这些码都要有」 |

**为什么多元素是拒绝而不是挑一个**：挑任一个都会放行「只有 C1 没有 C2」的人，
而他的 C2 面板 `/query` 会 403 ⇒ **报表看起来正常、点进去炸**。宁可发布时响亮地失败。

**为什么不是「拒绝一切有 scope 的面板」**：那会让人「先发空报表再补面板」，把门绕过去。
上面这张表**只在真正表达不了时**才拒绝。

`/query` 兜底**保留**（双保险）。

### 4.3 血缘门（**只查单调性，完整性不进第一档**）

| 查什么 | 怎么查 | 档位 |
|---|---|---|
| **单调性** | 指标在 **dbt YAML**（与 `expression` 同处）声明 `reads: ["<contract 列全名>", …]`；CI 检查 `policy(指标) ⊇ ∪ policy(声明的源列)` | **第一档（CI 红）** |
| **完整性**（声明是否漏了） | 需要 contract → staging → marts 的列级血缘（U1/U2），**仓内不存在** | **第二档（仅评审）**，标注为**未验** |

⚠️ **诚实标注这道门的弱点**：它**只**拦「加了限制却忘了同步指标」，**拦不住**「故意/无意漏申报」。
完整性要机械化，得先有 dbt 模型级血缘（U2）——**那需要真实案例驱动，本 spec 不预先建**。

#### 4.4.1 `masking` 的三态语义（R9 已裁决，2026-10-17）

本列是**可空 JSONB**，取值有三种**原子形态**（互斥，下表列全）；**它们的并**（混合形）也存在——
见下表后的「混合形」段。（`019_query_audit_masking.sql` 的头注与
`query-service.ts` 的 `audit()` 闭包都按这张表写）：

| 库里存的值 | 含义 |
|---|---|
| `NULL` | 本次查询**没有任何列声明掩码**（无从掩起） |
| `{"net_sales": "round:1000"}` | 有列声明掩码，且**掩码生效**（值 → 记号） |
| `{"__exempted__": ["net_sales"]}` | 有列声明掩码，但查询者**持豁免码** ⇒ **未掩**（他看的是原值） |

**三种形态的并也存在（混合形）**：一个指标带两个掩码列、两条声明的 `grantedBy` 不同 ⇒ 一列被掩、
另一列被豁免 ⇒ 审计 JSON **同时带两个键** `{列:记号, "__exempted__":[列]}`。上面三态是**发生的形态**，
混合形是它们的**并**——落点实现（`maskingAuditOf`）按「并」写，别按「三选一」写。

> ⚠️ **响应面 `masking` 字段（契约 `Record<string,string>`）不能复用审计值**——它装不下 `__exempted__`。
> 两者必须由 `query-service.ts` 从同一份 `authz.plan` 在一处派生（防「各写一遍 ⇒ 不同尺」）。

**为什么第三态必须显式记**：没有它，`NULL` 就把「**豁免用户看过原值**」与「**根本没声明掩码**」
合并成同一个值——而「这一列是唯一凭据」要回答的恰恰是前者，一合并就答不上。

⇒ **判据不是「查询时带了什么码」，而是「这次掩码到底有没有生效」。**
「带了码」≠「掩码被豁免了」（码可能不匹配这条 mask 的 `grantedBy`，见 §5.2），
拿前者当后者是**静默的错**。

**落点三处口径一致**：迁移 `019_query_audit_masking.sql` 头注、`query-service.ts` 的 `audit()`
写入点、消费面 `deploy/openclaw/data-query-plugin/skills/data-query/SKILL.md` 文案。

⚠️ **先签语义再改代码**：三态一定，`NULL` 的含义就变了。**今天改是安全的**——全仓 0 条 `mask:`
声明（§2 取证）⇒ 不存在「持豁免码看过原值却记成 NULL」的存量行。但**顺序不能反**：先把语义
落进 spec 与头注，再动代码；否则代码改了、口径没改，两处各说各话。

## §5 P2：值级（脱敏）

### 5.1 mask 词表与**可下推性**（本 spec 最容易做错的一处）

| kind | 语义 | 能下推进聚合内部？ | 说明 |
|---|---|---|---|
| `nullify` | 置 NULL | ✅ 等价 | 明细与合计都为 null，顺序无关 |
| `round` | 按步长取整（`step: 1000` ⇒ 千元） | ✅ **必须**下推 | 下推后 `total` == 展示行之和，且差分不出精确值 |
| `bucket` | 落区间（`edges: [...]` ⇒ 「50–100 万」） | ❌ **不可**（区间标签不能求和） | 只能作用于**输出值**；防护强度 **= 桶宽**，不是「安全」 |

**`bucket` 的两条附加约束**（不做就会自相矛盾）：

1. **不得附 `total`**：`bucket(sum)` ≠ `sum(bucket)`，两者同时出现会直接暴露精度差。
   ⇒ `bucket` 生效时该次查询视同 `totalable = false`（与 `MetricDef.totalable` 同语义，`authz.ts:20-38`）。
2. **必须标注防护强度**：回包 `masking` 里写 `"bucket:[500000,1000000]"`，让调用方知道这是**有界**而非**安全**。

**能选、不能扩**：加 kind = 改常量 + 加展开分支 + 加测试，走 PR（同 `CHART_TYPES` 纪律）。

### 5.2 声明链（四处，缺一处静默不生效）

```
dbt/semantics/l1_metrics.yml        mask: [{ column, kind, step|edges, grantedBy }]
        │  scripts/sync-data-semantics.mjs   ← 今天这里硬编码 requiredScope: null（:385）

data.metrics                        新增列 mask_spec jsonb（迁移，幂等）

        │  authorize()  运行期展开

```

**L2 不声明**（R10，2026-10-17 裁决）：掩码的解析单位是**列**、不是指标行（§5.3.1）⇒ L2 只要它的
`selectSql` 里出现同一个列引用，就**自动**被同一条声明覆盖，**不需要**在 L2 定义里再声明一次；
按「同一列只许一处声明」门禁（§4.3.1），**也不许**（重复声明 ⇒ CI 红）。
⇒ `data.metrics` 里 L2 行的 `mask_spec` 恒 `null` **不再是洞**——旧文把它当绕过口，
**根因是解析单位错了**（实测订正见 §5.3.1）。

> 上面这张链路的**存储路径没变**（声明仍从 dbt YAML 经 `sync-data-semantics.mjs` 落进 `mask_spec`）；
> 变的只是**运行期怎么把它取出来**：按**列**取，不按**行**取。

**`grantedBy` 是新增权限码**（写进 `modules/data/manifest.yaml` 的 `permissions[]`，
由装载器按各租户 org 逐个 upsert——既有机制，不新增基建）。语义：

> **持有 `grantedBy` ⇒ 看原值；否则套 mask。** 与 `requiredScope` 的「默认拒绝」**方向相反**——
> 这是 masking 与 hiding 的本质区别，别把两个字段合成一个。

**解析顺序（写死，别让两处各有一套默认）**——⚠️ **单位是「列」，不是「指标行」**（R10，§5.3.1）：

```
① 列键声明（按列，全局）→ 本次 selectSql 里出现的每个列，取「已声明给它」的 mask；命中即掩
② 默认档（按指标兜底）
   → 本指标**一条列键声明都没命中**，且**本指标的 `reads` 申报里含 `sensitivity !== 'none'` 的源列**。
   ⇒ 整值 nullify（§4.1.1）
③ 都没有                → 无掩码
```

> ⚠️ **② 的触发条件为什么这么写（机械可判）**：`reads` 是**湖契约列全名**、`selectSql` 是 **mart 列引用**，
> 两者**不同命名空间、无机械映射**；「`selectSql` 读了带 sensitivity 的列」在仓内**不可判**
> （那需要 contract → staging → marts 的列级血缘，仓内不存在，见 §2.3 U1/U2）。⇒ ② 只按 `reads` 申报判。

> **① 与 ② 的关系（别读反）**：① 是**全局按列**查表——声明取自**全部**指标行，不只本行；
> ② 只在本行**一条都没命中**时兜底 ⇒ 声明了列键 mask 的指标**不会**再叠默认档（**声明赢，掩码不叠**），
> 而**读了同一个列的别的指标**（含 L2）**同样**被 ① 命中 ⇒ **这正是 #820 的修法**（R10）。
> ② 仍是**指标级**的（整值属于「值」这个概念，不属于任何列）⇒ 默认档**不**按列跨指标传播
> ⇒ **L2 不继承**（⚠️ 订正旧文「默认档**天然覆盖 L2**」的说法，见 §7 R12）：默认档是**整值 / 指标级**的，
> 不按列传播；真正的兜底是 `L2_BASE_MASKED` 写侧守卫。

**豁免码的解析（同一张表，别另起一处默认）**：

```
mask 元素声明了 grantedBy    → 用声明的那个码
默认档（指标未声明 mask）     → 用 data:precise（§4.1.1，R8）
```

> `data:precise` 是**平台级**码，它豁免的是**默认档**；声明了 `grantedBy` 的 mask 由**它自己的码**
> 豁免 ⇒ 「某条指标要比平台默认更严，连持 `data:precise` 的人也掩」是**可表达的**。
> ⚠️ 这条关系是**本节写死的默认**，不是某处实现细节——将来若翻转成「平台码总是放行」，
> 那是**语义变更**，走 spec 修订，别在实现里悄悄改。

**`mask` 元素的解析规则**（唯一实现 = `scripts/sync-data-semantics.mjs` 的 `masksOf`。下面两条是
2026-10-17 T1 的**计划外语义**，在此**回签**——此前只落在实现里，spec 不写就会长期各说各话）：

- **`column` 缺省（字段缺席）≡ `column: null`**（`masksOf` 的 `m.column ?? null`）——即**整值掩码**
  （把 `… as value` 的表达式整个换成 typed NULL，§4.1.1 默认档的形态）。两者是**同一个语义**，
  不是「未声明掩码」；「未声明掩码」只由**整个 `mask` 字段**缺席 / 为 `null` 表达（`masksOf` 回 `null`）。
- **`kind: 'nullify'` 会剥掉 `step`**：`step` 只在 `round` 下有语义，物化时不写进 `mask_spec`
  ——免得库里的声明带着一个没人读的键，让对账者误以为它在生效。

> ⚠️ **手写**声明里 `column` 缺席或为 `null` ⇒ **拒**（`maskItemError`）。整值形态**只由默认档合成**
> （`applyDefaultMaskTier` 不经 `maskItemError`）。读取侧仍按「缺席 ≡ null」解释**库内既有行**。

其余校验（`kind ∈ MASK_KINDS`；`round` ⇒ `step` 是正整数；
`column` 非 null ⇒ 必须逐字出现在该指标的 `selectSql` 里，且**不是**维度/grain 列、**不是**固定别名位
`value`）见 `masksOf` 与 `maskItemError` 的实现与头注。

### 5.3 运行期展开：**`selectSql` 存原值，运行期定点替换**

> 🔴 **订正（2026-10-17 写 P2 计划前实测）**：本节初稿的方案（**编译期占位符骨架存库**）**被推翻**。
>
> 实测两条：
> 1. **`${}` 那套与本设计无关**——数据面代码**不认** `${ENV:…}` / `${datetime}`（grep 零命中），
>    那是 **duckle 管线属性**与**契约 `expr`** 的层 ⇒ 「占位符语法冲突」这个担心**不成立**。
> 2. **但占位符绝不能进 `selectSql`**。它有**两个真消费者**会把里面的表达式当 SQL 用：
>    `authz.ts:256` 直接把它拼进最终 SQL；`semantic-compiler.ts` 的 `parseL1Select`
>    用 `L1_SELECT_RE`（`:178`）把表达式抽出来喂 **L2 编译**。占位符会**原样进 L2 产物**
>    ⇒ 一条语法错的 SQL，且要到某个租户查那个 L2 时才炸。
>
> ⇒ **改为：`selectSql` 一个字都不动，掩码在运行期做「列引用定点替换」。**

**做法（订正后）**：

```
库里存的 selectSql（原值，不变）：   select sum(fct_retail_sale.net_amount) as value, … from …
指标声明的 mask：                   { column: "fct_retail_sale.net_amount", kind: "round", step: 1000, grantedBy: "data:precise" }

运行期 authorize()：
  ⚠️ 先按【列】解析出本次要用的掩码集（§5.2 ①/②，§5.3.1）——
     不是取「本行 mask_spec」，而是取「本次 selectSql 里出现的列，已声明给它们的 mask 的并集」
  有 grantedBy → 原样
  无 grantedBy → selectSql.replace(/\b<转义后的 column>\b/g, maskedExpr(column))
               → select sum(round(fct_retail_sale.net_amount, -1000)) as value, … from …
```

> 🔴 **「掩码集从哪来」是本节的要害**：旧文默认「取本行的 `mask_spec`」，那正是 #820 的洞
> （L2 行的 `mask_spec` 恒 `null` ⇒ 永不掩）。**按列解析是 R10 的裁决**，理由与边界见 §5.3.1。
> ⇒ **凡本节后续提到「指标声明的 mask」，一律读作「按列解析出来的掩码集」**，别读回「本行的字段」。

**为什么定点替换天然满足「掩码先于聚合」**：替换的是**列引用本身**，而列引用在表达式里
必然位于聚合函数**内部**（`sum(<列>)`）⇒ 展开后就是 `sum(round(<列>, -n))`。**顺序不可能写错**，
因为根本不存在「先聚合再掩码」的表达形式。

⚠️ **必须用词边界**（`\b` + 转义 `column` 里的 `\.`）：`cost` 不能命中 `cost_money`、`total_cost`。
`_` 是词字符 ⇒ `\bcost\b` 不会命中 `cost_money`（正是想要的）。

**为什么这么做**（三个理由，都是硬的）：

1. **天然满足不变量 2**：替换的是列引用，展开后必然在聚合函数**内部** ⇒ 顺序不可能写错。
2. **零侵入**：`selectSql` 保持原值 ⇒ `parseL1Select` / L2 编译 / `authz` 拼接**全部不受影响**；
   也不需要为「骨架」多加一列。
3. **编译期可机械校验**：`mask.column` 必须**逐字出现在**「**声明它的那条指标**」的 `selectSql` 里，
   否则编译期报错——拼错列名不会变成静默失效。
   > ⚠️ 措辞按 R10 收严：基准是**声明者**的 `selectSql`（证明列名真实、拼写正确）；
   > **运行期**它会作用到**所有**读到该列的指标上——包括**没**声明它的那些（L2 就是这类）。
   > 两件事别混：「声明时校验谁」≠「运行期作用到谁」。

#### 5.3.1 解析单位改「列」——L2 为什么会被漏，以及怎么修（R10 已裁决，2026-10-17）

> 🔴 **订正（2026-10-17 裁决 R10 前实测）**：本节初稿写的「L2 的表达式里已经**没有**那个列引用了
> （编译期已展开成 `sum/base`）⇒ 定点替换命中不了它」——**是错的**。
>
> 用**真编译器**跑出来的两条 L2 产物（探针 `/tmp/p2820/probe.ts`，跑完即弃、不进仓）：
>
> ```
> A1 refine（无 filters）selectSql =
>    select sum(fct_x.net_amount) as value, bizday, branch_num from dbt.fct_x
> A2 refine（有 filters）selectSql =
>    select sum(t.value) as value, t.bizday, t.branch_num from (
>      select sum(fct_x.net_amount) as value, bizday, branch_num, branch_num from dbt.fct_x
>      where bizday = '2026-01-01' group by bizday, branch_num, branch_num) t
>
> A1 contains fct_x.net_amount? true
> A2 contains fct_x.net_amount? true
> ```
>
> **两种 refine 形态的 L2 `select_sql` 都逐字保留了被掩列的列引用** ⇒ 「定点替换命中不了它」
> 不成立（`compileRefine` 是 `select ${shape.expression} as value …`，`expression` 就是 L1 的表达式原文）。
>
> **真正的原因**：运行期驱动源是 `authz.ts:310` 的
> `maskedSelectSql(metric.selectSql, metric.masks, requester.hasScope)`——它**只吃本行的 `masks`**；
> 而 **L2 行的 `masks` 恒 `null`**（`metric-write.ts` 落库时不写 `mask_spec`；`metric-store.ts:71`
> 与 `authz.ts:72` 的注释都写死了这一点）⇒ **L2 永不被掩**。
> ⇒ **根因是「解析单位取错了」（按行），不是「列引用丢了」**。

**裁决（R10）= 路线 C：解析单位从「指标行」改为「列」**。

```
掩码集 = ⋃ { 声明 d : d.column 逐字出现在本次 metric.selectSql 里 }
         （d 取自【全部】指标行的列键声明，不只本行）
运行期按 d.column 做定点替换（§5.3 的做法块不变）
```

**行为只增不减**（这是选它的第一理由）：

| 场景 | 今天（按行） | 改后（按列） |
|---|---|---|
| L1 自己声明了 mask，本租户查它 | 掩 | **掩**（它的 `selectSql` 含自己的列 ⇒ 同样命中）——**不变** |
| **L2 读了同一个列** | **不掩（洞 = #820）** | **掩** ← 增量正好落在这里 |
| 别的 L1 读了同一个列 | 不掩（同型的洞） | 掩 |
| 整值掩码（`column: null`） | 指标级 | **仍是指标级**（见下「整值声明」） |

**不需要的东西**（C 相对路线 A/B 的核心优势）：**不需要** `base_metrics` 血缘列（路线 A），
**不需要**写 L1 时反向检查有无 L2 依赖（路线 B），⇒ **没有任何会过期的状态**——每次查询现算。
（路线 B 本来就没有抓手：`data.metrics` **没有** base/refs 列，全仓 grep
`base_metric|baseMetric|base_metrics` 48 处命中**无一是存储列**；唯一线索是 `compileRefine`
写进 `description` 的 `L2 派生自 <id>` 文本，脆弱。）

**与行业口径一致**（§9）：Snowflake Dynamic Data Masking、Databricks Unity Catalog column mask、
BigQuery policy tags **都是「列上策略、按 querying role 在读列时生效」**——掩码是列的属性，
不是某条查询/某个视图的属性。C 就是这条口径。

**配套三条**（前两条是**新增门禁**；第三条是**旧推论，实测已证伪**，见 §7 R12）：

1. 🔴 **同一列只许一处声明**（列 → 声明必须是**函数**）。两个指标声明同一个 `column` ⇒ **CI 红**。
   理由：C 之后「列 → 掩码」必须是单值的，否则「同一列被两条声明赋予不同 kind/step」无法裁决
   （静默取其一 = 另一种 fail-open）。落在 §4.3.1 那张检查表里（同脚本，不另起）。
   既有的「`column` 必须逐字出现在**声明它的那条指标**的 `selectSql` 里」（§5.3 理由 3）**保留**。
2. 🔴 **整值声明（`column: null`）今天一律拒**（唯一实现 = `maskItemError`，`scripts/sync-data-semantics.mjs`）；
   **整值形态只由默认档派生**（§4.1.1）。三条理由：
   - 「值」这个概念属于**指标**，不属于**列** ⇒ 整值**本就不该跨指标传播**，C 管不着它，
     放它进来就是**以同型的洞重新出现**（L2 又不继承）；
   - 全仓 **0 条** `mask:` 声明（实测）⇒ 收紧**零成本**，且合「无案例不立标准」；
   - 该形态的整值头正则在评审里有已知坏 SQL 边角（PR #827 的 M6，fail-closed）。
   ⇒ 将来真有案例再加回来：那是**新增**（走 PR + spec 修订），不是改语义。
3. 🔴 **FALSE**——**默认档不漏 L2**（不需要额外机制）：默认档的触发条件是「**本指标的 `selectSql` 读了带
   `sensitivity` 的列**」，而 L2 的 `selectSql` **保留了源列引用**（上面实测）⇒ L2 **同样**命中。
   ⚠️ **订正（2026-10-17 实测，见 §7 R12）**：上面这条**不成立**（原文保留作对照）——
   默认档是**整值 / 指标级**的 ⇒ **不按列传播** ⇒ **L2 不继承**；真正的兜底是 `L2_BASE_MASKED` 写侧守卫。

**`L2_BASE_MASKED` 守卫（T4 / issue #797）在 C 下的定位变化**：它的**前提**是「L2 会漏 ⇒
基于被掩 L1 的 L2 是绕过口」；C 落地后该前提**消失** ⇒ 它从**安全**约束降为**可用性**约束
（代价 = 一次 400，用户得换个做法）。

> **现状与处置（本轮不动）**：守卫已落地、有测试钉住、fail-closed，且**今天是空转**
> （无带掩码的 L1 行；生产 `data.metrics` 整表 0 行）。
> ⇒ **本轮保持原样**，把「C 落地后是否撤掉/放宽它」记为**待议**（§7 R11）——撤它属于
> **语义变更**，不在 #820 的射程里。
> 收口位置（存档）：`resolveL1Base`（refine / expr 两支与写路径的源闸预检都经它）；
> base 命中带非空 `masks` 的 L1 ⇒ 抛 `L2_BASE_MASKED`，HTTP/MCP 面 400 + `base`/`masks` 点名。
> ⚠️ 这里刻意不写夹具的实时计数（「2 行 / org `acme`」）：数字会随夹具演进而腐坏，且极易被
> 后来的读者误读成**生产现状**。夹具形状看测试文件，本文只给定性结论。

### 5.4 回包与指令面（**不做这条 = 另一种泄漏**）

回包 `QueryOk` 增**可空**字段：

```jsonc
{ "columns": [...], "rows": [...], "masking": { "net_sales": "round:1000" } }
```

**为什么必须有**：模型拿到 `1234000` 会报成「123.4 万**元整**」。**脱敏了但答成精确值 = 另一种泄漏**
（更隐蔽——用户以为系统给的就是准的）。

同步两处（**都在既有机制内**，不新造）：

1. `deploy/openclaw/data-query-plugin/skills/data-query/SKILL.md`——写死：
   **`masking` 非空 ⇒ 答「约 ¥X」「X 元上下」，不得报精确值**（随镜像走，重建部署生效）。
2. `query_data` 工具描述——同一条。

### 5.6 误伤怎么修，以及**自助的边界在哪**（R2 已裁决，2026-10-17）

**裁决**：`grantedBy` 特权码**由租户管理员发**——租户管理员在租户内是最高权限，发码走既有机制，
**不新增任何发码通路**。确切位置（2026-10-17 核实）：

- 端点 `POST /api/platform/admin/permissions/:code/users`——**挂载点是 `/api/platform/admin`**
  （`apps/server/src/app.ts:302` 的 `app.route('/api/platform/admin', adminRoutes(...))`），
  不是裸 `/admin`；处理器在 `apps/server/src/routes/admin.ts:151`。
- 门卫 `app.use('*', requireScope('tenant:admin'))`（`admin.ts:57`）——整组路由都要 `tenant:admin`。
- 该端点还校验 `code` 必须 ∈ 模块声明的 `permissions[]`（否则 404 `NO_SUCH_CODE`，`admin.ts:153`）
  ⇒ **这正是「码必须先写进 manifest」的机械保证**（§8.1 的第 ① 步不是可选项）。

**误伤的两条修法，一条自助一条不自助**（别含糊）：

| 症状 | 修法 | 自助？ |
|---|---|---|
| 「这些人本来就该看精确值」 | 租户管理员**发码**（既有机制） | ✅ 自助 |
| 「这个指标根本不该被掩码 / 该用取整而不是 NULL」 | 改 dbt YAML 的 `mask` 声明 → **PR** | ❌ 走 PR |
| 「这个列不该被标敏感」 | 改 `contracts/*.json` → **PR** | ❌ 走 PR |
| 「改了掩码**波及了别的指标**（R10 后按列生效）」 | 同上（改 dbt YAML / contracts）→ **PR** | ❌ 走 PR |

> **为什么中间档不自助**：`mask` 声明在 **git**（dbt YAML），不在租户可编辑的配置里。
> 让租户自助改「平台级口径声明」会开一个**绕开评审改口径**的口子——与既有的
> 「口径只能有单一定义、改动走 PR」（`docs/architecture.md` §5.1 第 1 条）冲突。
> 自助的是**授权**（发码），不是**口径**。

#### 5.6.1 ⚠️ 必须写明的一条：**这不是防租户管理员的机制**

租户管理员持有 `tenant:admin` ⇒ 他能给自己发 `data:precise`，也能给任何人发。
**所以列级/值级权限防的是「租户内的普通成员」，不防租户管理员。**

平台侧要「连租户管理员也看不到」，**唯一**的实现是**不让这个指标/源进这个租户**
（`sourceSystem ∉ adoptedSources` ⇒ `visibleMetrics` 过滤掉，`authz.ts:120-128`），
或平台侧不下发该指标。**码级收口做不到这件事**——因为所有码都按租户 org 供给，租户管理员都能发。

⇒ 结论写死：**别把 CLS/脱敏当保密机制卖。** 它是**权限分级**机制；对租户管理员的保密
只能靠「不给这个租户接这个源」。

## §6 验收

| 判据 | 怎么验 |
|---|---|
| **列级不可绕** | 不满足指标 `requiredScope` 的人：`/query` 回包无成本列 **且** 抓 `authz.plan.sql` 确认 SQL 里也没有；再走 MCP 与报表各打一次，同样结论 |
| **值级恒定性** | 同一指标换过滤 / 换时间窗 / 换分组 / 换 `total=true`，**掩码恒定**；`total` == 展示行之和（`round` 类） |
| **差分攻击** | 造两组只差一行的过滤，取两次结果之差 ⇒ **只能得到掩码后的值**，得不到精确值 |
| **单调性门会红** | 变异测试：给源列加 `sensitivity` 而指标不收窄 ⇒ **恰好** `gates` 变红（判据只有变异确认，见既有教训） |
| **报表发布门** | 三种构造各验一次：面板都无 scope ⇒ 发布后为 `null`；面板同一个码 ⇒ 发布后等于该码；面板**两个不同码** ⇒ **发布被拒且点名**。三种情况下低权限者 `/query` 仍被拒 |
| **审计** | 脱敏查询后 `data.query_audit.masking` 非空；**掩码生效的列**其记号两侧一致，`__exempted__` 只进审计、不进回包（见 §4.4.1） |
| **前端不算数** | 从 `rows` 原始 JSON 判，**不看界面** |

```
P1 列级（契约 sensitivity + 指标 requiredScope 声明面 + 血缘单调门 + 报表发布门）   ← 本 spec 主体
        │
P2 值级（mask 词表 + 列键解析（按列，R10/§5.3.1）+ 运行期定点替换 + masking 回包 + 审计 masking 列 + SKILL）   ← 本 spec 主体
        │
P3（只登记，不设计）维度级隐藏（dims 白名单，同一投影点）；标签批量（sensitivity → 策略映射）
```

与「掩码先于聚合」），再写码**——架构先行，顺序不得颠倒。

### 8.1 🔴 上线顺序（R6 的直接后果，不得调换）

因为 R1 判的是 **fail-closed**，而 `data:precise` 是**新码、今天无人持有**，
**先开闸 = 全租户问数同时返回 NULL**。所以：

```
① 权限码进 manifest（默认档的 data:precise，§4.1.1；以及各 mask 声明的 grantedBy），
   装载器按租户 org 供给（此时无人持有，行为不变）
② 租户管理员把码发给「今天本来就该看精确值」的人      ← 自助，走既有 /admin/permissions
③ 给契约列打 sensitivity                             ← 此时开闸才安全
④ 按租户灰度开闸，看一天再下一个租户
```

> **③ 的前置**：先盘点存量 L2（`select count(*) from data.metrics where source = 'l2'`），
> 逐个确认其 base 是否会被默认档覆盖——**不会**（R12）。这些 L2 在打标之前就已存在，
> `L2_BASE_MASKED` 守卫拦不住它们。

⚠️ **①②③ 的前两步有机械闸兜底**（§4.3.1 开闸前置闸）：① 的「码在不在 manifest」与
「打 `sensitivity` 前 `data:precise` 在不在」由 CI 判红，不靠人记得。**② 没有闸**——那是租户的
判断，见 §4.3.1 的射程说明。

⚠️ **② 不能省**。省了就是 §7 R6。按租户灰度是因为「该看的人是谁」是**每个租户自己的判断**，
平台不该替他猜（也无从猜）。

**P3 不预先做**的理由：dims 白名单与值级同机制、同投影点，**不需要新架构**，但今天**没有真实案例**
（无案例不立标准）；真需求出现时随依赖登记。
