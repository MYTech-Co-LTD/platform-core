# platform-core 个性化需求分级与模块租户隔离：设计

> 本文是「客户定制需求怎么受理、定制代码怎么管」的**规划稿**（spec-1，伞形口径）。
> **状态：设计定稿（2026-09-14 brainstorming 四问对齐），未落实施。**
> 工作铁律：实施中任何方向/范围调整，先改本文再动码。

## 0. 触发链与分解

「客户不管是平台托管还是自托管，有个性化需求怎么办」→ 审计发现：个性化处理无成文口径
（spec / architecture / module-protocol 全文搜「个性化/定制」零命中），且 demo 参考模块的表
**没有租户维度**（`modules/demo/migrations/001_note.sql`）——共享部署上租户间数据互见。

brainstorming 四问的答案（2026-09-14）：

1. 近期定制形态：**新模块（全新功能域）+ 壳层深度定制**（两者都有）；
2. 自托管客户：**5 家以上，私有化为主**；
3. 壳层定制发生线：**两条线都要**（平台托管运行期 + 自托管构建期）；
4. 定制代码归宿：**全进主仓，零 fork，跟 main 滚动升级**。

据此分解为三份 spec，各自走 spec → plan → 实施：

- **spec-1（本文）**：个性化分级口径 + 模块租户隔离约定 + 零 fork 收录规则 + 批量发放。先行。
- **spec-2（待立项）**：壳层主题/布局系统——L2 车道。两形态分层：租户行主题字段 + 运行期主题化
  （平台托管线）/ 构建期主题包（自托管线）；含布局、导航结构、登录页结构、多语言。
  **本文 §1 的 L2 口径倒逼它尽快排期。**
- **spec-3（待立项）**：私有化多实例交付——每客户一个 openship project、single 形态开通流程成文
  （含 runbook §6.1 订正、provision CLI 补齐）、升级跟版策略、每客户 Casdoor 归属。

## 1. 四级受理口径（L0–L3）

判定口诀：需求进来先问「配置能不能解」→「能不能装进一个模块」→「是不是壳」→ 都不是才是动架构。
逐级降级受理成本。

| 级 | 定义 | 典型需求 | 受理条件 | 动作与责任 | 生效周期 |
|---|---|---|---|---|---|
| **L0 配置** | 已有能力内的开关/参数 | 换 logo/主题色/产品名、开企微登录、绑域名、开/停模块、授权 | 无需开发 | 运营自助（平台托管线=平台超管在 Casdoor 后台；自托管线=客户 tenant:admin 在 console M3 页） | 即时（订阅 ≤TTL 60s） |
| **L1 模块** | 新功能域，`modules/<id>` | 工单系统、报表、客户专属业务页 | 不碰宿主/认证内核/壳；走 manifest 协议 + 三同纪律；**表必须带租户维度**（§2） | 开发（PR 过全门禁）→ 随宿主镜像发布 → 订阅发放（§4）→ 授权 | 开发周期 + 一次部署 |
| **L2 壳层** | 主题/布局/导航结构/登录页结构/多语言 | 白标、界面按客户重组 | **车道由 spec-2 建；建成前 L2 需求一律不接**——记入待办，不降级 hack、不临时改壳 | 主题包 / 租户主题配置（机制待 spec-2） | spec-2 落地后 |
| **L3 架构** | 动宿主/认证内核/模块协议/壳本身 | 改登录链路、改门卫语义 | architecture-first：先经人同意 → 改架构文档 → 再写码；**多租户形态下必须泛化**——为客户私有改共享面 = 改全体客户，不接受 | 架构评审 | 视改动 |

附则：

1. **L1 内的「改既有模块」**：给某客户往共享模块加行为，优先做**模块内配置开关**（env / manifest
   参数）；fork 新模块 id 属例外，需评审立项——5+ 家客户下 fork 是失控起点。
2. **L2 是唯一「现在没有车道」的级**：把「不接」写明白，倒逼 spec-2 尽快立项，而不是让第一个
   壳层需求以 hack 形态混进 L3。

## 2. 模块租户隔离约定（L1 护栏）

问题：demo 参考实现的 `demo.note` 无租户列（`id/body/created_at`）——照它抄的模块在共享部署上
租户间数据互见。identity 里现成的租户材料是 `orgId`（`modules/demo/index.ts`）。

约定（**正文唯一事实源回写 `docs/module-protocol.md` 新节「租户数据隔离」，本节只记决定与理由**）：

1. 模块表分两类：**租户数据表**必须带 `org text not null` 列（值 = `identity.orgId`）；
   **全局表**（字典/配置类跨租户共享数据）可不带，须在模块 README 声明理由（评审点）。
2. 查询纪律：租户数据表的所有读写按 `c.get('identity').orgId` 过滤；唯一约束必须含 org
   （`unique(org, …)`——漏掉会出现「A 租户占住名字，B 租户用不了」）。
3. 索引：租户数据表的热路径索引以 org 为前缀列（查询都带 org，不前缀等于全表扫）。

**隔离键 = `org` 文本列，不用 `tenant_id` 外键**：identity 现成 orgId，模块代码零 join、自包含；
不跨 schema 引 `platform.tenant`（B1 边界干净）；org 与租户 1:1，权威源在 Casdoor + 租户行。

**强制方式**：本期 = 文档约定 + demo 模板修正；CI lint（扫模块 migrations 建表必须含租户列）
**待沉淀**——第一个真模块案例落地后再评估升级（本仓规矩：门禁升级是单独的决定）。

## 3. 零 fork 收录规则

1. 客户定制代码进主仓**只允许三种形态**：**模块**（`modules/<id>`）/ **主题包**（形式待 spec-2
   定义，暂挂）/ **配置开关**（模块内 env、manifest 参数、租户行字段）。
2. 命名：客户专属模块 id 带客户前缀（`<customer>-<func>`，如 `acme-report`），通用模块不带——
   一眼识别归属、防撞名（纯约定，无技术强制）。
3. 同质量门禁：客户代码与平台代码过同一套 CI/PR 纪律；B1/B2 lint 天然拦「客户逻辑散进平台面」
   （跨 schema 即红）。
4. 不接受：宿主/共享模块里的「某客户特判」（`if 客户==acme` 式）；评审按 §1 的 L1/L3 边界拦。
5. 例外口子：合同约定代码归客户、或合规要求物理隔离的，零 fork 解不了——单独仓/分支 +
   商务与架构双确认，属个别案例不进主策略。

## 4. 新模块 → 存量租户批量发放

- 口径：**merge main ≠ 客户可见**——发放（订阅）+ 授权才可见；发放是发布清单的必要一步。
- 落地：`scripts/provision-tenant.mjs` 增强 `--all-tenants --module <id>`：遍历
  `platform.tenant` 各 org 执行 `ensureModulePlan` + `upsertSubscription(Active)`，幂等可重跑
  （与 SaaS 管理域 spec D2「plan 按租户 org 各建一份」同构）。
- 「新租户 → 补发已订模块」方向 CLI 已有的 `--module` 覆盖，不动。

## 6. 已知边界

1. L2 车道建成前一律不接 ⇒ **第一个真实壳层需求到达前，spec-2 必须排期**（本文立此存照）。
2. 「主题包」形态未定义（等 spec-2），§3 第 1 条该形态暂挂。
3. CI 门禁暂缓（§2）：护栏当前 = 文档 + 模板 + 评审。
4. 定制代码的商务归属由合同定；本文假定「付钱定制、代码沉淀进产品」模式。
