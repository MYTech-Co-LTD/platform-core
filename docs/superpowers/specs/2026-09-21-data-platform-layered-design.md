# 数据平台分层设计（采集 → 清洗 → 语义 → 消费：BI 与智能问数）

- 日期：2026-09-21
- 状态：**设计稿，待评审**
- 依据：2026-09-20/21 的调研与本机全链路实测（ZOS 实读、dbt→pg_duckdb、Metabase、OpenClaw/Ossie/MCP 调研）
- 关联：`2026-09-20-data-stack-module-design.md`（模块接入与选型定稿）、`docs/module-protocol.md`、
  `deploy/delivery-private.md`；经验库《duckdb-ossie 全链路 PoC》
- **本文回答**：一个新的数据源从进到出，每一层做什么、不做什么、边界在哪，以及
  **精准性 / 自由性 / 响应速度** 三个目标各自靠什么实现、在哪里互相冲突。

---

## 1 先看清冲突：三个目标两两拉扯

| 目标 | 靠什么达成 | **代价** |
|---|---|---|
| **精准性** | 契约 + 类型化 + 单一事实源 + 测试 + 对账 | 严格 ⇒ 改一次要走 PR，**慢** |
| **自由性** | 自助切片、任意维度组合、AI 按指标问 | 自由 ⇒ **口径分叉**风险 |
| **响应速度** | 物化 / 预聚合 / 缓存 | 物化 ⇒ 只算好固定组合，**自由度下降** |

**⇒ 唯一的解法是「分层，每层只解一个」，并把冲突点显式钉在某一层。**

| 冲突 | 钉在哪一层 | 怎么钉 |
|---|---|---|
| 精准 ↔ 自由 | **口径在语义层，切片在消费层** | 口径只能定义一次；消费层只能组合，不能改义 |
| 自由 ↔ 速度 | **物化层做「按需物化」** | 不是全量物化（慢），也不是不物化（自由但卡） |
| 精准 ↔ 速度 | **测试与对账是异步的** | 不阻塞查询；红了下线物化，不阻塞源 |

## 2 分层架构（七层）

```
┌─ ① 采集层（duckle）──────────────────────────────────────────┐
│  职责：调 API / 取数 → 落 parquet（每租户一桶）                │
│  ★ 在这里定型：schema 声明 + 类型化 + 分区 + 批次标记           │
│  不负责：业务口径、join、去重规则                              │
└───────────────────────────┬──────────────────────────────────┘
            parquet（对象存储，分区清晰，可回溯，不覆盖历史）
┌───────────────────────────▼──────────────────────────────────┐
│ ② 落地区（Raw / Bronze）—— 原样保留，只读                      │
│  职责：可回溯、可重算的「事实底账」                             │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
│ ③ 清洗层（dbt staging / Silver）★ 一对一，不改语义              │
│  职责：类型化 cast、编码/单位/时区统一、去重、命名规范化         │
│  不负责：业务聚合、跨表 join、口径                              │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
│ ④ 建模层（dbt intermediate + marts / Gold）                   │
│  职责：join（星型：事实+维度）、粒度明确、**业务口径定义在此**    │
│  不负责：展示格式、权限                                  │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
│ ⑤ 语义层（指标/维度声明）★ 声明，不是物化                       │
│  职责：指标名+表达式+粒度+owner+tier；维度的可切片轴             │
│  不负责：权限、物化、展示                                       │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
│ ⑥ 物化层（按需）                                               │
│  职责：把「被消费的组合」物化成表/视图，供低延迟读               │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
│ ⑦ 消费层                                                      │
│  · BI（Metabase）：读物化 + 构建器自由切片                      │
│  · 智能问数（OpenClaw → 平台 MCP）：按指标/维度问               │
│  · 应用/页面：平台 API                                        │
└───────────────────────────────────────────────────────────────┘
        ┌──────────────────────────────────────────────┐
        │ 贯穿：治理（平台模块）——身份/权限/租户/词表裁剪 │
        │      血缘 · 测试 · 对账 · 审计                │
        └──────────────────────────────────────────────┘
```

## 3 每层做什么、不做什么（分工表）

| 层 | 谁实现 | **必须做** | **明确不做** |
|---|---|---|---|
| ① 采集 | **duckle** | 取数、**落盘即定型**（类型/schema）、分区、批次标记、幂等可重跑 | 业务口径、join、去重规则 |
| ② 落地 | 对象存储 | 原样保留、不覆盖历史、可回溯 | 任何转换 |
| ③ 清洗 | **dbt `staging/`** | **一对一**映射、类型化、规范化、去重 | 业务聚合、跨表 join、口径 |
| ④ 建模 | **dbt `marts/`** | join、粒度、**口径在这里定义一次** | 展示格式、权限 |
| ⑤ 语义 | **dbt 的语义声明**（或 Ossie 格式） | 指标/维度/粒度/owner/tier 的**声明** | 物化、权限、展示 |
| ⑥ 物化 | **dbt（按需 `--select`）+ 调度** | 物化被消费的组合、缓存 | 定义口径 |
| ⑦ 消费 | Metabase / 平台 MCP / 页面 | 展示、切片、问 | **定义或改口径** |
| 治理 | **platform-core 模块** | 身份/权限/租户、**词表裁剪**、血缘、门禁、对账 | 算数 |

> **最重要的一条纪律**：**口径只能在 ④ 定义一次**。③ 只规范化不改义，⑤ 只声明不计算，⑦ 只组合不改义。

## 4 一个新数据源从进到出（标准路径）

| 步 | 在哪 | 动作 | 产物 |
|---|---|---|---|
| 1 | ① | 摸清源 API 的字段与类型 → **写 schema 声明**（含类型） | 契约文件 |
| 2 | ① | duckle 管线：取数 → **按声明 cast** → 落 parquet（分区 + 批次标记） | `s3://<bucket>/<domain>/<table>/<date>/all.parquet` |
| 3 | ③ | `stg_<table>.sql`：**一对一**，用 `r['col']::type` 取列并定型 | `staging.stg_<table>` |
| 4 | ③ | 加 dbt tests：`not_null` / `unique` / `accepted_values` / 金额范围 | 测试 |
| 5 | ④ | `dim_*`（维度）、`fct_*`（事实）：join + 粒度明确 | 星型模型 |
| 6 | ④ | 口径模型：把「有效订单」「净销售额」等定义在这里 | 口径表/视图 |
| 7 | ⑤ | 声明指标与维度（名字、表达式、粒度、owner、tier） | 语义声明 |
| 8 | ⑥ | 按消费需求物化（高频组合） | 物化表 |
| 9 | ⑦ | BI 建看板 / AI 问数 / 页面接 API | 消费 |
| 10 | 治理 | 登记血缘、跑对账、入 CI 门禁 | 可审计 |

## 5 三个目标各自靠什么实现

### 5.1 精准性（源头治本 + 多层兜底）

| 手段 | 落在哪 | 说明 |
|---|---|---|
| **落盘即定型** | ① | **金额/时间/日期在写 parquet 时就 cast 成正确类型**（不是字符串） |
| **schema 契约** | ① | 字段集稳定；漂移必须显式处理，不能靠 `union_by_name` 兜 |
| **staging 一对一** | ③ | 唯一碰原始类型的地方；**不跳过这一层** |
| **口径单一定义** | ④ | 口径只出现一次 |
| **dbt tests** | ③④ | 断言（**cast 错了不报错，只有断言能抓**） |
| **对账** | 治理 | 每个指标一条独立复算，与物化结果比对 |

### 5.2 自由性（把"能切什么"做宽）

| 手段 | 落在哪 |
|---|---|
| **星型模型做全**（维度丰富） | ④ —— 维度不够，消费层就没得切 |
| **指标 + 维度声明** | ⑤ —— 组合自由来自声明，不来自物化 |
| **BI 构建器** | ⑦ —— Metabase 实测：基于 Model 可自由聚合/分组/时间分箱 |
| **AI 按指标问** | ⑦ —— 词表 = 声明的指标×维度 |

### 5.3 响应速度（分层物化，不是全量物化）

| 手段 | 说明 | 实测依据 |
|---|---|---|
| **分层物化** | staging 物化一次、marts 物化一次，消费层不再回源 | 1.09M 行聚合 **~1 秒** |
| **按需物化 + 缓存** | 消费层要什么组合就物化什么 | 解决「全量物化慢 / 不物化卡」的两难 |
| **分区裁剪** | parquet 按日期分区 ⇒ 只读需要的分区 | 建 1.09M 行 staging **36 秒**（读 83 个文件） |
| **物化存储要算账** | **实测膨胀 ~8 倍**（515KB parquet → 4136KB 表） | 别全量物化 |

## 6 模块化：业务模块怎么接进来

**每个业务模块是一个「数据域」**，自带 ①③④⑤，共享治理与消费入口。

| 面 | 每模块自己的 | 平台共享的 |
|---|---|---|
| 数据 | **自己的 schema**（三同纪律）、自己的 bucket 前缀 | — |
| 管线 | 自己的 duckle 管线 | 采集规范（契约/幂等/批次标记） |
| 模型 | 自己的 dbt 目录（`models/<module>/`） | staging 规范、命名规范、测试基线 |
| 语义 | 自己的指标命名空间（**`<module>:<metric>` 前缀**） | 语义格式、词表裁剪机制 |
| 消费 | — | BI / 智能问数 / 页面入口 |
| 治理 | — | 身份权限租户、血缘、门禁、对账 |

⇒ **模块之间不互相读数据**（跨模块联动必须走 API 或物化交换，见模块协议的 B1 纪律）。

## 7 硬约束清单（写死，违反会静默出错）

1. **落盘即定型**：金额/时间/日期在 ① 就 cast 成正确类型；**不落字符串**。
   ⚠️ **2026-09-22 拍板注记**：本条适用范围**收窄**——新数据源接入尽量在落盘侧做对；
   存量 parquet（VARCHAR）不重落盘、由 staging 手写 cast 补，见 §10 拍板记录·分叉 1。
2. **字段集稳定**：schema 漂移必须显式处理（改契约），**不靠 `union_by_name` 兜**。
3. **staging 一对一**：③ 不改语义、不做 join。
4. **口径单一定义**：④ 只定义一次；⑤ 只声明；⑦ 只组合。
5. **消费层不改义**：BI/AI 只能组合已声明的指标与维度。
6. **物化要算存储**：×8 膨胀；按需物化。
7. **对账是硬要求**：每个指标一条独立复算（**cast 错了静默，只有它能抓**）。

---

## 8 治理（已验通的四机制，见模块接入 spec §10）

- **记录**：结构化 `COMMENT`，与 DDL 同迁移
- **血缘**：Postgres 目录递归（免费、不漂移）+ parquet 源解析
- **排查**：五步阶梯（读定义 → 看 viewdef → 递归依赖 → 抽 s3 路径 → **独立复算**）
- **门禁**：四条 CI（COMMENT 齐全 / 字段齐全 / **声明与实现一致** / 同名唯一 + 对账通过）

## 9 已知的坑（本次压真实数据挖出来的五条，全部实测）

| # | 坑 | 表现 | 处置 |
|---|---|---|---|
| 1 | **parquet 列全是 `VARCHAR`** | 金额 `"12.79"`、时间 `"2026-07-01 10:02:34"` 都是字符串 | **落盘即定型**（约束 1） |
| 2 | **schema 漂移** | 同一域不同日期：46 列 vs 43 列（`supplier_*` 时有时无） | 显式处理（约束 2） |
| 3 | **两个时间列两种格式** | `order_time` = `2026-07-01 10:02:34`；`order_detail_bizday` = **`20260707`** | 落盘即定型 |
| 4 | **`DOUBLE` 不是 pg_duckdb 可用的 cast 目标** | 报错 `type "double" is only a shell` | 用 `numeric` / `float` |
| 5 | **★ 读 parquet 必须 `r['列名']` + 别名 `r`** | `SELECT *` 能过，**点名取列 `column does not exist`** | 写进 staging 规范 |

> 第 5 条是 pg_duckdb 的机制（报错里有提示），**但 `SELECT *` 的成功会掩盖它** —— 新写 staging 的人必然踩。

## 10 需要拍板的分叉

### ✅ 拍板记录（2026-09-22）

> 以下分叉经人拍板、逐叉销账（含一项上游确认）。下方分叉表与 §7 硬约束清单**原文不删改**（历史留档），
> 与本记录冲突处**以本记录为准**。

1. **上游确认**：dbt 主干地位 = 对 09-20 定稿 §11.1 的**生效扩展**（定稿生效、dbt 提前）。
2. **分叉 1（采集侧定型在哪做）**：**dbt staging 承担**——parquet 允许 VARCHAR 存量
   （乐檬实测坑 #1，见 §9 表），`stg_*.sql` 手写 cast，**存量不重落盘**；cast 正确性靠
   dbt tests / 对账断言兜（§5.1 原文口径：**cast 错了不报错，只有断言能抓**）。
   「落盘即定型」硬约束（§7 第 1 条）的适用范围**相应收窄**：**新数据源接入时尽量在落盘侧做对**，
   存量按 staging 补（§7 第 1 条旁已加指向注记）。
3. **分叉 2（语义声明格式）**：**dbt YAML 为事实源**，Ossie 暴露经 **dbt 原生 Ossie 支持**
   （拍板人指出：dbt 原生支持 Ossie，此前材料假设的「YAML→引擎格式自建转换层」代价**不成立**；
   此条按拍板人口径记录，出处=选型实测人裁定）。事实源纪律仍守 09-20 定稿 §11.7
   （引擎只当编译产物）。
4. **分叉 3（智能问数的入口）**：按定稿安全论断**确认销账**——OpenClaw → 平台 MCP
   （已随 PR #146 落地）；Metabase MCP 记为「不经 facade 不合规」的**观察项**。
5. **分叉 4（物化调度）**：**openship jobs**——`dbt --select` 由 job 定时打；**零新组件**；
   handbook §3 已同向。
6. **分叉 5（L2 表达力）**：**定义权下放**——租户管理员与平台超管均可**定义**指标与语义
   （不止 A 薄档的组合/裁剪四件事）；定义产出仍是**受治理的、可机检的声明**（禁任意 SQL 不变）；
   **预留 agent 接入面**（后续接 agent 做这层，接入本身另题不在本轮）；门禁③「声明与实现一致」
   的机检范围须**覆盖用户/agent 产生的声明**。C 厚档维持定稿排除。

| # | 分叉 | 选项 |
|---|---|---|
| 1 | **采集侧定型在哪做** | duckle 管线内（需改 duckle）vs 落盘后由 dbt 定型（staging 层承担） |
| 2 | **语义声明格式** | dbt 的 YAML（成熟）vs Ossie 格式（可迁移，但实现弱） |
| 3 | **智能问数的入口** | OpenClaw → 平台 MCP（带权限，per-requester OAuth）vs Metabase MCP |
| 4 | **物化调度** | dbt + openship jobs vs 常驻调度 |
| 5 | **L2（租户级语义）的表达力** | A 薄（可见性+过滤+别名+目标值）/ B 中（+受限表达式）/ C 厚 |

## 11 资源画像（实测，供选机器）

| 项 | 实测 |
|---|---|
| dbt 内存 | 3 模型 204 MiB → **100 模型 222 MiB**（几乎不涨） |
| pg_duckdb 内存 | threads 1→191 MiB；threads 4→**199 MiB**（几乎不变） |
| 建 1.09M 行 staging | **36 秒**（读 83 个 parquet） |
| 1.09M 行聚合 | **~1 秒** |
| 物化存储膨胀 | **~8×** |

⇒ 在百万行量级，**dbt + pg_duckdb 各约 200 MiB**。资源门槛要等数据量再上量级才显现。
