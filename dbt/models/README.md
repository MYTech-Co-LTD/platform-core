# `models/` — 两轴布局：**域**（顶层）× **客户分叉**（嵌在域里）

> 本文是 `dbt/models/` 的**结构约定**。域开关的机制与实测、以及「一个数据面只物化自己的域」这条
> 不变量的**口径与理由**，见 `docs/architecture.md` §2.5 与 `dbt/README.md` §1.1 —— 本文不复述。

## 0 两个词，别混

| 词 | 指什么 |
|---|---|
| **域**（domain） | **一类数据的采集/建模归属**（`lemeng` 零售、`forms` 表单…）。顶层目录 = 域。 |
| **客户**（customer） | **交付对象**（如 `shanhai`）。客户分叉是**某个域内**的口径分叉，嵌在该域目录下。 |

> 2026-10-17 之前是**单轴**（`common/` = 所有客户共用，`customers/<客户>/` = 客户特有），
> 而 `common/` 的定义其实是「**所有客户共用的域**（当前只有乐檬）」—— 它一直是**乐檬域的默认部分**。
> forms 域落地时这个单轴撑不住了（forms 既不「所有客户共用」，也不是任何客户的私有分叉）⇒ 改成
> **域为顶层轴、客户嵌在域里**，`common/` 溶解成域的默认。

## 1 目录形态

```
models/
├── <域>/                       # 顶层 = 域（小写蛇形，如 lemeng / forms）
│   ├── staging/                # ③ 清洗：一对一、只规范化不改义
│   │   ├── sources.yml         # 本域的落地声明（**不是读路径**，见 dbt/README.md §2.1）
│   │   ├── schema.yml          # 列描述 + dbt tests
│   │   └── stg_<源>_<表>.sql
│   ├── marts/                  # ④ 建模：口径只在这里定义一次
│   └── customers/              # 按客户分叉（**域内的**口径分叉）
│       └── <客户标识>/         # 与交付/客户标识一致（如 shanhai）；**小写蛇形**
│           ├── staging/        # 该客户特有的源 → 一对一 staging（命名仍受规则 ④ 机检约束）
│           ├── marts/          # 该客户特有的口径模型
│           └── schema.yml      # 列描述 + tests
└── tests/                      # 见 dbt/README.md §1
```

- **目录先建、约定先立**，但**里面有真模型之前不要建空的客户子目录**（空目录在 dbt 里没有意义，
  只会让「这个客户接过没有」变成看不出来的事）。
- **域目录 = 域开关的判据面**：新增一个域目录**必须**同时在 `dbt_project.yml` 的
  `models.platform_data` 下登记 `+enabled` —— 否则 dbt 默认 `enabled: true`，**每个数据面都会 build
  它**（门禁规则 ⑪ 双向机检，缺一即红）。机制见 `dbt/README.md` §1.1。
- **客户目录里不复制本域已有的模型**。要改共用口径 ⇒ 改域目录（走 PR，被看见），不是在本目录 fork
  一份 —— 口径只能有单一定义（layered §7 约束 4）。
- 客户模型引用共用层照旧 `{{ ref('stg_lemeng_retail_order_line') }}`（跨目录 ref 在 dbt 里是正常的）。
  ~~旧湖的 `stg_lemeng_retail_detail`（双轨期保留件）~~ 已于 2026-10-06 **仓内退役**（`git rm`）
  ⇒ 仓内**只剩新湖形态**的 staging 可参照：取列一律「函数别名 + `r['列名']`」，**别照 CTE 形态写**
  （见 `dbt/README.md` §3 第 1 行）。
- **命名空间是**全仓一条规则**，不因为分了目录就放宽**：客户特有指标与域内指标放在同一份声明文件里
  （`dbt/semantics/l1_metrics.yml`），同受静态门禁规则 ⑥ 约束（三段式 `<源>:<业务域>:<指标>`，三段都
  小写蛇形），**同名唯一**。形态与判据见该文件头注与规则 ⑥（**客户标识落哪一段**以该声明文件的字段
  约定为准，本文不复述）。

## 2 加一个客户分叉时要动的东西（同一个 PR，少一件即半接）

| # | 动什么 | 为什么 / 机检 |
|---|---|---|
| 1 | `models/<域>/customers/<客户>/staging/sources.yml` 声明源 | 规则 ④ 会要求同名 `stg_<source>_<table>.sql` 存在（双向） |
| 2 | 对应的 staging 模型（手写 cast，含 `r['` 取列） | 规则 ①（cast 规范见 `dbt/README.md` §3） |
| 3 | `marts/` 的口径模型（口径只定义一次） | 纪律，无机检 |
| 4 | `dbt/semantics/l1_metrics.yml` 里声明客户指标（必填字段齐全） | 规则 ⑤⑥ |
| 5 | 每个新声明指标一条 `dbt/tests/<源>/audit_<指标>.sql`（文件名用 `metricToAuditFileName()` 算，别手写） | 规则 ⑦（含映射无碰撞） |
| 6 | `dbt/README.md` §8「实证 vs 暂定」表补该客户的行 | 否则下一个接手的人分不清哪些是猜的 |

**只加源不加契约与管线 = 半接**：新增数据源的三件套（`contracts/` 采集契约 + `duckle/` 管线 +
本目录 staging）必须同一个 PR（`docs/architecture.md` §5.1 第 2 条）。该纪律**当前没有静态门禁**，
靠评审守。

## 3 私有化交付时的边界

- 客户特有的**路径/桶名/凭据**一律走 env（`profiles.example.yml` 登记的键名 + openship env(isSecret)），
  **不进仓**：本目录的任何文件里不许出现明文凭据（含注释）。
- 客户特有模型若只对某个客户成立，**在那个模型文件头注明**（谁、什么时候、为什么）——
  本目录里「看起来通用其实只对一个客户成立」的模型是最容易伤人的形态。
