# 平台问数 Skill

用户问**业务数据**时使用。权限由平台按当前对话人实时裁决——你能看到的词表就是这个人能问的全部。

## 方法论：先判问法，再选策略（v2，spec §8.3）

**每次开查前先给问法归类**，按表选策略，不要默认裸拉明细：

| 问法 | 策略 |
|---|---|
| 单点（某天 / 某店某天） | 直接查明细（行数 ~74–220/天/账套，安全） |
| 区间合计（近N天 / 本月共多少） | **先 `args.total=true` 拿总数**（服务端求和恒返回单行）；需要分布再按天拆单日查 |
| 区间分布（按天 / 按店走势） | 说清分组；**先窄后宽**（先单账套、先 2~3 天探行量） |

**行数预算**（超预算 = 生成极慢、用户观感卡死）：net_sales ≈147 行/天（3120）/ ≈74 行/天（64188）；
区间×双账套 ≈ 天数×220——**区间超过 4 天必用 `total:true`**，不要裸拉明细。

## 查询约定

1. **先 `list_metrics()`**：看当前用户可见的指标（id/名称/参数说明）。词表按人裁剪且随权限实时变——**以返回为准，勿凭记忆**。
2. **再 `query_data({ metricId, args })`**：args 按该指标的参数说明给，日期一律 `YYYY-MM-DD`。
3. **明细与合计互斥**：`total:true` 的回包恒单行 `{columns:["total"],rows:[[合计值]]}` 且 `truncated` 恒 false；要明细就不传 total，要总数就别拉明细。

## 纪律（回包信号 → 动作）

- **`truncated:true`**：只能答「数据不全」，**不得当全量下结论**；收窄范围或改传 `total:true` 重查。
- **`error` 带参数不合法（BAD_PARAM）**：读 error 里的 detail（哪个键、什么毛病）**自纠**后重发；**同一个错误调用不要原样重试**。
- 回包 `subject` 是本次钉死的数据主体（汇报时顺带说明数据范围）；该范围没有数据就如实说，**不要编数**。

## 汇报与行为

- **调工具前先说一句要查什么**（如「我查一下上周销售额」）——用户立刻能看到进度，不用干等。
- 数据用 markdown 表格 + 一句话结论；合计就报总数，明细用表格分行。
- `error` 带「扫码登录」= 对话人还没关联平台账号：把指引原样转告即可，**不要重试**。
- `error` 提示不在可见范围 = 权限如此：如实转告，**不要换词试探其他指标**。
