# contracts/customers/ — 客户级契约覆盖

**用途**：同一个数据源、不同客户**字段集不一致**时，把该客户的契约放这里。

```
contracts/customers/<客户>/
  └── <源>.<表>.json        ← 形态与 contracts/common/ 完全一致（同一份元 schema）
```

**三条纪律**：

1. **形态同源**：客户级契约与 `common/` 的契约**用同一个元 schema**
   （`../common/_schema.schema.json`）、同一套字段语义。**不另立格式**——两份格式并存
   就等于「契约」有两种含义，校验器再也没法一把过。
2. **只放差异的完整声明，不放补丁**：契约是**声明式**的（声明结果，不声明增量）。
   客户级契约也是**一份完整契约**，不是对 `common/` 那份的 diff/patch。
   ⇒ 复制 `../common/<源>.<表>.json` 后改成本客户的真值，而不是写「在 common 基础上加两列」。
   （理由：落盘前校验要的是「这批数据应该长什么样」的一个确定答案，不是一份要按顺序
   执行才能算出来的补丁——补丁的解析顺序会变成一个隐性事实源。）
3. **`domain` / `table` 不变**：客户级覆盖改的是**列集与分区**，不改表身份。
   ⇒ 若客户需要的是一张**不同的表**，那它就该是新源，进 `common/`，不是客户覆盖。

**⚠️ 本目录当前为空目录（只有本 README）** —— 这是**计划的形态**，不是遗漏：
本任务（T5）只交付目录约定与元 schema，**实际客户级契约随对应的接入 PR 落到这里**。

**⚠️ 覆盖的优先级尚未定义**：`common/<源>.<表>.json` 与 `customers/<客户>/<源>.<表>.json`
同时存在时，**谁赢**——本任务**不拍这个板**（它依赖客户级覆盖的第一个真实案例）。
在有人按案例定下规则之前：**不要去猜顺序**，遇到两者并存就问 owner。
